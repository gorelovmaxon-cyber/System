# System2 operations and recovery

Этот runbook сводит ежедневную работу, запуск и восстановление. Команды ниже выполняются
из корня текущей копии `System` (на этом ПК `E:\SystemTheBest\System`). Секреты вводятся локально и никогда
не копируются через Git.

## Короткий порядок ежедневной работы — принятый core

Текущий выпуск: `systemqwen` и `site-portfolio`, общая память, локальный поиск и Git-обмен.
`trading-dev` и `autopilot-framework` подключаются позже; их `local_paths` сейчас не менять.

1. Перед работой из корня `System` выполните `git status --short --branch`, затем
   `git fetch origin master`. Если есть свои или чужие незавершённые правки, сначала
   разберите их и проверьте возможные совпадения путей с обновлением. Для чистых
   отслеживаемых файлов получите изменения командой `git merge --ff-only origin/master`;
   при отказе остановитесь и согласуйте расхождение без force/reset.
2. Прочитайте актуальный [HANDOFF](../HANDOFF.md), обязательные правила проекта и
   файл текущего задания. Для `site-portfolio` также прочитайте его собственный
   HANDOFF в подтверждённом локальном каталоге. Старые снимки в System HANDOFF
   обозначены как архив.
3. Если появилось полезное **проверенное** знание, сохраните его с точными
   `evidence`, `source` и `scope` (зарегистрированный `systemqwen`, `site-portfolio`
   или `user` для действительно общего правила):

   ```powershell
   node scripts/memory/save.js --category facts --statement "Подтверждённый факт" --evidence "путь к проверенному источнику или точная ссылка" --source "задача и дата" --scope systemqwen
   node scripts/memory/search.js --query "Подтверждённый факт" --project systemqwen --limit 3
   ```

   Сверьте в результате `source`, `scope` и текст с исходным доказательством.
   При отсутствии нового полезного знания запись в память не нужна. Записи с
   `U+FFFD` не используйте как подтверждённые факты без сверки источника.
4. Перед публикацией проверьте `git status --short`, добавьте только файлы своей
   задачи через `git add -- <путь1> <путь2>`, затем проверьте
   `git diff --cached --name-only` и `git diff --cached --check`. Коммит содержит
   ID задания: `git commit -m "<ID>: краткое описание"`. Публикуйте обычным
   `git push origin master` по [правилам workflow](system-workflow.md#коммиты-и-синхронизация).
   Не добавляйте секреты, `config/system.local.json`, `.env` и чужие черновики.
5. После push сравните `git rev-parse HEAD` и
   `git ls-remote origin refs/heads/master`. Перед сменой ПК оставьте в актуальном
   HANDOFF результат, evidence, остаток, следующий шаг и опубликованный SHA;
   на другом ПК начните снова с пункта 1.

Docker/Activepieces необязательны для этого порядка; Windows/WSL не трогать.
Figma исключена. Дефект `U+FFFD` остаётся открытым.


Для этого проверенного способа откройте **новый** сеанс Claude Code из корня сайта

клиенту всё равно не открыт доступ к папке System, предоставьте его средствами клиента;
неизвестная команда сама не прочитает файлы на другом диске.

### Работа с одной задачей через start

В целевом чате GPT предоставьте агенту доступ к файлам проекта и инструментам
System2. Укажите корни проекта и System; попросите прочитать правила проекта
(`AGENTS.md`/`CLAUDE.md`, если есть), актуальный `HANDOFF.md` и текущее задание.
Обратитесь к агенту один раз: «Старт: <задача>». Это текст запроса на маршрут
из [workflow](system-workflow.md#один-start-для-новой-задачи-сайта), **не**
зарегистрированная slash-команда и не гарантия автоматической загрузки правил
в любом клиенте. Новый сайт или существенная переработка выбирает
[site-build](../.claude/skills/site-build/SKILL.md) и читает
[стандарт сайтов](standards/site-creation.md) напрямую. После существенных
вопросов и согласованной spec агент сохраняет brief, spec с дизайн-системой и
адаптивной сеткой, тикеты и пакет передачи. В планирующей роли/systemqwen он
останавливается до реализации; разрешённое исполнение продолжается по контракту
ролей/autopilot. При повторном обращении он должен продолжить этап из HANDOFF,
не проводить интервью заново. В новой сессии сначала сверяйте файлы, а не
восстанавливайте решения по старому чату. Исторически проектный адаптер и доступ
к System проверены также в Claude Code CLI 2.1.280 через `/start`; его API 402
в поздней пробе не блокирует работу в целевом чате GPT. Живой планирующий проход
и агентный checkpoint без подсказок требуют отдельного вердикта по evidence.

После планирования пользователь открывает чат выбранного исполнителя и передаёт ему локальный
пакет: согласованную spec, один ограниченный тикет, правила проекта, HANDOFF и
критерии проверки. Исполнитель реализует только этот тикет и фиксирует результаты;
независимый приёмщик проверяет их отдельно. Само обращение start не запускает другого
агента и не подтверждает выполненную реализацию. Без ответа пользователя на
существенный вопрос или доступных файлов и инструментов этап остаётся ожидающим.

Подтверждённые решения и новые полезные знания агент сохраняет через штатный
`save.js` на контрольной точке и проверяет через `search.js`; отсутствие нового
знания допускает отсутствие записи. Перед финальным ответом после содержательного
обращения агент фиксирует новое в проектном [журнале](decision-journal.md) или
делает no-op. На границе задачи разбирает `pending`, затем отмечает перенос после
успеха writer и обновляет HANDOFF. Состояния `persisted`, `indexed` и `synced`
проверяются отдельно. Перед сменой ПК опубликуйте scoped-коммит проекта и System,
сверьте SHA каждого с его remote и оставьте в HANDOFF этап, ссылки на spec/тикет,
проверки, остаток и следующий шаг. После аварийного закрытия до контрольной точки
последние ответы могли не сохраниться: проверьте файлы и память, затем восстановите
недостающее с пользователем. На новом ПК повторите локальную настройку доступа к
единственной копии System; игнорируемые local config и секреты Git не переносит.

## Профиль `core` — основной путь без Docker (решение пользователя 2026-09-23)

Основной профиль (`config.profile: "core"`, действует по умолчанию, если поле
не задано ни в example, ни в local config) не требует Docker/Activepieces и не
устанавливает захват очереди через git hooks:

1. `node scripts/memory/bootstrap.js --root <root>` — создаёт/обновляет
   `config/system.local.json`, не ставит hooks и не поднимает Docker; если на
   этой машине раньше был включён hooksPath `.git-hooks-templates` этого
   репозитория, снимает именно его (чужой hooksPath не трогает).
2. `node scripts/memory/doctor.js --json` — Khoj/bridge/Activepieces при
   `enabled: false` показываются как `disabled`, а не `PROBLEM`; включённая, но
   недоступная интеграция остаётся видимой ошибкой.
3. Локальная запись и поиск работают без внешних сервисов:
   `node scripts/memory/save.js --category facts --statement "..." --evidence "..." --source "..."`,
   затем `node scripts/memory/search.js --query "..." --project <project_id>`
   (без Khoj — локальный fallback с source/scope).
4. `node scripts/memory/sync.js --status`, затем `sync.js --push` на границе
   блока/передачи.

Khoj остаётся полезным необязательным ускорителем поиска — его можно включить
(`integrations.khoj.enabled: true` в `config/system.local.json`) и запускать
как раньше; его отсутствие не блокирует ядро. Bridge нужен только клиенту,
который его использует.

## Ежедневные операции и диагностика

```powershell
node scripts/memory/sync.js --status
node scripts/memory/queue-status.js
node scripts/memory/indexer.js --status
node scripts/memory/doctor.js --json
docker compose -f services/activepieces/docker-compose.yml logs --tail=100 app worker
```

При отказе delivery очередь остаётся pending/failed; `queue-status.js
--redeliver failed` повторяет её. При отказе Khoj persisted-запись сохраняется,
а indexer показывает failed; после восстановления используйте `--requeue-failed`
и `--run`. Не запускайте бесконечные shell-циклы.

`queue-status.js` печатает `corrupt_count` по очереди и обоим журналам
(`corrupt.writer`, `corrupt.indexer`) и флаг `torn_tail`. Счётчик снимается
до чтения, поэтому он показывает состояние на момент запуска. Явный ремонт:

```powershell
node scripts/memory/queue-status.js --quarantine
```

Команда перечисляет созданные sidecar-`*.corrupt-tail-*`; повреждение в середине
журнала она не чинит, а сообщает в `quarantine.<журнал>.error` и оставляет файл
без изменений — такой журнал разбирается вручную.

## Повторная доставка и планировщик

Один проход (`node scripts/memory/queue-worker.js`) обрабатывает очередь один раз:
событие, оставшееся `pending` из-за недоступного получателя, без нового запуска не
доставляется. Простои закрывает ограниченный `watch`:

```powershell
node scripts/memory/queue-worker.js --watch --max-idle-ms 600000
```

`watch` ожидает `next_attempt_at` ближайшего события, повторяет попытки по backoff
очереди, а события с исчерпанными попытками оживляет не чаще одного раза в
минуту (`--no-revive` отключает оживление и завершает работу терминальным
статусом). Работа прекращается сама: `status: idle` — недоставленных событий нет,
`deadline` — истекло окно `--max-idle-ms` (по умолчанию 10 минут), `failed` —
терминальный отказ при `--no-revive`. Второй экземпляр worker возвращает
`{"status":"busy"}` и не делит очередь с первым. Бессрочный фоновый сервис и
глобальный оркестратор не предполагаются: простои длиннее окна закрывает
повторный запуск `--watch` (например, из планировщика задач), а не новый демон.

post-commit hook сам запускает `--watch --no-revive --max-idle-ms 120000` после
постановки события в очередь — этого достаточно, чтобы пережить перезапуск
сервиса без нового commit.

## Откат

Для кода и переносимых конфигов используйте обычный `git revert <commit>` на
проверенной ветке, затем тесты. Не используйте `reset --hard`, force push или
удаление `.local/`. Для сервиса сначала остановите compose, верните явно
закреплённый image tag из release notes, затем `pull`, `up -d` и health.

## Backup

Резервируйте на защищённый диск/менеджер секретов с датой, не в репозиторий:

- `.claude/memory/`, `config/system.example.json` и flow blueprint — Git;
- `config/system.local.json`, `.local/` (queue/writer/indexer logs) — отдельная
  локальная копия;
- Activepieces DB/flow — экспорт из UI и named volume `activepieces-postgres`
  по Docker procedure;
- `.env` и bridge/AI/Khoj keys — только отдельное encrypted secret store,
  восстанавливать вручную по именам переменных.

Предварительно проверьте размер и список файлов, создайте архив в явно
выбранной папке вне workspace и зафиксируйте checksum. Не архивируйте реальные
ключи вместе с Git backup.

## Restore

1. Клонируйте репозиторий, выполните `node scripts/memory/bootstrap.js` и
   заполните local config/secrets вручную.
2. Восстановите `.local/` и Activepieces export/volume только в тот же явно
   выбранный профиль, проверьте ownership и отсутствие ключей в log.
3. Запустите bridge → Khoj → Activepieces; восстановите flow и connection в UI.
4. Перестройте производный Khoj index из `.claude/memory`, не восстанавливайте
   его как источник истины. Проверьте поиск, writer idempotency и test event.
5. Выполните doctor и evidence report, затем `sync`/`push` в согласованных границах без
   нового вопроса; вне них — по указанию пользователя.

Проверка на отдельной копии: используйте [second-pc.md](second-pc.md),
временный clone и репрезентативный backup памяти/flow blueprint/queue.
