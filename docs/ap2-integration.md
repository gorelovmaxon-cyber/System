# Интеграция ap2 (Autopilot v2.1.0) в System2

Версия: 2026-11-09. Источник: `nick-vels/skills@v2.1.0` (MIT).
Установлено как `ap2` — имя не конфликтует с нашим `/autopilot`.

## Что есть в ap2, чего нет в нашем /autopilot

| Возможность | ap2 | наш autopilot |
|---|---|---|
| Живой дашборд (HTML, таймеры, цвет состояния) | ✅ `dashboard.html` | ❌ |
| Манифест требований R01… с гейтами G1–G4 | ✅ `manifest.md` | есть в workflow, но не в коде |
| Фазовая загрузка: один файл на фазу | ✅ читает только текущую фазу | ❌ 360 строк всегда |
| Слепая приёмка из чистого клона | ✅ G4 | ❌ |
| ap.py — учёт прогона, коммиты, статусы | ✅ | ❌ |
| Роли планировщик / приёмщик как правило | ❌ | ✅ |
| Память (decision journal, supersedes) | ❌ | ✅ |
| Переносимость (Git, second PC, restore) | ❌ | ✅ |
| Проектный scope (чужой HANDOFF не задаёт этап) | ❌ | ✅ |
| Маршрутизация по домену (сайты, ОК, обращения) | ❌ | ✅ |

Вывод: ap2 — сильный движок исполнения одного проекта. System2 — контракт ролей,
памяти и переносимости. Они не дублируют, а дополняют друг друга.

## Как это работает вместе

```
пользователь: «ставь под ключ: телеграм-бот для заявок»
→ /start → рекомендует /ap2
→ пользователь: /ap2 semi <задача>

  ap2 берёт управление:
  Фаза 0: открывает dashboard.html
  Фаза 1: brief.md + manifest.md (R01, R02, …)
  Фаза 2: grill — вопросы ровно по пробелам брифа
  Фаза 3: spec.md
  Фаза 4: plan — тикеты + гейт G3 (трасса манифест ↔ тикеты)
  Фаза 5: build — подагенты по тикетам
  Фаза 6: review — код-ревью
  Фаза 8: blind acceptance G4 — из чистого клона, без spec.md

→ System2: plannerская роль принимает отчёт ap2
→ Decision journal: ключевые решения → save.js
→ HANDOFF обновляется на границе задачи
```

Наш контракт ролей остаётся внешним: пользователь выбирает планировщика и
приёмщика, ap2 — движок исполнения внутри их задания.

## Дашборд

ap2 сам открывает `dashboard.html` при запуске. Файл лежит в `.autopilot/`.
Структура сигналов:

| Цвет шапки | Состояние |
|---|---|
| Синий | идёт работа |
| Оранжевый | ждём ответа пользователя |
| Зелёный | сдано |
| Бирюзовый | ревью |
| Фиолетовый | ремонт тикета |
| Красный | упало |

Содержимое дашборда (обновляется после каждого `ap.py` события):
- Этап текущей сборки и таймер
- Каждое требование из брифа — строками с цветными полосами
- Тикеты: волны, статусы, коммиты
- Ваши слова дословно (из brief.md), не пересказ

Дашборд не нужно искать и запускать вручную — ap2 открывает его сам.
Если сервер упал после сна: `python3 .autopilot/ap.py` без аргументов —
сервер поднимается на том же порту.

## Когда использовать /ap2

**Да:**
- «собери под ключ», «просто сделай», «мне нужен готовый результат»
- задача — один проект с брифом: бот, сайт, фича, интеграция
- важно видеть покрытие требований в реальном времени
- нужна слепая приёмка из чистого клона

**Нет:**
- совместное написание кода строку за строкой → обычный чат
- одна правка одного файла → прямое поручение исполнителю
- задача туманная, больше одного проекта → `/wayfinder` сначала
- операционные карты без кода → `/ok <задача>`

## Режимы

| Режим | Брифинг | Спецификация | Тикеты |
|---|---|---|---|
| `full` | авто (самобрифинг) | авто | авто |
| `semi` | только пробелы | авто | авто |
| `interview` | все развилки | авто | авто |
| `manual` | все развилки | показать → ждать «ок» | обсудить → ждать «ок» |

По умолчанию: `semi` — задаёт только необходимые вопросы.

Глубина: `strict` (только бриф), обычная (по умолчанию), `deep`
(детально разрабатывает углы брифа, не расширяет его).

## Манифест и гейты

Четыре гейта защищают бриф от потери требований:

| Гейт | После | Условие |
|---|---|---|
| G1 | Брифинга | у каждого требования статус, нет `open` без причины |
| G2 | Спецификации | 0 открытых; независимый читатель не нашёл пропусков |
| G3 | Плана | каждое `in-spec` требование в тикете, каждый тикет → требование |
| G4 | Приёмки | слепая проверка из клона, без spec.md |

G2 и G4 — одна проверка на двух концах: «что пообещали» и «что сделали».
Провал гейта отправляет фазу на доработку.

## Файлы ap2 в проекте

После запуска `/ap2` в проекте создаётся:

```
.autopilot/
├── YYYY-MM-DD-slug--wip/
│   ├── YYYY-MM-DD-brief.md   бриф дословно (с редакцией секретов)
│   ├── manifest.md           R01, R02, … со статусами
│   ├── spec.md               спецификация
│   ├── interfaces.md         границы и правила проекта
│   └── tickets/NN-slug.md
├── state.js                  состояние прогона
├── ap.py                     учёт событий
└── dashboard.html            живой вид
```

`.autopilot/` коммитится — это запись того, что обещали и сделали.

## Обновление ap2

При выходе новой версии:
```bash
cd /tmp && git clone --depth 1 --branch vX.Y.Z https://github.com/nick-vels/skills ap2-new
cp -r ap2-new/skills/autopilot/. E:/SystemTheBest/System/.claude/skills/ap2/
```
Затем поправить `version` в `ap2/SKILL.md` и прогнать `npm run check`.

## Ограничения

- Python 3 обязателен для `ap.py` и дашборда. Без Python дашборд не работает,
  но прогон продолжается: статусы манифеста ведутся вручную, гейт G3 — самостоятельно.
- ap2 не пишет в нашу память (decision journal). Ключевые решения прогона
  фиксируются вручную через `save.js` по итогам сессии.
- Два `/ap2` в одной директории одновременно не запускать:
  `state.js` один на директорию.
