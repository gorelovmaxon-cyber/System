# Маршрут: сайты

Для лендингов и клиентских сайтов. Рекомендация start и явный выбор команды описаны в
[едином workflow](../system-workflow.md#один-start-для-новой-задачи-сайта).
Сначала общее ядро (`CLAUDE.md` и HANDOFF),
retrieval — только по условию из
[system-workflow.md](../system-workflow.md#контекст-и-retrieval).
Start сопоставляет задачу с проектом, сохраняет назначенную роль и этап,
рекомендует команду и завершает ответ без брифа, spec или генерации. Чужой HANDOFF
не задаёт этап нового сайта; клиентские решения не пишутся в чужой scope.
После явного выбора пользователем команды новый сайт и переработка идут через
[site-build](../../.claude/skills/site-build/SKILL.md) к
[autopilot](../../.claude/skills/autopilot/SKILL.md) в выбранном режиме.
Site-build добавляет требования сайтов к фазам autopilot без второго процесса
и отдельного запуска каждой внутренней фазы. Далее — действия выбранного маршрута,
а не продолжение start: краткий бриф о цели, аудитории, контенте, формах и аналитике.
[Стандарт сайтов](../standards/site-creation.md) читается напрямую независимо от Khoj.
Продолжение использует сохранённый этап, баг/мелкая правка/готовые тикеты — короткий
маршрут с применимыми правилами. Инструкции сайта не распространяются на другие домены.

1. До spec показать подходящий подтверждённый опыт с источниками, затем
   согласовать структуру, контент и критерии. Если опыта нет, сообщить это явно.
2. Подготовить локальные brief, spec и тикеты с применимыми ID стандарта,
   визуальным направлением, дизайн-системой, адаптивной сеткой, планом анимаций,
   картой контента/ассетов и QA. Эти решения планируются до подробной вёрстки;
   существующие документы дополняются без дублирования. В планирующей роли или
   планирующем запуске systemqwen передать разрешённый блок выбранному исполнителю и остановиться до
   реализации. В разрешённом полном цикле продолжать по autopilot и общему
   контракту ролей, без самоназначения исполнителем и автоматического открытия чатов.
   Макеты, ImageGen/Figma и конечные ассеты — реализация отдельного исполнителя;
   планировщику доступно текстовое описание композиции и требований.
3. Выполнить визуальную проверку в браузере; Figma MCP SC-14 использовать
   только при наличии макета и доступа.
4. Проверить имеющиеся формы и требуемую аналитику; применимые требования
   доступности (клавиатура, контраст, сенсорный ввод, reduced motion) действуют
   для созданных элементов без добавления ненужных функций.
5. Зафиксировать evidence по ID: проверено / не выполнено / неприменимо /
   не проверено. Обновить HANDOFF с ролью, режимом, артефактами и следующим шагом.

Публикация, домен, реклама и платная аналитика не запускаются автоматически.
Рекомендация по прошлому сайту допускается только из записи со статусом
`confirmed`, проверенным `source` и разрешённым `scope: user` или текущим проектом.
Если `date` в записи отсутствует, дату не выводить по догадке. Результат
`search.js` с `ok:false` — локальный fallback, а не успех Khoj. Поле
`encoding_warning: U+FFFD` означает повреждение текста записи. Запись с `U+FFFD`,
устаревшая или без сверяемого источника не подтверждает совет. Не читать чужой
project scope и не переносить клиентские требования/секреты в общий урок.
