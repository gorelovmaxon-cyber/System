# Единый рабочий процесс System2

Этот документ — источник истины для ролей, фаз, остановок, статусов и приёмки.

## Роли

1. **Планировщик** — обычно Opus или выбранная пользователем модель. Проводит grill,
   формирует spec и план, фиксирует архитектурные решения и принимает результат.
   Реализацию не пишет.
2. **Автор тикетов** — в текущем процессе Sonnet. Разбивает согласованный spec на
   проверяемые тикеты по [TICKET_TEMPLATE.md](../TICKET_TEMPLATE.md), с зависимостями,
   границами и командами проверки.
3. **Исполнитель** — GPT Luna через VS Code/Qwen Code. Реализует один тикет строго в
   заданных границах, проверяет и коммитит результат.
4. **Приёмщик** — планировщик или независимый проверяющий. Сверяет diff, проверки,
   evidence и исходные требования; только он переводит тикет в `done`.
5. **Пользователь** — оркестратор, который проходит гейты и передаёт тикеты исполнителю.

Модели — настраиваемая реализация ролей. Нельзя выводить роль из имени файла или
предполагать, что автор тикетов одновременно является исполнителем.

## Фазы и гейты

- **Планирование:** grill → spec → план. Остановка до начала нарезки.
- **Нарезка:** автор тикетов публикует тикеты в порядке зависимостей. Остановка до
  исполнения.
- **Исполнение:** исполнитель берёт один тикет, делает scoped-коммит и переводит его в
  `awaiting-review`.
- **Приёмка:** приёмщик проверяет фактический diff и команды. Успех переводит тикет в
  `done` и открывает следующий; замечания возвращают тикет на доработку.
- **Финал:** после всех тикетов выполняются сквозные проверки, резервирование и
  evidence-отчёт. Результат готов только если он проверен и запущен, а не только написан.

Правило: **один тикет = один коммит = одна остановка на приёмку**. Выполнение уже
согласованного набора не требует нового разрешения перед каждым тикетом, но каждый
тикет всё равно останавливается на `awaiting-review`.

## Контракт тикета

Тикет описывает пользовательское поведение, границы, зависимости, затрагиваемые
файлы/ресурсы, проверки и критерии приёмки. Полная реализация в тексте тикета не
обязательна. Короткий пример допустим только для снятия неоднозначности. Фиксированное
число строк или тикетов не является критерием качества.

Статусы:

`planned` → `ready-for-agent` → `in-progress` → `awaiting-review` → `done`

Если результат нельзя проверить из-за внешней зависимости, используется
`awaiting-validation` с причиной; если продолжение невозможно без внешнего решения —
`blocked` с причиной.

## Коммиты и синхронизация

Коммит должен быть scoped и содержать ID тикета. Перед коммитом проверь статус и не
включай чужие черновики. `push` выполняется после приёмки/проверки, по указанию
пользователя или через согласованный механизм SC-11. Force-push, автоматический
фоновой push и destructive reset запрещены. Ошибка синхронизации должна быть видна
пользователю и не маскируется как успешная доставка.

## Память, секреты и evidence

Состояния `persisted`, `synced` и `indexed` различаются. Секреты не попадают в
Git, отчёты или поисковый индекс; локальные защищённые настройки документируются только
по имени и наличию. Каждое внешнее утверждение о версии, API или доступности содержит
дату и официальный источник. Evidence включает команду, фактический результат и
ограничения проверки.
