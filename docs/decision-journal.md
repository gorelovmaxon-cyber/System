# Журнал решений проекта

Это проектный вход для разбора опыта. Файлы `<PROJECT_ROOT>/.system2/decision-journal/*.json` входят в Git-пакет **самого проекта**. Каноническая память остаётся только в System2 `.claude/memory`; поиск выполняется через `search.js`. Журнал не содержит полного чата, машинных путей, секретов, ключей, клиентских персональных данных или длинных копий документов.

## Уровень А — во время разговора

После каждого содержательного обращения, до финального ответа, проверь: появилось ли прямое решение/исправление пользователя, существенный открытый вопрос, проверенный результат или полезное наблюдение агента. Если нет — no-op. Для нового элемента вызови из корня System2:

```text
node scripts/memory/decision-journal.js capture --project-root <PROJECT_ROOT> --type decision --summary "Краткое решение" --source "беседа YYYY-MM-DD, пересказ решения" --verification confirmed
```

Типы: `decision`, `correction`, `question`, `fact`, `observation`. Проверка: `confirmed`, `observation`, `open`. Для исправления добавь `--supersedes <id>`; прежний файл сохраняется, а текущим значением считается исправление после проверки цепочки. Повтор тех же данных вернёт `created: false`. Если источник не даёт permalink, укажи беседу, дату и честный пересказ. Не придумывай message ID, точную цитату или SHA. Запись с U+FFFD сверяй с первоисточником; скрипт не принимает её как confirmed. До фиксации конфликта два несовместимых варианта остаются pending. Скрипт отклоняет распространённые форматы ключей, но агент обязан сам исключить остальные чувствительные данные.

Открытые вопросы остаются здесь и в HANDOFF. `observation` не становится `confirmed` по факту записи. Прямое решение не требует второго вопроса «сохранить?»; предположение о предпочтении требует подтверждения.

## Уровень Б — граница задачи

На завершении задачи, передаче, смене проекта или по запросу пользователя открой `pending` текущего проекта. Отбери подтверждённые записи, проверь источник, конфликты, дубли в памяти и scope. Прямое устойчивое предпочтение пользователя → `user-profile` с подходящим scope; факты, тарифы и решения одного проекта → память его `project_id`; проверенный переносимый приём → общая память только при доказанной применимости. Наблюдение остаётся `observation`; вопрос остаётся pending до ответа.

Для каждой отобранной записи используй **штатный** `save.js` с устойчивым ID `journal_<project_id>_<journal_id>` и тем же payload при повторе. После результата `persisted` проверь `search.js --project <project_id>` и источник; поиск может быть недоступен или не обновлён. Затем `mark --project-root <PROJECT_ROOT> --id <journal_id>`: команда проверит writer-log и запишет `memory_event_id` и файлы памяти. Если процесс прервался после writer, повтори тот же `save.js` с тем же payload/event_id и `mark`; вторую запись writer не создаст. Не помечай `persisted` при конфликте writer. Изменённую формулировку после подтверждённой записи оформляй как correction с `supersedes`, не меняй payload старого event_id.

```text
node scripts/memory/decision-journal.js pending --project-root <PROJECT_ROOT>
node scripts/memory/save.js --category decisions --statement "..." --evidence "..." --source "..." --scope <project_id> --status confirmed --event-id journal_<project_id>_<journal_id>
node scripts/memory/search.js --query "..." --project <project_id>
node scripts/memory/decision-journal.js mark --project-root <PROJECT_ROOT> --id <journal_id>
```

`state: persisted` означает локальную запись памяти; публикация двух scoped-коммитов проекта и System даёт `synced` только после проверки remote. `indexed` подтверждается отдельно через поиск/состояние индекса. Ошибка Git или Khoj не удаляет локальные файлы и не означает успех синхронизации или индексации. Публиковать пакет на границе задачи, а не после каждой реплики. В HANDOFF укажи непросмотренные ID, event_id уже перенесённых записей и следующий шаг. При старте читай HANDOFF и `pending`, не весь архив.

## Явное закрытие без переноса в память

`pending` можно закрыть отдельно от writer:

```text
node scripts/memory/decision-journal.js close --project-root <PROJECT_ROOT> --id <id> --disposition resolved --reason "Ответ получен" --evidence "Проверяемое описание или ссылка на ответ"
node scripts/memory/decision-journal.js close --project-root <PROJECT_ROOT> --id <id> --disposition dismissed --reason "Предположение отклонено" --evidence "Основание решения"
node scripts/memory/decision-journal.js close --project-root <PROJECT_ROOT> --id <id> --disposition superseded --correction-id <correction_id> --reason "Заменено поправкой" --evidence "Источник поправки"
```

Закрытие сохраняет исходные summary/source/verification и задаёт state `closed`,
closure (disposition/reason/evidence и correction_id при замене), closed_at.
`pending` больше не выводит эту запись; память не создаётся и mark явно отказывает.
Persisted нельзя понизить через close. Точный повтор идемпотентен, иное закрытие —
конфликт. Для superseded нужна существующая correction того же проекта с supersedes
на закрываемый ID; capture correction сам старую запись не закрывает.
Причина/evidence должны быть непустыми и проверяемыми агентом; CLI не доказывает
истинность текста и не повышает observation/open до confirmed.

Capture/mark/close сериализуются штатной локальной блокировкой каталога журнала;
JSON сначала полностью пишется и fsync-ится во временный файл, затем заменяется
rename под владением. Обрыв до замены сохраняет прежний JSON, после — новое состояние.
Сиротский tmp не является записью и не выводится pending. Атомарность двух файлов не заявляется.

Идентичность capture обратно совместима: сначала проверяется прежний ID от summary
в нижнем регистре. Для точного summary проверяются все прежние payload-поля; смена
source/verification конфликтует. Только при коллизии summary из-за регистра выбирается
детерминированный ID отдельного namespace `journal-case-v1` с исходным регистром.
Повтор проверяет legacy-точную запись первым делом, затем отдельный ID. Старые ID,
payload и ссылки corrections не переименовываются. Различные регистрозависимые строки
не объединяются; конкурирующие создания используют ту же блокировку.

## Предел автоматизации

В целевом чате GPT с файловыми инструментами доступен контракт в инструкциях и вызываемый CLI. Отдельный подтверждённый hook перед **каждым** финальным ответом для этого интерфейса не установлен. Поэтому нельзя обещать выполнение после каждой реплики без действий агента, фоновое чтение других чатов или спасение сообщения до фактической записи. Claude hooks не доказывают поведение чата GPT. При новой сессии восстановление проверяется чтением опубликованных файлов; сохранённое локально до push не доступно другому ПК.
