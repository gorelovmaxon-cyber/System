# 2026-08-17 — SystemQwen Architecture

**Дата:** 2026-08-17  
**Контекст:** D:\System2 — текущая система разработки  
**Источник:** Анализ проекта + документация

## Решение

**Использовать гибридную архитектуру Opus + Qwen с явными остановками между фазами** для экономии токенов (5-7×) при сохранении качества и полного контроля.

## Why

### Проблема
- Чистый Opus: высокое качество, но ~$2-3 на фичу
- Чистый Sonnet: дешевле, но качество planning/review ниже
- Autopilot (Opus + Sonnet субагенты): экономичнее, но нет полного контроля между тикетами

### Почему SystemQwen решает это
1. **Экономия токенов:** Opus только для thinking (20%), Qwen для execution (80%)
2. **Полный контроль:** 🛑 STOP после каждой фазы (grill, spec, tickets, каждый тикет, review)
3. **Качество:** Opus создаёт детальные алгоритмы → Qwen следует → Opus проверяет
4. **VS Code integration:** Qwen видит весь проект локально через расширение

### Экономика
- Opus: ~20k tokens (~$0.30)
- Qwen: ~120k tokens (~$0.15) 
- Opus review: ~15k tokens (~$0.23)
- **Итого: ~$0.68 vs ~$2.50 чистый Opus**

## How to apply

### Three-Phase Workflow

**Phase 1: Planning (Opus in Claude Code)**
1. Получает задачу через /start или /systemqwen
2. Делает grill → spec → tickets (детальные алгоритмы)
3. Сохраняет тикеты в .scratch/[project]/issues/
4. 🛑 СТОП: "Тикеты готовы: T1, T2, T3. Передавай T1 в Qwen."

**Phase 2: Implementation (Qwen via VS Code)**
1. Пользователь открывает тикет T1 и даёт его Qwen через чат VS Code
2. Qwen видит весь проект локально (через расширение)
3. Следует алгоритму из тикета строго
4. Пишет код, запускает тесты, делает коммит
5. 🛑 СТОП: "T1 готов: коммит [hash], тесты зелёные"

**Phase 3: Review (Opus in Claude Code)**
1. Пользователь передаёт результат от Qwen обратно Opus
2. Opus проверяет: git diff, тесты, соответствие тикету
3. 🛑 СТОП: "✅ T1 принят, передавай T2 в Qwen" или "⚠️ Нужна доработка: [замечания]"

**Цикл 2-3 повторяется для каждого тикета до конца.**

### Ключевые правила

**Opus (мозг):**
- Grill, Spec, Tickets — создаёт детальные тикеты с алгоритмами
- Review — проверяет результат работы Qwen
- Останавливается: после тикетов, после каждой проверки

**Qwen (руки):**
- Читает тикет от Opus
- Пишет код по алгоритму строго
- Тестирует, коммитит
- Останавливается: после каждого тикета

**Пользователь (оркестратор):**
- Запускает /start [задача]
- Передаёт тикеты между Opus ↔ Qwen
- Контролирует процесс на каждом шаге

### Главное правило

**Один тикет = один коммит = одна остановка.**

- Opus не пишет код сам (только примеры в тикетах)
- Qwen не додумывает за тикет (следует алгоритму строго)
- Пользователь контролирует каждый шаг (явные остановки)

## Альтернативы рассмотренные

### Отвергнуто: Чистый Opus
- ✅ Высокое качество
- ❌ Дорого (~$2-3 на фичу)
- ❌ Не окупается для bulk работы

### Отвергнуто: Autopilot (Opus + Sonnet субагенты) без явных остановок
- ✅ Экономичнее чистого Opus
- ❌ Нет контроля между тикетами
- ❌ Sonnet может отклониться от алгоритма

### Выбрано: SystemQwen (Opus + Qwen + explicit stops)
- ✅ Экономия 5-7×
- ✅ Полный контроль (явные остановки)
- ✅ Качество как у Opus (детальные алгоритмы + review)
- ✅ VS Code integration (Qwen видит проект локально)

## Применимость

✅ **Использовать SystemQwen когда:**
- Задача от 3+ тикетов
- Нужна экономия токенов
- Важен контроль на каждом шаге
- Работа в VS Code

✅ **Не использовать когда:**
- Однострочная правка (делать сразу)
- Нужен чистый research без реализации
- Работа НЕ в VS Code (тогда Autopilot с Sonnet)
