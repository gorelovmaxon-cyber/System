# systemqwen — режим с одним исполнителем

Единый контракт: [docs/system-workflow.md](../../../docs/system-workflow.md).

Поток:

1. Выбранный пользователем планировщик уточняет результат, формирует достаточный план и тикеты по
   [TICKET_TEMPLATE.md](../../../TICKET_TEMPLATE.md). Отдельный обязательный автор
   тикетов не нужен. Код реализации в этой роли не пишет.
2. Пользователь передаёт исполнителю разрешённый блок связанных тикетов: файл задачи,
   HANDOFF и отчёт предшественника. Автоматического runner'а нет — чат открывает
   пользователь.
3. Один выбранный пользователем исполнитель выполняет связанные тикеты последовательно. На каждый
   тикет — отдельный scoped-коммит; уточнения в границах блока не требуют нового
   разрешения на каждый тикет.
4. Исполнитель фиксирует проверки и сообщает awaiting-review на границе блока.
   Независимые done/READY себе не ставит.
   На согласованном решении, завершении тикета/блока и передаче проверяет,
   появилось ли полезное знание; прямое подтверждение сохраняет через save.js
   с evidence/source/scope, затем проверяет search.js. Если знания нет — no-op.
   HANDOFF обновляется без повторного анализа того же события.
5. Выбранный пользователем независимый приёмщик проверяет фактический diff, evidence и требования законченного блока,
   дополнительные проверки выбирает по риску. Только он ставит done либо возвращает
   конкретную доработку. Собственную реализацию не принимает; модель может совпадать
   с моделью исполнителя при отдельной независимой проверке.

Сохранять контекст предпочтительно; новая сессия допустима при необходимости, но тогда
нужен краткий HANDOFF. Параллельные агенты — явное исключение для независимых задач с
обоснованным выигрышем времени и учётом расходов, не режим по умолчанию.

Не обещай экономию без измерений и не выдавай написанное за проверенное.

## Gotchas

- Имя модели не назначает роль: планировщика, исполнителя и приёмщика выбирает пользователь.
- Усилие выбирают по сложности, неопределённости и риску среди доступных настроек
  клиента. Запись `high` в задании не переключает настройку и не доказывает фактический режим.
- Повторная самооценка автора не заменяет независимую приёмку, даже если названа review.
