# start — маршрутизатор

Одна дверь на любую задачу. Твоя работа здесь — **выбрать маршрут и объяснить его**,
а не выполнить задачу. Работу делает тот скилл, в который ты уводишь.

## Шаг 1 — Пойми задачу

Прочитай, что просит пользователь. Если из формулировки не ясен **тип** работы
(собрать / починить / изучить / проверить) — задай **один** уточняющий вопрос и жди ответа.

Факты ищи сам: посмотри папку проекта, `git status`, существующие файлы. Не спрашивай
то, что можешь увидеть.

**Готово, когда:** тип задачи определён.

## Шаг 2 — Выбери маршрут

| Задача | Маршрут |
|---|---|
| Собрать что-то новое под ключ: приложение, сайт, бот, фича, скрипт | `/autopilot` |
| **Собрать экономично через SystemQwen (Opus планирует → Qwen реализует → явные остановки)** | **`/systemqwen`** |
| Идея огромная и туманная, масштаб непонятен | `/wayfinder`, потом `/autopilot` |
| Пользователь хочет проектировать вместе, по шагам | `/grill-me` → `/to-spec` → `/to-tickets` → `/implement` |
| Уже есть спека или тикеты — просто реализовать | `/implement` |
| Что-то сломалось, тормозит, падает | `/diagnosing-bugs` |
| Проверить код: ветку, PR, текущие правки | `/code-review` |
| Изучить тему по первоисточникам | `/research` |
| Проверить идею или «лайфхак» по источникам, «есть ли доказательства» | `evidence-check` |
| Реализовать нарезанные тикеты сабагентами, вопрос «на какой модели гонять» | `subagent-pipeline` |
| Спланировать рефактор без правок | `/request-refactor-plan` |
| Найти улучшения архитектуры | `/improve-codebase-architecture` |
| Спроектировать интерфейс модуля / API | `/design-an-interface` |
| Закрепить термины предметной области, ADR | `/domain-modeling` |
| Прожарить идею вопросами, без сборки | `/grill-me` |
| Записать удачное в скилл | `/skill-forge` |
| **Мелкая правка**: переименовать, опечатка, одна строка | **Никакой скилл — сделай сразу** |

Не нашёл строку под задачу — предложи `/ask-matt` (роутер Pocock по его скиллам).

**Готово, когда:** маршрут выбран.

## Шаг 3 — Объясни, предложи экономию, спроси добро

Покажи пользователю коротко:

- **Команда:** какую вызываем.
- **Почему:** одно-два предложения — что в задаче указывает на этот маршрут.
- **Что будет:** 1–3 строки простым языком, чего ждать (например: «задаст 5–8 вопросов, потом соберёт сам до готового результата»).
- **Модели и экономия:** одной-двумя строками — чем гнать задачу дешевле без потери качества (см. таблицу ниже).

### Разбор модели под ЭТУ задачу

Не цитируй общее правило — **разбери конкретную задачу**. Таблицы «реализация → Sonnet»
недостаточно: одна и та же по названию работа в разных задачах стоит разного.

**Разложи задачу на этапы** (столько, сколько реально есть) и к каждому применяй один тест:

> **Нужно ли на этом этапе заметить то, о чём не спросили?**
>
> - **Да** → дорогая модель. Решения, противоречия в требованиях, нестыковки с реальностью,
>   выбор архитектуры, приёмка чужой работы, синтез разнородного.
> - **Нет, решение уже принято, надо исполнить** → дешёвая. Код по готовой спеке, сбор,
>   парсинг, разметка, переименование, механическая правка.

Отдельно проверь два признака, которые переводят этап в дорогие независимо от типа работы:

- **Цена ошибки высокая или необратимая** (деньги, прод, удаление данных) — не экономь.
- **Повторная попытка после провала** — раз первая не прошла, это была не рутина.

### Второй тест: дешевле сделать самому или делегировать

Дешёвая модель ≠ дешевле в сумме. **Считай полную стоимость этапа, а не ставку за токен.**

У делегирования есть накладные, которых нет у работы в текущем контексте:
промпт-контракт → **холодный старт** (агент заново вычитывает то, что у тебя уже загружено)
→ резюме обратно → риск переделки, если контекста ему не хватило.

> **Объяснить агенту дороже, чем сделать самому? → делай сам, даже на дорогой модели.**

**Делегируй**, если верно хотя бы одно:
- Объём большой — накладные в нём тонут (перебор десятков файлов, обход сайта, разбор выгрузки).
- Сырьё дальше не нужно: пусть заливает свой контекст, а не твой. Изоляция сама по себе выигрыш.
- Работа независима и её можно вести параллельно с другой.

**Делай сам**, даже если работа «исполнительская»:
- Мелочь, а нужный контекст уже загружен — пересказ дороже исполнения.
- Задача завязана на обсуждённое в этой сессии: агент переписки не видит, придётся выгружать её в промпт.
- Цена ошибки высока — одна переделка съест всю экономию.

**Выдай раскладку по этапам**, а не общий совет:

```
Этап 1 — <что> → <модель>, <сам или сабагенту>, потому что <признак>
Этап 2 — <что> → <модель>, <сам или сабагенту>, потому что <признак>
...
Где экономим: <какие этапы уходят на дешёвую / сабагентам и почему это безопасно>
Где НЕ экономим: <этапы, на которых нельзя, и чем это грозит>
```

Дальше:

- Задача **целиком исполнительская** — скажи прямо: «Opus тут не нужен, переключись: `/model sonnet`».
- Задача **смешанная** — назови, что уходит сабагентам на дешёвой, а что остаётся тебе.
- Задача **целиком про решения** — так и скажи, экономию не предлагай, это будет вредный совет.

**Проверь себя.** Самый частый срыв — назвать этап дешёвым, а потом делать его самому на
дорогой модели. Особенно ресёрч: он ощущается размышлением, хотя это сбор. Утекло — признай вслух.

**Рычаги помимо выбора модели** — упоминай, когда относятся к делу:
- Тяжёлое чтение — сабагенту: вернёт выжимку, а не зальёт контекст сырьём.
- `/clear` между крупными этапами: чистый контекст дешевле и точнее раздутого.
- Проверка блоками на завершённом куске, а не после каждого шага.

**Готово, когда:** у каждого этапа названа модель И способ (сам / сабагенту) с обоснованием,
и отдельно сказано, где экономить нельзя.

Затем спроси: **«Запускаю?»** и жди явного ответа.

- Пользователь сказал «да» / «запускай» → Шаг 4.
- Предложил другой маршрут → бери его, не спорь.
- Задача оказалась мелкой → сделай сразу, без скилла.

**Готово, когда:** получено явное подтверждение или выбран другой маршрут.

## Шаг 4 — Запусти

Способ зависит от того, как скилл вызывается.

**Модель может вызвать сама** (`autopilot`, `systemqwen`, `research`, `diagnosing-bugs`, `code-review`,
`domain-modeling`, `design-an-interface`, `prototype`, `qa`, `tdd`, `skill-forge`,
`request-refactor-plan`) → вызови и веди по нему.

**Только пользователь руками** (`wayfinder`, `grill-me`, `to-spec`, `to-tickets`,
`implement`, `ask-matt`, `improve-codebase-architecture`, `triage`, `handoff`,
`setup-matt-pocock-skills`) → **напиши пользователю точную строку, которую надо
вставить**, например: «Вставь: `/wayfinder <задача>`». Сам вызвать не пытайся — не
получится.

Если пользователь говорит «просто сделай сам» — прочитай `SKILL.md` этого скилла
(`.claude/skills/<имя>/SKILL.md`) и веди строго по нему.

**Готово, когда:** целевой скилл ведёт работу — вызван тобой или вставлен пользователем.

## Gotchas

- **Не делай задачу сам на Шаге 1–3.** Роутер только выбирает и объясняет; вся работа — внутри целевого скилла.
- **Не гоняй мелочь через `/autopilot`.** Однострочная правка не нуждается в вопросах, спеке и тикетах — просто сделай.
- **Не вали пачку вопросов.** На маршрутизацию хватает одного уточняющего; полный расспрос — работа `grilling` внутри `/autopilot`.
- **Не переписывай шаги целевого скилла.** Запустил — идёшь по нему, а не по своей версии.
- **Половину скиллов Pocock модель вызвать НЕ может** (`disable-model-invocation: true`) — попытка даёт ошибку. Для них выдавай пользователю готовую строку для вставки. Поймано в поле на `/wayfinder`.
