# Написание тикетов для исполнителя

Используй [единый шаблон](../../../TICKET_TEMPLATE.md).
Сохранено прежнее имя скилла для совместимости существующих ссылок.

Планировщик фиксирует результат, архитектуру и требования и формирует тикеты.
Отдельный обязательный автор тикетов не нужен: разбиение на проверяемые результаты
выполняет планировщик или исполнитель в границах согласованного блока. Исполнитель
пишет код и может уточнять связанные тикеты внутри этого блока.

- Прочитай спецификацию и необходимые файлы; не выдавай предполагаемые API за проверенные.
- Для каждого тикета укажи требования, зависимости, точки изменения, контракты и сценарии приёмки.
- Используй ссылки на файлы. Новый файл явно помечай как новый; относительные ссылки рассчитывай от тикета.
- Полный код не требуется. Короткие примеры допустимы только для устранения неоднозначности.
- Не требуй произвольное число строк или фиксированное количество тикетов ценой качества.
- Задавай архитектурные ограничения, оставляя исполнителю выбор деталей реализации.
- Не запрещай чтение смежного кода и проверку ошибочных предположений.
- Разделяй «написано», «проверено», «запущено». Команды без фактического запуска не являются результатом.
- После нарезки проверь покрытие требований, порядок зависимостей, ссылки и возможность выполнить проверки.
- Не запускай реализацию, если запрос был только на подготовку тикетов.

Не обещай экономию токенов числом без замеров.
