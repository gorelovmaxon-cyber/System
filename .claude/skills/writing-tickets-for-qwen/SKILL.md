# Навык: Написание тикетов для Qwen (экономия токенов)

## Цель
Создавать тикеты, которые Qwen выполнит с минимальными затратами токенов. Qwen должен читать только указанные файлы и менять только конкретные места, а не искать по всему проекту.

## Главный принцип
**Opus тратит токены один раз (читает проект, понимает архитектуру) → создаёт детальные тикеты с точными указаниями → Qwen тратит мало токенов (читает только указанные файлы, вносит изменения).**

---

## Структура экономного тикета

```markdown
# TICKET-N: [Краткое название задачи]

## Файлы для изменения:
- `путь/к/файлу1.py`
- `путь/к/файлу2.py`
- `путь/к/файлу3.py`

## Смежные файлы (для понимания контекста, читать по необходимости):
- `путь/к/related.py` — зачем: понять как вызывается функция X
- `config.py` — зачем: узнать формат параметров

## Задачи:

### 1. `файл1.py`
**Где менять:** После строки 45, в методе `process_data()`

**Что делать:**
- Добавить проверку на пустой список
- Если список пустой — вернуть пустой результат
- Добавить логирование размера входных данных

**Пример:**
```python
def process_data(self, items):
    if not items:
        print("[WARN] Пустой список данных")
        return []
    
    print(f"Обработка {len(items)} элементов")
    # существующий код...
```

### 2. `файл2.py`
**Где менять:** Параметр `BATCH_SIZE` (строка 12)

**Что делать:**
- Изменить значение с 5 на 1
- Добавить комментарий: "Обрабатывать по одному элементу (исправление зависания)"

### 3. `файл3.py`
**Где менять:** В методе `call_api()`, при вызове requests.post

**Что делать:**
- Добавить параметр `timeout=60`
- Обернуть в try-except для обработки Timeout
- При ошибке повторить 3 раза с паузой

## Критерии приёмки:
- [ ] Проверка на пустой список работает
- [ ] BATCH_SIZE изменён на 1
- [ ] API не зависает (timeout 60s)
- [ ] Есть retry логика при ошибках

## ❌ Что НЕЛЬЗЯ делать (приводит к перерасходу токенов)

### 1. Общие формулировки без указания файлов
**Плохо:**
```markdown
## Задача
Исправить зависание при обработке данных
```

**Почему плохо:** Qwen будет читать весь проект, чтобы найти где происходит обработка.

**Хорошо:**
```markdown
## Файлы для изменения:
- `src/processor.py` — метод process_data()
- `config.py` — параметр BATCH_SIZE
```

---

### 2. Описание проблемы без решения
**Плохо:**
```markdown
## Проблема
Процесс зависает на этапе обработки. Возможно из-за:
1. Большого размера данных
2. Отсутствия таймаутов
3. Проблем с API
4. Rate limits

Найди причину и исправь.
```

**Почему плохо:** Qwen будет диагностировать проблему заново, читая множество файлов.

**Хорошо:**
```markdown
## Решение
В `processor.py`, метод `call_api()`:
- Добавить timeout=60
- Добавить retry логику (3 попытки)
```

---

### 3. Отсутствие конкретных мест для изменения
**Плохо:**
```markdown
Добавь проверку на ошибки в обработчике данных
```

**Почему плохо:** Qwen будет искать все обработчики в проекте.

**Хорошо:**
```markdown
В `src/handlers/data_handler.py`, метод `process()` (строка 45):
Добавить try-except перед вызовом `transform_data()`
```

---

### 4. Избыточный контекст и теория
**Плохо:**
```markdown
## Контекст
Наша система использует микросервисную архитектуру. Каждый сервис общается через REST API.
Процессор данных вызывает внешний API для обогащения данных. В последнее время наблюдаются
проблемы с производительностью...

[ещё 3 абзаца теории]

## Архитектура
[диаграмма на 50 строк]
```

**Почему плохо:** Qwen тратит токены на чтение теории, которая не нужна для изменения кода.

**Хорошо:**
```markdown
## Контекст
Метод `call_api()` вызывает внешний API без таймаута → система зависает.

## Решение
Добавить timeout=60 в requests.post()
```

## ✅ Правильный подход

### Формула экономного тикета:
1. **Список файлов** (точные пути) — Qwen читает ТОЛЬКО их
2. **Конкретное место** (строка, метод, секция) — Qwen не ищет по всему файлу
3. **Готовое решение** (что добавить, что изменить) — Qwen не придумывает заново
4. **Минимум теории** — только то, что нужно для понимания изменений

### Пример идеального тикета:

```markdown
# TICKET-003: Добавить timeout в API запросы

## Файлы для изменения:
- `src/api_client.py`

## Задача:
В методе `call_api()` (строка 67), добавить timeout=60 в requests.post:

**Было:**
```python
response = requests.post(url, json=payload)
```

**Стало:**
```python
response = requests.post(url, json=payload, timeout=60)
```

## Проверка:
```bash
python test_api_client.py
```
Ожидаемый результат: запрос прерывается через 60 секунд при зависании.
```

**Токены Qwen:**
- Прочитает: 1 файл (~500 токенов)
- Найдёт: строку 67 (~50 токенов)
- Изменит: 1 строку (~100 токенов)
- **Итого: ~650 токенов**

---

## Сравнение: плохой vs хороший тикет

| Плохой тикет | Хороший тикет |
|--------------|---------------|
| "Исправь зависание системы" | "В `api_client.py:67` добавь timeout=60" |
| Qwen читает 10+ файлов | Qwen читает 1 файл |
| Qwen ищет причину проблемы | Qwen сразу вносит изменение |
| ~40,000 токенов | ~650 токенов |
| **60x дороже** | **60x дешевле** |

## Контрольный список перед отправкой тикета Qwen

- [ ] Указаны точные пути к файлам для изменения
- [ ] Указаны конкретные места (строка / метод / секция)
- [ ] Описано ЧТО делать, а не "найди и исправь"
- [ ] Нет избыточной теории и контекста
- [ ] Есть пример кода (если изменение не тривиальное)
- [ ] Указана команда для проверки результата
- [ ] Минимум текста — максимум конкретики

---

## Когда можно давать менее детальный тикет

Qwen может сам найти нужные места в коде, если:
- Задача очень простая ("переименовать переменную X в Y")
- Изменение в одном месте ("добавить import в начало файла")
- Паттерн очевиден ("добавить комментарий к каждой функции")

Но даже в этих случаях **указывай файлы** — это всегда экономит токены.

## Итог

**Ваша работа как Opus:** потратить свои токены один раз на понимание проекта и создание детальных тикетов.

**Работа Qwen:** быстро и дёшево выполнить чёткие инструкции из тикета.

**Результат:** экономия ~60x токенов по сравнению с "высокоуровневыми" тикетами.
