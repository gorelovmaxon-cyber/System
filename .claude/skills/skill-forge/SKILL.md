# skill-forge

Цель: **день 30 работы со мной должен быть заметно лучше дня 1.** Скилл копит твои
edge-кейсы, голос и процесс — промпт нет. Каждая сессия делает следующую умнее.

## Когда ковать

- Инструкция/процесс/формат повторялся за сессию **2–3 раза** — кандидат в скилл.
- Ты правил результат руками — значит скилл упустил кейс, его надо дописать (gotcha).
- **Перед завершением задачи или сессии — ВСЕГДА спроси:** «что забрать в скилл навсегда, а что было разовой правкой?»

Разовое — не в скилл. В скилл — только повторяемое.

## Как ковать (3 слоя, не один промпт)

Скилл собирается по [`templates/SKILL.template.md`](templates/SKILL.template.md):

1. **Description** — точное «когда брать» с триггер-фразами (по нему идёт подхват, не по имени). Размыто = не подхватится.
2. **Instructions** — плейбук по шагам, у каждого шага проверяемый критерий «готово».
3. **Tools** — `tools/`: скрипты, шаблоны, примеры. Сюда не доходят 90% — но сила здесь. Детерминированную логику вынеси в скрипт (0 токенов на код, стабильно).

Реши **тип вызова:**
- **Авто (model-invoked)** — нужен, если модель/другой скилл должны дёргать его сами. Цена: description висит в контексте каждый ход.
- **Ручной (`disable-model-invocation: true`)** — 0 контекста, но ты сам помнишь, что он есть. Для потоков, которые запускаешь рукой.
Много ручных скиллов накопилось — заведи **роутер-скилл** (один авто-скилл, который называет остальные и когда их брать).

## Композиция, не монолит

Не строй гиганта «делает всё». **3–5 узких скиллов**, каждый делает ОДНО — баг находится сразу, улучшения не ломают соседей. Разросся — предложи разбить.

## Gotchas — обязательная секция

В конец нового скилла добавь секцию **Gotchas**: что пошло не так в этой сессии, что
пришлось чинить руками, чего НЕ делать. Это то, что не даст повторить ошибку.

**Канонический gotcha (из поля):** промпт-рецепт с захардкоженными «Шаг 1/2/3»
переопределил скилл — модель пошла по промпту и проскочила `масштаб`/`grill`. Урок:
скилл-процесс триггерится **тонким** промптом (триггер + объект), а порядок держится
в `SKILL.md`, не в промпте. Куёшь workflow-скилл — не требуй, чтобы пользователь
вставлял шаги руками.

## Golden-кейс (заземляет качество)

Каждый новый скилл несёт **1–3 golden-кейса** (вход → ожидаемый результат) в `examples/`.
Это дешёвый регресс-гейт: правишь скилл — сверяешь, что кейсы всё ещё проходят. Без
заземления на проверку самокоррекция врёт.

## Консолидация памяти (периодически)

Память копится → зарастает осадком. Раз в N сессий прогони «бедняцкий Dream»:

1. Прочитай накопленное (`DECISIONS.md`, gotchas, список скиллов).
2. **Дедуп** — слей повторяющееся; **новейшее побеждает** при конфликте.
3. Выкинь устаревшее и разовое; оставь только выжимку с провенансом.
4. Много маленьких сфокусированных файлов, не мало больших. `git commit` = точка отката.

**Готово, когда:** дублей и устаревшего не осталось, каждый факт с источником.

## Процесс

1. Просмотри сессию: что повторялось, что правилось руками, что объяснялось дважды.
2. Предложи конкретный скилл: имя, description (когда брать), шаги, что в `tools/`, секцию gotchas.
3. Пользователь принимает нужное, отклоняет лишнее. **Ты вносишь принятое** — создаёшь файлы скилла.
4. Проверь: description точный? tools заполнен, а не пустой? тип вызова верный? не монолит?

**Готово, когда:** скилл создан с непустым `tools/` (если применимо) и секцией gotchas, либо пользователь явно сказал «разовое, не оформляем».
