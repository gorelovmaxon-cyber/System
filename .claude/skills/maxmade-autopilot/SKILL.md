Пайплайн поверх System2. Все правила System2 остаются в силе — они передаются исполнителю через контекстный пакет, а не заменяются этим скиллом.

## Пайплайн

```
[Ты] → бриф
  ↓
[Планировщик: Opus 5.5] → вопросы (Grill) → Spec → тикеты → контекстный пакет
  ↓
⏸ СТОП — ты проверяешь и передаёшь в Codex
  ↓
[Astra в Codex] → корректирует план или запускает
  ↓
  Один сеанс на блок тикетов:
  [GPT 6.1] → реализует тикет → коммит → отчёт
  [Astra] → читает отчёт → CONTINUE / REWORK / ESCALATE
  [GPT 6.1] → следующий тикет (если CONTINUE)
  ↓
[Ты] → финальная приёмка блока
```

## Фаза 1 — Планировщик (Opus)

Планировщик читает обязательные файлы по контракту `/start`, затем:

1. Запускает `/start <задача>` для маршрутизации
2. **Читает правила домена по обязательному гейту ниже** — для сайта это `docs/routes/sites-workflow.md` и `docs/standards/site-creation.md`
3. Выполняет Grill (`/grilling`) — вопросы раундами, 5–8 вопросов, каждый с рекомендованным ответом. «ок» принимает все; не согласен с одним — «2 — другой ответ, остальное ок»
4. Пишет Spec (`/to-spec`) — без новых вопросов, открытые места становятся PLACEHOLDER
5. Делает тикеты (`/to-tickets`) — по объёму кода, не по типу продукта
6. Собирает контекстный пакет по шаблону `templates/executor-brief.md`

**Стоп:** планировщик заканчивает пакетом передачи. Реализацию не начинает.

## Фаза 2 — Передача в Codex

Ты передаёшь Astra контекстный пакет. Astra может:
- Скорректировать тикеты или порядок (не переписывая spec)
- Сразу запустить исполнение

Astra не делает реализацию сама — запускает GPT 6.1.

## Фаза 3 — Исполнение (один сеанс Codex на блок)

**Принцип одного сеанса:** Astra и GPT 6.1 работают в одном контексте внутри блока. GPT 6.1 видит предыдущие тикеты блока, связанный код, решения Astra. Разрыв сеанса только на:
- Границе блока (System2 правило)
- Контекст вырос за ~100K
- Смена модуля или домена

**Цикл тикета:**
```
GPT 6.1 читает тикет из контекстного пакета
  → реализует строго в границах тикета
  → коммит с ID тикета (формат: T03: краткое описание)
  → заполняет отчёт по шаблону templates/executor-report.md
  → передаёт Astra
```

**Gate-логика Astra (три варианта — только один):**

| Вердикт | Критерии | Действие |
|---|---|---|
| `CONTINUE` | Коммит есть, SHA указан, проверки пройдены, отчёт заполнен | Передать следующий тикет GPT 6.1 |
| `REWORK T[N]: <причина>` | Проверка не прошла, коммит не по тикету, граница нарушена | Вернуть тот же тикет GPT 6.1 с конкретным замечанием |
| `ESCALATE` | Тикет выходит за spec, нужны credentials/доступ, неясная архитектура | Остановить, выйти к тебе |

Astra не переписывает тикет при REWORK — только указывает что именно не так.

## Обязательный гейт: правила домена до тикетов

Перед составлением тикетов планировщик определяет домен задачи и **обязан** прочитать соответствующие канонические правила. Это гейт, а не справка: без прочтения тикеты не составляются.

| Домен | Обязательно прочитать | Когда |
|---|---|---|
| Сайт (лендинг, переработка, новый сайт) | `docs/routes/sites-workflow.md` + `docs/standards/site-creation.md` | до Grill, повторно перед тикетами |
| Операционные карты | `docs/standards/operational-cards.md` | до выполнения |
| Разработка (функция, баг, API) | `docs/routes/dev-workflow.md` | до тикетов |
| Маркетинг | `docs/routes/marketing-workflow.md` | до тикетов |

**Для домена «сайт» дополнительно обязательно:**
- Тикеты содержат конкретные ID правил стандарта и способы проверки
- В контекстный пакет (`templates/executor-brief.md`) включается блок правил сайтов, а не ссылка «см. стандарт»
- Мобильная версия входит в критерии приёмки, если тикет затрагивает UI
- Визуальная проверка — отдельное доказательство, не заменяется «сборка прошла»

**Если правило-файл недоступен:** остановиться, назвать недоступный файл и запросить доступ. Не составлять тикеты по памяти и не выдавать это за соблюдение стандарта.

Astra и GPT 6.1 не имеют прямого доступа к System2 — правила едут в контекстном пакете. Пакет без нужного блока правил считается неполным, и Astra возвращает его на доработку (`ESCALATE`), а не запускает исполнение.

## Команда `/start` в этом режиме

`/start` работает как обычно: читает контекст, выбирает маршрут, останавливается на рекомендации. После того как ты выбрал `maxmade-autopilot`:

1. `/start` рекомендует этот скилл
2. Планировщик читает `E:\SystemTheBest\System\.claude\skills\maxmade-autopilot\SKILL.md`
3. Выполняет Фазу 1 (Grill → Spec → тикеты → пакет)
4. Стоп

`/start` не запускает Grill сам — только рекомендует маршрут.

**Частые ошибки:**
- Планировщик начинает реализацию — нельзя, стоп после пакета
- Astra меняет spec вместо тикетов — spec заморожена после планировщика
- GPT 6.1 ставит себе done — нельзя, только Astra даёт CONTINUE
- Два тикета в одном коммите — нельзя, один тикет = один коммит
- Новый сеанс Codex на каждый тикет — нельзя, один сеанс на блок

## Когда НЕ использовать

- Мелкая правка (1–2 файла, понятная граница) → прямое поручение исполнителю
- Только вопросы или анализ → обычный чат
- Операционные карты без кода → `/ok <задача>`
- Задача туманная и больше одного проекта → `/wayfinder` сначала

## Gotchas

- Маршрут сайтов теперь этот: `start` рекомендует maxmade-autopilot, а `site-build`
  остаётся внутренней фазой правил. Не создавай второй процесс и не вызывай start обратно.
- Передача между чатами ручная: не обещай реализацию, заканчивая только документами.
- Планировщик не создаёт код, макеты и ассеты. «Эскиз» и «прототип» — тоже реализация.
