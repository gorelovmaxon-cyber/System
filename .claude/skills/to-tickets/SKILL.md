# to-tickets

Используй единый [TICKET_TEMPLATE.md](../../../TICKET_TEMPLATE.md). Тикеты готовит
тот, кто планирует: отдельная обязательная роль автора тикетов не нужна. Тот, кто
готовит тикеты, не реализует код и не подменяет приёмщика.

Для каждого тикета укажи:

- пользовательское поведение и границы результата;
- точные файлы/ресурсы, которые нужно изменить или прочитать;
- зависимости и порядок;
- контракты, ошибки, безопасность и критерии приёмки;
- команды фактической проверки и ожидаемый результат;
- ручные доступы или внешние условия, без значений секретов.

Точные пути обязательны, когда они делают тикет исполнимым. Полная реализация и
фиксированное число строк не обязательны; короткие примеры допустимы только для
устранения неоднозначности. Не выдавай устаревшие версии или API за проверенные.

Сохраняй тикеты как локальные файлы проекта в папке согласованной spec, если
внешний tracker отдельно не выбран. Публикуй в порядке зависимостей. Начально
`ready-for-agent` ставь только тикетам без незакрытых блокеров, остальные —
`planned`. После явного выбора планирующего маршрута подготовь пакет передачи
отдельному исполнителю и остановись до реализации. Сам `/start` заканчивается
рекомендацией, не подготовкой тикетов; выбранный затем autopilot не требует
ручного вызова каждого внутреннего навыка.

## Gotchas

- Требования берутся из `manifest.md` дословно (R01…), а не из пересказа в спецификации.
- У каждого тикета должно быть хотя бы одно требование. Тикет без требования — работа,
  которую никто не заказывал; удали или согласуй, а не помечай `ready-for-agent`.
- Тикетов больше, чем работы, — дефект нарезки. Задача на 2–3 контекста не режется на 8 тикетов.
