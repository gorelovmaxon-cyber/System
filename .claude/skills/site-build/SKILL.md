# site-build — создание сайта по стандарту

Специализированный вход после явного выбора пользователем site-build:
`site-build → autopilot`. Start только рекомендует эту команду и завершает ответ;
рекомендация не является её запуском. Повторять start перед прямым вызовом не нужно.
Это навык в `.claude/skills/`, а не shell-команда и не runner передачи между чатами.
Прямой вызов: `/site-build <задача>`; в чате с файловыми инструментами допустим
текст «Выполни site-build: <задача>». Доступность slash-интерфейса зависит от клиента.

## Вход и готовность

1. Найди каноническую System2 через действующую локальную привязку проекта.
   Прочитай инструкции и HANDOFF проекта, актуальное задание, pending решений
   текущего проекта и [маршрут сайтов](../../../docs/routes/sites-workflow.md).
   При прямом входе также прочитай общие CLAUDE/workflow System2.
2. Прочитай [стандарт сайтов](../../../docs/standards/site-creation.md) напрямую.
   Retrieval по [общему контракту](../../../docs/system-workflow.md#контекст-и-retrieval)
   дополняет его; отказ поиска не блокирует доступное планирование.
3. Определи сценарий, роль, выбранный режим и разрешённый объём по задаче и HANDOFF.
   Пользователь выбирает модели и роли. Не переключай их по имени команды.
   Проверь соответствие задачи проекту: HANDOFF другого продукта не задаёт этап
   нового клиентского сайта. При несовпадении сообщи его, не записывай клиентские
   решения в чужой scope и не регистрируй новый проект без явного выбора.

**Готово:** установлены проект, актуальные решения, сценарий и разрешённая граница.
Если корень неизвестен, уточни привязку; не угадывай путь и не создавай копию стандарта.

## Выбор сценария

| Вход | Действие |
|---|---|
| Новый сайт | Применить стандарт и продолжить autopilot с нужной начальной фазы |
| Существенная переработка | Изучить текущий сайт и сохраняемые решения; описать изменяемые части, продолжить autopilot |
| Продолжение | Открыть сохранённые brief/spec/тикеты/evidence и продолжить этап из HANDOFF |
| Готовые тикеты | Перейти к разрешённому исполнению/передаче, приложить применимые правила; не повторять grill |
| Мелкая локальная правка | Применить затронутые правила и короткий маршрут, без полного цикла |
| Ошибка или аудит | Соответствующая диагностика/проверка; создание сайта заново не запускать |
| Только предложения, «не внедряй» | Подготовить варианты; не переходить к реализации |

**Готово:** известные ответы использованы, неизвестное отделено от фактов; нет
повторного интервью или расширения задания. Объём определяется результатом, не числом файлов.

## Передача в autopilot

Прочитай [autopilot](../autopilot/SKILL.md) и выполняй его разрешённые фазы,
добавляя требования сайта. Передай ему задачу, проект, сценарий, роль, режим,
известные ответы, сохранённый этап, ссылки на стандарт и существующие артефакты.
Не копируй процесс autopilot и не вызывай `start` обратно.
Это дополнение требований сайтов к фазам autopilot, а не второй процесс или
повторное интервью. Пользователь не обязан отдельно запускать grill/spec/tickets.
Если клиент запрещает вложенный вызов навыка, следуй прочитанному контракту
напрямую; не объявляй текстовую ссылку фактически выполненной командой.

На фазах grill/spec/tickets обеспечь
[данные планирования и передачу правил](../../../docs/standards/site-creation.md#артефакты-планирования-и-передача-правил):
brief, spec, визуальное направление, дизайн-система, адаптивная сетка, план
анимаций, карта контента/ассетов, применимые ID, исключения, QA, тикеты и HANDOFF.
До spec показывай рекомендации с пометками «источник / новое предложение / неизвестно».
Для нового сайта используй запрос по теме и, если registry содержит прежний сайт,
один запрос по его ID/названию: общий технический урок может не попасть в тематический
поиск. Оба запроса используют `--project` текущего проекта; чужой scope не открывается.
Подтверждённые общие уроки допустимы из scope user с проверенным источником.
Решения по палитре/эффектам другого проекта не переносятся автоматически.
Используй существующие документы; если папки задач нет — `.scratch/<task-id>/`.

**Готово:** исполнителю понятно, что строить, на какой сетке, как ведут себя
компоненты и анимации, какие данные реальны и чем доказать результат.

## Режим и граница реализации

- В планирующем запуске (планировщик или планирование `--mode=systemqwen`) завершить план и пакет передачи,
  обновить HANDOFF и остановиться до реализации. Выбранного исполнителя запускает
  пользователь в другом чате. Не требовать ручного вызова каждого подготовительного навыка.
  Отдельно назначенный исполнитель продолжает переданный разрешённый блок;
  сохранённое обозначение systemqwen в HANDOFF не возвращает его к планированию.
- Разрешённый полный цикл идёт по autopilot и
  [ролям/полномочиям workflow](../../../docs/system-workflow.md#полномочия).
  Нужны явные границы исполнения, выбранная роль и доступный способ выполнения.
  Одно «создай сайт» не отменяет уже назначенную планирующую роль.
  Планировщик не создаёт визуальные макеты, ImageGen/Figma-результаты и конечные
  ассеты; текстовое описание композиции и требований допустимо. Ответ о формате
  результата не назначает исполнителя и не согласовывает композицию.
  Исполнитель может продолжить свой разрешённый блок; планировщик не становится
  исполнителем и не запускает чужой чат. Нет доступной передачи — сохранить пакет.
- Без установленного режима использовать текущую роль; если роль неизвестна,
  подготовить план и обозначить необходимость выбора исполнителя перед реализацией.
- Молчание не означает согласование spec или разрешение на внешний шаг.
  Уже разрешённая работа не требует повторного разрешения на каждый этап.
- Публикация, регистрация домена, платные сервисы и отправка реальных заявок
  определяются отдельными границами проекта; эта команда их не разрешает.

**Готово:** выполнены только разрешённые фазы, состояние честно отмечено.

## Проверка и продолжение

Перед реализацией и приёмкой прочитать стандарт и применимые требования тикета.
Сохранить evidence по ID: «проверено / не выполнено / неприменимо / не проверено».
Сборку, визуальную проверку и независимую приёмку не подменять друг другом.
Автор реализации не ставит себе независимый `done`.

Обновить HANDOFF: этап, режим/роль, решения и исключения, ссылки на артефакты,
проверки, ограничения, разрешённый блок и следующий шаг. Память — штатный writer,
только подтверждённые уроки и указатель на стандарт; вторую копию не сохранять.

**Готово:** следующий вход восстанавливает этап из файлов без старой переписки.

## Gotchas

- Остановка start после рекомендации обязательна. После явного выбора site-build
  действуют фазы autopilot и назначенная роль; не переносить остановку start на
  каждую внутреннюю фазу и не требовать повторного интервью.
- «Запускаю через 60 секунд» не заменяет согласованную spec или выбор исполнителя.
- Наличие навыка в System2 не регистрирует slash-команду во всех клиентских проектах.
  При недоступном интерфейсе дать текстовый вызов с доступом к каноническому файлу.
- Ссылки на стандарт без конкретных ID и проверок в тикетах не доказывают применение.
- Файл `writer-entries.md` может содержать разные scope. Найденная user-запись
  не разрешает чтение всего файла с чужими проектными записями: использовать
  разрешённую выдержку и её источник, а стандарт читать напрямую.

## Примеры входа

- «Создай сайт мастерской», планирующая роль: brief/spec с сеткой и дизайн-системой,
  применимые ID в тикетах, пакет передачи; до реализации остановиться.
- «Продолжи сайт», HANDOFF указывает разрешённый блок исполнителя: открыть spec и
  тикеты, выполнить блок без нового grill, сохранить evidence и передачу приёмщику.
- «Сделай кнопку круглее»: короткая правка в разрешённом объёме, проверка связанных
  кнопок/ширин; новый бриф и полный цикл не запускать.
