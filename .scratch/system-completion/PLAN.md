# План нарезки для Sonnet: SystemQwen v1

## Как использовать

Вход: [SPEC.md](SPEC.md), [единый шаблон](../../TICKET_TEMPLATE.md).
Автор тикетов: Sonnet, уже выбранный в workflow. Название доступного варианта
модели проверить в интерфейсе; этот план не предполагает доказанного превосходства
«Sonnet 5» над «GPT 5.6 Sol». При недоступности Sonnet тот же пакет подходит другому автору.

Планировщик подготовил архитектуру; Sonnet пишет тикеты; GPT Luna реализует;
планировщик/Opus проверяет результат. Автор тикетов не реализует заранее всю систему.

## Уже сделано перед нарезкой

SC-00: обновлены TICKET_TEMPLATE.md, ссылка templates/ticket-template.md,
инструкция writing-tickets-for-qwen и старый sonnet-ticket-plan.
Сохранены контекст, пути, ограничения, алгоритм, критерии и итоговый отчёт.
Добавлены статусы, требования, реальные сценарии проверки; убрана обязательность полного кода.
SC-00 не нарезать и не выполнять повторно; это изменение шаблона, не запуск системы.

Один тикет может содержать несколько тесно связанных файлов; не дробить по принципу
«создать файл», «написать функцию», «написать инструкцию».

## Содержание тикетов

### SC-01 — Единый workflow и предпосылки

Читать CLAUDE.md, OPUS.md, QWEN.md, README.md, start/autopilot/systemqwen,
subagent-pipeline/to-tickets и TICKET_TEMPLATE.md. Убрать противоречия ролей и
обязательность писать полный код при планировании. Сохранить остановку после подготовки
спецификации и после нарезки; исполнение целого согласованного набора не требует
повторного разрешения на каждый уже разрешённый тикет.
Проверить установленные Node, Git Bash по реальному пути, Docker/Compose, доступность
Khoj/Activepieces/Figma и AI connections без вывода ключей. Выбрать совместимые версии
по официальным источникам, зафиксировать конфигурацию и prerequisites.
Новые файлы: docs/system-workflow.md и .scratch/system-completion/ENVIRONMENT.md.
Приёмка: однозначные роли; список доступного и недостающего; прежние несовпадения
API/compose подтверждены или опровергнуты для выбранных релизов.

### SC-02 — Конфигурация памяти

Существующие: .claude/memory/MEMORY.md, memory/user-profile/coding-style.md,
auto-learn/profile-update. Новые: config/system.example.json, docs/memory-contract.md,
модуль разрешения путей в scripts/memory/. Единый system_root и стабильный project_id;
перемещение System2 не меняет идентичность проектов. Локальные привязки и secrets игнорируются Git.
Приёмка: запуск из другой рабочей папки находит тот же профиль; отсутствующий root выдаёт
понятную ошибку; две копии памяти не создаются. Существующие данные сохранены.
Перед изменениями — резервная копия текущего локального состояния (включая нужные
untracked/gitignored-файлы); секреты — отдельно и защищённо; git-история их не восстановит.

### SC-03 — Качество памяти

Ввести поля из SPEC, правила observation/confirmed/superseded и объединения дублей.
Проверить существующий профиль на смешение личных предпочтений, проектных решений и
неподтверждённых обещаний. Миграция сохраняет источники, исходный текст и возможность отката.
До правок — локальная резервная копия затронутых записей (часть может быть незакоммичена).
Довести facts по dev/kwork только по реально доступным источникам; отметить unknown для
недоступных проектов, не утверждать их аудит. Не собирать целиком чужие проекты без нужды.
Приёмка: прямое пожелание и выбор агента различаются; конфликт не теряет прежнюю запись.

### SC-04 — Установка Khoj

Довести docs/khoj-setup.md; разместить воспроизводимый конфиг в services/khoj/.
Выбрать поддерживаемый путь установки по SC-01, а не обязательно старый pip-сценарий.
Настроить авторизацию, разрешённые источники, persistent storage, индексацию и перезапуск.
Приёмка: живой health и поиск по настоящей записи; индекс сохраняется/восстанавливается
после перезапуска; исключённые секреты не индексируются. Команды и ответ приложены.

### SC-05 — Поиск в workflow

Создать адаптер в scripts/memory/, изменить только нужные фазы autopilot/start и
docs/khoj-integration.md. Бюджет контекста, ссылки, границы проектов, результаты без ответа,
timeout/401/невалидный ответ. Полезные выдержки, а не обязательное чтение всех top-3 файлов целиком.
Приёмка: 5 заранее заданных вопросов с ожидаемыми источниками, включая отсутствие ответа;
при остановленном Khoj задача продолжается с обязательными файлами и локальным индексом.

### SC-06 — Activepieces

Довести существующий compose из .scratch/activepieces, перенести канонический конфиг в
services/activepieces/ и обновить docs/activepieces-setup.md. Версии, число контейнеров,
переменные и health выбрать по SC-01; число «3» не важнее работоспособности.
Секреты с корректными форматами до первого запуска, локальная привязка портов, persistence,
рабочий execution worker. Подготовить AI connection и связность с host bridge.
Приёмка: UI доступен, тестовый flow выполняется и сохраняется после перезапуска.

### SC-07 — Capture и очередь

В scripts/memory/ реализовать команды приёма commit/session-summary по SPEC,
контракт JSON и очередь. SHA первого коммита, кавычки, UTF-8, пустой diff, размеры событий.
Резюме включает мотивы, corrections и next_action; не зависит от чтения браузерных чатов.
Приёмка: выключенный получатель не теряет событие; после восстановления оно доставляется;
ошибки видны, commit не зависит от скорости AI-запроса.

### SC-08 — Writer

Реализовать bridge API и единый путь ручной записи, allow-list категорий, аутентификацию,
идемпотентность и сериализацию. Не давать AI выполнять команды или выбирать произвольный путь.
Приёмка: повтор event_id, параллельные события, неверная категория, попытка выхода за root,
перезапуск после записи до ACK; ни потери старой памяти, ни повторного добавления.

### SC-09 — Flow

Создать flow export/config в services/activepieces/flows/ и связать с работающим bridge.
Обновить docs/activepieces-flow-config.md: реальные входы, вызов выбранного AI connection,
разбор ответа, проверка схемы, ветка «нет знания», writer, подтверждение и ошибка.
Импортировать и запустить на выбранной версии; сохранять конфиг без секретов и локальных ID.
Приёмка: положительный сценарий, has_pattern=false, невалидный AI JSON, ошибка provider/writer.
Недостающий API key отмечать как блокировку живого теста, а не заменять успехом мока.

### SC-10 — Актуальность индекса

После persisted изменения ставить задачу индексации; обработать удаление/superseded,
повторную доставку и восстановление Khoj. Разделить состояния saved/indexed.
Приёмка: новое знание находится; изменённое возвращает новую версию; удалённое не находится;
временный отказ индекса не отменяет подтверждённую запись памяти.

### SC-11 — Hooks и Git sync

Сохранить hook в .git-hooks-templates/, добавить установщик без перезаписи чужого hook.
Учитывать core.hooksPath, worktree, Windows, отсутствие upstream, текущую ветку.
Объединить capture и синхронизацию: не конкурировать двумя post-commit файлами.
Автоматические записи не порождают повторный анализ; синхронизация сообщает ошибки,
не использует force push/reset и не обещает «push только каталога».
Приёмка: чистый клон, повторная установка, исходный пользовательский hook, offline,
divergence между двумя рабочими копиями; всё исходное содержимое сохранено.

### SC-12 — Память и продолжение проекта

Создать project-memory-init и связать auto-learn/profile-update с bridge и HANDOFF.
Маркеры в проектных инструкциях позволяют обновлять только принадлежащую системе секцию.
Учитывать завершение сессии раньше завершения задачи. Одна запись резюме вместо двойного
auto-learn из Phase 5/8. Резюме отражает реальные результаты проверок и незакоммиченные изменения.
Приёмка: новый и существующий проект; повторный init без дублей; другая сессия восстанавливает
следующий шаг; профиль не зависит от текущей папки.

### SC-13 — Второй ПК

Создать bootstrap/doctor для нового устройства и docs/second-pc.md: clone, runtime,
конфигурация локальных путей, секреты, установка hooks, запуск сервисов, синхронизация,
перестроение индекса. Воспроизвести на изолированном клоне, затем на реальном втором ПК.
Приёмка: продолжение проекта A, запуск B с общим профилем и без чужого состояния;
конфликт записи с двух устройств сохранён и разрешается явно.
Если второй ПК недоступен, отчёт «изолированный клон проверен» не закрывает живую проверку.

### SC-14 — Figma

Довести .claude/mcp-servers/figma, .env ignore и README. Читать реальные nodes/style,
fills/opacity, layout spacing, padding и разные радиусы; сохранять происхождение и не
терять одноимённые узлы. Определить поддерживаемое подмножество и сообщать ограничения.
Использовать проверенную реализацию MCP транспорта/SDK либо доказать соответствие выбранному
протоколу; REST endpoint сам по себе не MCP. API ошибки и node-id в URL обрабатывать явно.
Приёмка: fixture с ожидаемыми значениями, настоящий MCP client initialize/list/call,
живой запрос к доступному макету. Не обещать отсутствие ошибок дизайна.

### SC-15 — Маршруты

Один start/router: разработка (поведение и тесты), сайты (бриф, дизайн, визуальная проверка,
формы и требуемая аналитика), маркетинг (цель, аудитория, источники, материалы и измерение).
Gemini-исследование принимается как внешний документ; API-интеграция Gemini не требуется.
Не навязывать Figma, анимацию, рекламу, SEO-статьи каждой задаче. Данные клиента отделены.
Приёмка: три примерных запроса выбирают маршрут и релевантную память; сложность процесса
соразмерна задаче; публикация/расход бюджета не возникают из одного анализа.

### SC-16 — Качество и экономика

Добавить шаблон evidence-отчёта и независимую проверку исходных требований, регрессий,
сценариев и ограничений. Собрать фактические время, retries и доступные метрики
контекста/токенов на сопоставимых задачах; недоступную стоимость обозначать unknown.
Проверка по брифу обязательна с первого тикета, здесь оформляется единый механизм.
Приёмка: внедрённый намеренно дефект/пропущенное требование обнаруживается приёмкой;
отчёт не приравнивает node --check к функциональному успеху.

### SC-17 — Эксплуатация

Свести инструкции запуска, диагностики и отката в docs/system-operations.md;
обновить README/QUICKSTART и ссылки. Backup включает память, DB flow, конфигурацию,
неотправленную очередь и способ безопасного восстановления ключей. Проверить восстановление
на отдельной копии. Описать будущий remote-профиль: сервер, приватный доступ, один writer,
backup и health; не объявлять удалённый сервер развёрнутым без фактического запуска.
Приёмка: другой агент проходит runbook; восстановленный flow обрабатывает событие;
потерянный индекс перестраивается из источника без потери памяти.

### SC-18 — Финальная приёмка

Независимый приёмщик читает SPEC, реальные артефакты и отчёты. Выполняет полный цикл
из SPEC и сверяет R01–R13. Для всех провалов назначает исправление ответственному тикету,
а не открывает бесконечный новый архитектурный план. Создать RELEASE-REPORT.md с
таблицей requirement → ticket → evidence → status. Нет проверенного второго ПК/доступа
к обязательному сервису — соответствующая часть остаётся awaiting-validation.
Релиз v1 готов только после устранения блокирующих дефектов и обязательных проверок.

## Требования к пакету Sonnet

- Создать issues/SC-01-*.md … SC-18-*.md и issues/SUMMARY.md.
- SUMMARY содержит порядок, зависимости, статусы, ручные prerequisites и покрытие R01–R13.
- Существующие файлы инспектировать. Для новых указать точный предлагаемый путь.
  Не требовать от следующего агента «найти где-то worker» или придумать API целиком.
- Контракты фиксировать один раз в spec/contract, в тикетах ссылаться на нужную часть.
- Команды будущих проверок согласовать с создаваемыми файлами; не выдумывать существующие тесты.
- Все ссылки вычислить от расположения issues, проверить отсутствие циклов и пропущенных требований.
- Начально только SC-01 ready-for-agent, остальные planned. Живые доступы перечислить заранее.
- Можно разделить большой тикет на суффиксы a/b с обновлением графа, если иначе он непроверяем.
  Не расширять согласованную цель и не переписывать предыдущие исторические тикеты.
- После нарезки остановиться и передать SUMMARY исполнителю. На этом шаге не запускать сервисы.
