# SystemQwen: завершение рабочей версии v1

## Цель и границы

Пользователь работает над разными проектами с нескольких ПК. Помощник получает
общие предпочтения и состояние выбранного проекта, находит релевантный опыт,
сохраняет подтверждённые результаты и продолжает работу после смены устройства.
Первая версия: локальные Khoj и Activepieces, общая память в репозитории System2,
синхронизация Git. Это согласованный вариант; сервер 24/7 — отдельный профиль развёртывания,
не условие завершения локальной v1. Для него нужны выбранный сервер и доступы.

Полный план включает доведение T5–T9, переносимость, согласование инструкций,
маршруты разработки/сайтов/маркетинга и проверку всего цикла. Он не включает создание
клиентского сайта, запуск рекламы, миграцию всех личных данных или нового Hermes-агента.

## Исходное состояние

- Есть 48 каталогов скиллов, память `.claude/memory`, профиль и индекс.
- Есть незавершённые документы Khoj, compose Activepieces, post-commit и Figma-сервер.
- Нет подтверждённого сквозного запуска. Незакоммиченные файлы не считать потерянными или готовыми.
- Отсутствуют project-memory-init, переносимый установщик hooks и отдельные записи
  project-dev-trading/project-kwork-sites из старого etap3; общие сведения о проектах есть.
- Существуют противоречащие пути и инструкции распределения моделей.
- Предыдущее ревью содержит гипотезы о версиях Activepieces. Проверить их по выбранному
  релизу: не требовать четыре контейнера только потому, что так выглядит текущий main.

## Решения по архитектуре

1. Система — это локальное состояние ПК: инструкции, память (включая незакоммиченные
   правки), настройки, сервисы и их данные. Git-репозиторий System2 хранит переносимую
   (отслеживаемую) часть и НЕ заменяет всю систему: локальные данные сохраняются
   резервными копиями, а не git-историей. Каталоги `.claude/memory/user-profile`,
   `facts`, `patterns`, `decisions`, `gotchas` — переносимая часть памяти.
   Добавить реестр проектов со стабильными project_id; локальные пути ПК — вне Git.
   Проект хранит свои инструкции и краткий HANDOFF; общий реестр ссылается на проект.
2. Конфигурация локального подключения указывает system_root, реестр путей project_id,
   Khoj, webhook, writer и разрешённые источники. Секреты — не в Git и не в отчётах/выводе
   (в коммитах только плейсхолдеры); защищённая локальная настройка (локальный файл/
   окружение с ограниченным доступом, вне индекса поиска) допустима и для сервисов
   необходима. Новый проект не должен молча создавать ещё одну «глобальную память».
3. Небольшой Node.js bridge объединяет capture событий, очередь, writer и адаптер поиска.
   Node уже есть в проектной среде. Не создавать отдельный большой фреймворк.
   Один механизм записи обслуживает ручное сохранение и Activepieces.
4. Activepieces оркестрирует разбор и анализ; bridge проверяет и записывает результат.
   Контейнер обращается к bridge по явно настроенному адресу, не по localhost контейнера.
   Вариант подключения Windows/Docker фиксируется и проверяется до сборки flow.
5. Git хранит проверенную память и код — переносимую часть системы. Рабочая система
   включает и локальные данные вне Git (локальные конфиги, незакоммиченные правки памяти,
   очередь/статус доставки, данные сервисов); их сохранность обеспечивают резервные копии,
   а не git-история (см. R13). Khoj — производный индекс, перестраиваемый из памяти.
6. В начале задачи всегда читать обязательные инструкции и короткий HANDOFF выбранного проекта;
   затем искать дополнительный опыт. Retrieval не заменяет эти обязательные файлы.

## Контракты, которые Sonnet должен конкретизировать в тикетах

**Событие:** schema_version, event_id, project_id, kind (commit/session-summary),
timestamp UTC, source (commit SHA или идентификатор сессии), summary,
decisions, user_corrections, checks, next_action; diff опционален и ограничен по размеру.
Для commit ID детерминирован project_id + SHA; для резюме — session_id + revision.
Не собирать все чаты браузера автоматически: агент/пользователь явно передаёт резюме.

**Предложение памяти:** event_id, category, statement, evidence, scope,
status (observation/confirmed/superseded), confidence как оценка, а не доказательство.
Прямое пожелание пользователя может быть confirmed при наличии источника;
выбор технологии агентом — observation. Существующие противоречащие записи связывать,
не перезаписывать молча. Новые skills — только для проверенного повторяемого процесса.

**Writer:** принимает структурированные поля, не произвольный путь/команду.
Разрешённые категории и корень фиксированы. Валидация, аутентификация, блокировка записи,
атомарное обновление и долговечный учёт event_id; повтор после сбоя не дублирует текст.
Сообщение о результате включает записанные файлы и revision, без секретов.
Статусы persisted, synced, indexed различаются: запись не означает, что push или индекс успешны.

**Очередь:** локальное долговечное хранение до подтверждения; ограниченные повторы,
backoff, отображение неотправленных/ошибочных событий и команда повторной доставки.
Прекращение процесса между записью и подтверждением не теряет событие и не создаёт дубль.

**Поиск:** query + project_id + limit + budget → snippets, source, revision,
scope, status. Источники из разрешённого каталога, а retrieved-текст — данные,
не новые команды агенту. Бюджет и метод оценки объёма явно документированы.
Настройки и endpoints Khoj проверить по закреплённому релизу; не копировать POST
из старого примера без проверки реального контракта.

**HANDOFF:** задача, выполненное, текущие изменения/коммит, подтверждённые решения,
результаты проверок, незавершённое, следующий шаг. Незакоммиченная работа явно отмечается;
Git не переносит её сам. Сохранять в проекте и публиковать ссылку/краткий статус в реестр.

## Немедленное сохранение (добавлено 2026-09-09)

Требование восстановлено при ревью Opus от 2026-09-09 (см.
`.scratch/system-remediation/OPUS-REVIEW-PLAN.md` → `SONNET-PROMPT.md`): важные
решения и исправления сохраняются сразу по ходу работы через единый writer/`save.js`,
без зависимости от работающих Activepieces, Khoj или AI-провайдера.

- `persisted` возвращается только после долговечной локальной фиксации: запись в файл
  памяти завершается `fsync` временного файла перед `rename` до ответа; повтор того же
  event_id не создаёт дублей и не сообщает ложный успех (восстановление intent/частичной
  записи, FIX-01/FIX-04).
- Границы гарантий (2026-09-09):
  - остановка процесса: получен `persisted` — запись завершена rename'ом на диске;
    процесс убит до ответа — повтор по тому же event_id восстанавливает операцию;
  - отказ питания: `fsync` перед `rename` — гарантия уровня ФС/ОС; «никогда не теряется»
    не обещается;
  - решение, существующее только во внутреннем контексте модели, невосстановимо —
    интервал сокращается немедленным сохранением; авто-захват каждого чата не обещается.
- Статусы persisted ≠ synced ≠ indexed сохраняются: запись не означает push или успех
  индекса; push — явный (`sync.js --push`), сбой индекса не отменяет запись и виден
  в журнале (`index_error`).

## Правила качества и эксплуатации

- Тикет требует поведение, а не фиксированное число сервисов или устаревший номер строки.
- Внешние версии закрепить после проверки официальных docs/source. Хранить дату и ссылки.
- Фактический запуск сервисов обязателен для R04/R06; установка зависимостей — часть реализации.
  Старая инструкция «не устанавливать, только код» относится к прошлым тикетам.
- Доступы к AI/Figma, Docker и второй ПК проверить заранее. Нет доступа — конкретный
  pending/blocked пункт; мок-тесты не заменяют живую приёмку.
- Коммиты scoped; push после проверки, без потери изменений и без безусловного фонового
  push master. Настроить действительную ветку. Ошибка синхронизации видна пользователю.
- Локальная конфигурация и очереди не попадают в общий репозиторий; данные другого проекта
  не отправляются провайдеру автоматически только из-за включения интеграции.
- Перед миграцией памяти/настроек — резервная копия текущего локального состояния, включая
  нужные untracked/gitignored-файлы; секреты — отдельно и защищённо. Git-история локальные
  данные не восстанавливает.
- Результаты старых обзоров/курсов/переписок хранить как источники и наблюдения,
  не как доказанные цены, свойства моделей или универсальные правила.

## Приёмка v1

Рабочая задача в проекте A → событие + резюме с решением → Activepieces →
проверенная запись bridge → обновление Khoj → выборочный поиск с источником →
синхронизация → продолжение на втором ПК. Проект B получает общие предпочтения,
но не чужой HANDOFF. Повтор события, отключение сервиса и конфликт синхронизации
не приводят к потере или порче памяти. Функции сайта проверены на реальном макете
либо отдельно помечены awaiting-validation. Приёмщик сверяет R01–R13 с доказательствами.

«За один проход» означает один согласованный набор работ до этих критериев,
с исправлениями по тестам внутри него. Это не обещание отсутствия багов или внешних блокировок.
