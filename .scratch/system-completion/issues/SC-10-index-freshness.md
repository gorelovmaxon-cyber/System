# SC-10 — Актуальность индекса Khoj после записи/изменения/удаления

**What to build:** После persisted-записи памяти ставится задача индексации Khoj; обновление/удаление/superseded обрабатываются так, что поиск возвращает актуальную версию, а временный отказ индекса не отменяет подтверждённую запись и не создаёт бесконечного цикла автоматизации.
**Requirement IDs:** R08
**Blocked by:** SC-05, SC-09
**Status:** awaiting-validation

> Статус уточнён 2026-09-11: очередь индекса, ревизии, lease/backoff и aggregate-status проверены локально; живой reindex Khoj недоступен.

## Контекст

SPEC R08: «После записи/изменения/удаления памяти поиск обновляется; нет бесконечного цикла автоматизации». Статусы persisted/synced/indexed различаются (SC-08: writer отмечает persisted). Сейчас индексация Khoj — ручная (SC-04); после записи через writer поиск может вернуть устаревшее. Нужен механизм постановки задачи индексации, обработка удаления/superseded, повторной доставки и восстановления индекса после падения/пересоздания Khoj.

## Входные/выходные данные

Вход: события из writer-log со статусом persisted и без indexed; файлы `.claude/memory/…` после записи/изменения/удаления (superseded-правки тоже меняют файл). Выход: журнал indexer-log с задачами (pending → indexed|failed), поиск (SC-05) возвращает актуальное содержимое.
Правила:
- «saved ≠ indexed»: подтверждённая запись не отменяется и не прячется из-за отказа индекса; поиск может временно не находить новое — это видно по журналу (failed + причина).
- Удаление/superseded: удалённая/заменённая запись не находится поиском (или возвращается только как superseded-связь с пометкой), при этом прежний текст сохранён в файле (SC-03).
- Без бесконечного цикла: индексация не порождает новых событий/записей; авто-коммиты памяти исключены из анализа (префикс, SC-11).

## Алгоритм (шаг за шагом)

1. **Определить механизм переиндексации Khoj** по документации выбранного релиза (SC-04): поддерживает ли он инкрементальное обновление файла, переиндексацию всего корня, REST/CLI. Зафиксировать, что реально доступно; если инкрементального нет — использовать переиндексацию корня памяти с ограничением частоты (не чаще N раз в минуту) и пометкой в контракте.
2. **Реализовать indexer-log.js**: журнал задач (файл, дата, статус, причина, счётчик повторов) с ограниченными повторами и backoff; команда просмотра и ручного повтора.
3. **Реализовать indexer.js**: функция `queueIndex(paths)` → задачи в indexer-log; функция `run()` — берёт pending-задачи, вызывает механизм Khoj (шаг 1), отмечает indexed/failed; CLI: `indexer.js --run`, `indexer.js --status`, `indexer.js --requeue-failed`.
4. **Связать writer → indexer**: после persisted-записи (SC-08 writer.js) ставить задачу индексации на затронутые файлы; ответ /write не ждёт индексации (асинхронно), но в журнале события появляется `indexed:false` до выполнения.
5. **Обработать удаление/superseded**: при superseded-правке/удалении записи — задача индексации того же файла; проверить, что поиск перестаёт возвращать удалённое (или возвращает с пометкой superseded) после переиндексации.
6. **Проверить восстановление**: остановить/пересоздать Khoj (эмуляция потери индекса), пересобрать индекс из памяти штатным способом (SC-04) — поиск снова находит записи; журнал indexer-log переходит в indexed.
7. **Обновить контракт-док и конфиг** (секция «Актуальность индекса», indexer.* настройки), README.
8. **Проверить** сценариями ниже.

## Критерии приёмки

- [ ] Новое знание (запись через writer SC-08) находится поиском после обработки задачи индексации (поиск из SC-05 возвращает новый файл/фрагмент).
- [ ] Изменение записи (новая версия через writer) — поиск возвращает новую версию/актуальный текст, а не старый.
- [ ] Удаление/superseded — после переиндексации поиск не возвращает удалённую запись как актуальную (допустимо: superseded с пометкой).
- [ ] Временный отказ Khoj (остановлен на момент записи): запись остаётся persisted (в журнале writer-log indexed:false, в indexer-log failed с причиной); после восстановления Khoj `indexer.js --requeue-failed`/`--run` приводит к indexed.
- [ ] Нет бесконечного цикла: индексация/авто-записи не порождают новых событий анализа (проверка: за один акт записи — одна задача индексации, журнал не растёт сам собой).
- [ ] docs/memory-contract.md разделяет persisted/synced/indexed; R08 выполнен для записи/изменения/удаления.
- [ ] `git status` не показывает `.local/` (журналы вне Git).

## Superseded, удаление и ревизии — редакция 2026-09-11

Index-task идентифицирует `event_id`, нормализованный файл и hash его ревизии.
Точная повторная постановка идемпотентна; изменение, ручная повторная индексация,
superseded или явное удаление создают задачу новой ревизии. `indexed:true` у
writer-события допустим только после успеха всех его файловых задач.

Superseded сохраняет прежний текст и потому переиндексирует файл с обеими
историческими записями. Явное физическое удаление переиндексирует уже изменённый
файл без удалённой записи; её история остаётся только в Git/backup. Live-проверка
Khoj остаётся `awaiting-validation` до появления сервиса.
