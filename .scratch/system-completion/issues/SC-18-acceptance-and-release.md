**Requirement IDs:** R01–R13
**Blocked by:** SC-01…SC-17
**Status:** blocked

> Статус уточнён 2026-09-11: v1 NOT READY до независимой приёмки локального блока и живых Khoj/Activepieces/Figma/second-PC сценариев.
**Перед началом работы:** Открой VS Code в `E:/System2`. Все тикеты SC-01…SC-17 приняты (или явно awaiting-validation/blocked с причинами). Назначь независимого приёмщика: тот, кто не писал код соответствующих тикетов (планировщик/Opus или отдельная сессия).

## Контекст

SPEC «Приёмка v1»: рабочая задача в проекте A → событие + резюме с решением → Activepieces → проверенная запись bridge → обновление Khoj → выборочный поиск с источником → синхронизация → продолжение на втором ПК. Проект B получает общие предпочтения, но не чужой HANDOFF. Повтор события, отключение сервиса и конфликт синхронизации не приводят к потере или порче памяти. Функции сайта проверены на реальном макете либо отдельно помечены awaiting-validation. Приёмщик сверяет R01–R13 с доказательствами. «За один проход» — один согласованный набор работ до критериев; это не обещание отсутствия багов или внешних блокировок. SC-16 дал evidence-механизм; здесь — сводная проверка и релизный отчёт.

## Входные/выходные данные

**Полный цикл приёмки (из SPEC):** выбрать реальную рабочую задачу в проекте A (например, SystemQwen-задачу/тестовый тикет) → выполнить её по маршруту (SC-15) с retrieval (SC-05) → зафиксировать событие (commit/session-summary через hook SC-11/capture SC-07) → flow Activepieces (SC-09) анализирует → bridge (SC-08) записывает → индексация (SC-10) обновляет поиск → поиск возвращает запись с источником → синхронизация (SC-11) → продолжение в другом клоне/ПК (SC-13). Параллельно: проект B получает общие предпочтения, но не чужой HANDOFF.
**Отрицательные сценарии:** повтор события (нет дубля); отключение Khoj (задача продолжается, R05); конфликт синхронизации (обе версии сохранены).
**Функции сайта:** при наличии маршрута «сайты» — проверка на реальном макете или awaiting-validation.

## Алгоритм (шаг за шагом)

1. **Собрать состояние**: прочитать SUMMARY и отчёты всех тикетов; составить предварительную таблицу R01–R13: для каждого требования — какие тикеты его покрывают и какие есть доказательства.
2. **Независимый прогон полного цикла** из SPEC на реальной (или специально созданной тестовой) задаче проекта A. Каждый шаг подтверждается фактическим результатом (команда+вывод), а не ссылкой на «тикет принят».
3. **Прогнать отрицательные сценарии**: повтор события, отключение Khoj/сервиса, конфликт синхронизации (эмуляция двух клонов, SC-13) — без потери/порчи памяти.
4. **Проверить проект B**: общий профиль доступен, чужой HANDOFF не подтянулся.
5. **Сверить функции сайтов** (если в объёме): реальный макет/доступ — иначе awaiting-validation.
6. **Заполнить RELEASE-REPORT.md**: таблица requirement → ticket → evidence → status. Для каждого «не done» — причина и назначенное исправление (тикет-фикс). Отдельно — перечень внешних предпосылок (второй ПК, ключи, Figma-доступ) и их статус.
7. **Исправления**: блокирующие дефекты, найденные приёмкой, оформляются как маленькие fix-тикеты на владельца и передаются в исполнение; после исправлений — повторная проверка именно этих пунктов.
8. **Решение о релизе**: v1 готов, когда нет блокирующих дефектов и обязательные проверки выполнены (done), а необязательные честно awaiting-validation. Зафиксировать решение в RELEASE-REPORT.md и SUMMARY.
9. **Проверить** сценариями ниже.

## Критерии приёмки

- [ ] Полный цикл из SPEC пройден на реальной задаче проекта A: событие → flow → запись bridge → обновление поиска → поиск с источником → синхронизация → продолжение в другом клоне/ПК.
- [ ] Повтор события не создаёт дубля; отключение Khoj не блокирует задачу; конфликт синхронизации сохраняет обе версии.
- [ ] Проект B получает общие предпочтения, но не чужой HANDOFF.
- [ ] RELEASE-REPORT.md содержит таблицу R01–R13 с evidence и статусами; ни один пункт не помечен done без доказательства.
- [ ] Каждый «не done» имеет причину и назначенное исправление (fix-тикет на владельца); новый архитектурный план не открывался.
- [ ] Релиз v1 объявлен только при отсутствии блокирующих дефектов и выполнении обязательных проверок; второй ПК/ключи/макет без реальной проверки — awaiting-validation.
- [ ] R01–R13: сверены с доказательствами по всему набору.

## Проверки

**Среда и предпосылки:** локально + внешние предпосылки по списку (второй ПК, API-ключи, Figma-макет); при их отсутствии соответствующие проверки — awaiting-validation (это ожидаемо и фиксируется, а не маскируется).
**Команды:** полный цикл по шагам SPEC (используются команды из принятых тикетов и system-operations.md); проверки отрицательных сценариев.
**Ожидаемый результат:** цикл работает с доказательствами; отчёт полон; статусы честные.
**Если проверка недоступна:** внешняя предпосылка отсутствует → awaiting-validation с причиной; приёмщик не «закрывает» её и не заменяет моком.

## Ограничения

- Этот тикет — приёмка и отчёт, не новая разработка: исправления минимальны и назначаются владельцам.
- Релиз v1 = готовность локальной версии до критериев; сервер 24/7/remote-профиль — вне v1 (SC-17 описывает как план).
- Незакрытые awaiting-validation пункты не блокируют «релиз локальной v1», если они явно перечислены; блокирующие — блокируют.

## Как закончить

1. Выполнить полный цикл и отрицательные сценарии; заполнить RELEASE-REPORT.md; назначить fix-тикеты при необходимости.
2. Отдельный коммит: RELEASE-REPORT.md, SUMMARY.md (финальные статусы), fix-тикеты (если созданы).
3. Приёмщик ставит done по этому тикету только после завершения назначенных исправлений и финальной сверки; релиз объявляется в RELEASE-REPORT.md.
4. Ответ до 6 строк: итог приёмки (R-таблица кратко), блокеры/awaiting-validation, коммит, решение о релизе v1.
