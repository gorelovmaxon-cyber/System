# SC-13 — Восстановление и продолжение на другом ПК

**What to build:** Документированный и проверенный bootstrap нового устройства (clone → runtime → локальные пути/секреты → hooks → сервисы → синхронизация → перестроение индекса) с проверкой на изолированном клоне и, при доступности, на реальном втором ПК.
**Requirement IDs:** R09, R13
**Blocked by:** SC-12
**Status:** planned
**Перед началом работы:** Открой VS Code в `E:/System2`. SC-12 принят (HANDOFF/реестр работают). Определи, доступен ли реальный второй ПК; если нет — пометь заранее в SUMMARY/отчёте: живая проверка второго ПК будет awaiting-validation.

## Контекст

SPEC R09: на другом ПК восстанавливаются память, состояние проекта и подключения; конфликты сохраняют обе версии. R13: резервирование, восстановление, документация запуска и перечень ручной настройки проверены. Приёмка v1: продолжение проекта A на втором ПК, запуск проекта B с общим профилем и без чужого HANDOFF; конфликт записи с двух устройств сохранён и разрешается явно. Решение 1: локальные пути ПК — вне Git (реестр в конфиге SC-02). Khoj — производный индекс, перестраиваемый из памяти.

Планировавшийся `.scratch/etap3/PROMPT_FOR_OTHER_PC.md` описывал продолжение на другом ПК, но без bootstrap/doctor, без проверки сервисов и без сценария конфликтов. Второй ПК — внешняя предпосылка; изолированный клон проверяется всегда, живой второй ПК — только при его наличии (иначе честный awaiting-validation).

## Входные/выходные данные

**doctor.js — вывод по каждому пункту:** `OK | MISSING <что> | BROKEN <что>: <инструкция>` (без значений секретов; например, `OK git/remote origin`, `MISSING config/system.local.json → запусти bootstrap/init-local-config`).
**Порядок bootstrap:** (1) git clone System2 (ветка по политике SC-11); (2) `init-local-config.js` — локальные пути/реестр для этого ПК; (3) секреты — по README сервисов (сгенерировать .env/токены локально); (4) `install-hooks.sh`; (5) установка/запуск сервисов (Khoj SC-04, Activepieces SC-06, bridge SC-08) — по их README; (6) перестроение индекса (SC-10/SC-04); (7) `doctor.js` — всё OK; (8) синхронизация: `sync.js --pull`-эквивалент/merge без force (конфликты сохраняются).

## Алгоритм (шаг за шагом)

1. **Написать doctor.js**: проверить каждый пункт из «Входные/выходные данные»; единый JSON/текстовый вывод; коды выхода (0 = готово, 1 = проблемы).
2. **Написать bootstrap.js**: последовательность шагов; каждый шаг вызывает существующие команды (init-local-config, install-hooks, README-команды сервисов, indexer); идемпотентен; не делает ничего необратимого без явного флага; после завершения запускает doctor.
3. **Написать docs/second-pc.md**: полный runbook с перечнем ручной настройки, командами, ожидаемыми результатами и типовыми ошибками; явно: Khoj-индекс и .env на втором ПК пересоздаются локально, из Git они не приходят.
4. **Проверить на изолированном клоне** (обязательно, локально): свежий clone во временную папку (та же машина — проверка механики), bootstrap → doctor OK; продолжение «проекта A»: скопировать/создать тестовый HANDOFF-проект или выполнить init (SC-12) — восстановить следующий шаг; «проект B» с общим профилем без чужого HANDOFF.
5. **Проверить конфликт с двух устройств** (эмуляция на двух локальных клонах): в обоих клонах запись в память → коммиты с разными изменениями одного файла → синхронизация/merge → конфликт сохранён (обе версии видны), разрешение явное, без force и потери.
6. **Реальный второй ПК** (если доступен): прогнать bootstrap и сценарии R09; если нет — зафиксировать: «изолированный клон проверен; живая проверка второго ПК — awaiting-validation».
7. **Обновить projects-overview/реестр**: пометка, что проверено (клон/реальный ПК), без лишних деталей.
8. **Проверить** сценариями ниже.

## Критерии приёмки

- [ ] doctor.js на текущей машине показывает все пункты OK (после bootstrap) либо понятные MISSING/инструкции.
- [ ] Свежий изолированный клон: bootstrap проходит до doctor OK; память/реестр/HANDOFF восстанавливаются; hooks активны; индекс перестроен и поиск находит записи.
- [ ] Продолжение проекта A на «втором устройстве» (клон): start/Phase 0 находит HANDOFF и следующий шаг; проект B запускается с общим профилем и НЕ получает чужой HANDOFF.
- [ ] Конфликт записи из двух клонов: merge сохраняет обе версии (в конфликте видны обе), разрешение явное, без force; ничего не потеряно.
- [ ] Незакоммиченная работа на исходной машине явно помечена в HANDOFF и не «переезжает» сама (Git не переносит её) — документировано в second-pc.md.
- [ ] Реальный второй ПК: если доступен — сценарии R09 выполнены живьём; если нет — в SUMMARY/отчёте статус «изолированный клон проверен; второй ПК awaiting-validation» (не выдаётся за полную проверку).
- [ ] R09/R13: восстановление памяти, состояния проекта и подключений описано и проверено на клоне; перечень ручной настройки есть.

## Проверки

**Среда и предпосылки:** локально (два клона); реальный второй ПК — внешняя предпосылка.
**Команды:** `node scripts/memory/doctor.js`, `node scripts/memory/bootstrap.js` (во временном клоне), команды из docs/second-pc.md; эмуляция конфликта — коммиты в двух клонах + merge.
**Ожидаемый результат:** bootstrap→doctor OK на клоне; конфликт-merge без потерь; статусы честные.
**Если проверка недоступна:** второй ПК отсутствует → его живая проверка помечается awaiting-validation; проверка механики на изолированном клоне обязательна и выполняется.

## Ограничения

- Удалённый сервер/облачный профиль — не здесь (SC-17 описывает как будущее).
- Никаких авто-push и деструктивных операций на втором ПК; конфликты разрешаются явно пользователем.
- Не копировать локальные секреты/очереди между машинами через Git.
