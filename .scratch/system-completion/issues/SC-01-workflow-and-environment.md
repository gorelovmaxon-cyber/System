## Алгоритм (шаг за шагом)

1. **Зафиксировать целевую модель ролей** (текст для docs/system-workflow.md):
   - **Планировщик** (роль, обычно Opus/архитектор в Claude Code): grill → spec → план работ; НЕ пишет код реализации.
   - **Автор тикетов** (в текущем процессе — Sonnet): нарезает проверяемые тикеты по spec и единому шаблону.
   - **Исполнитель** (в текущем процессе — GPT Luna через VS Code расширение): реализует по алгоритму тикета строго, тестирует, коммитит; НЕ меняет архитектуру тикета.
   - **Приёмщик** (планировщик/Opus): проверяет diff, тесты, соответствие тикету и требованиям; ставит done.
   - **Пользователь** — оркестратор. Гейты: остановка после подготовки spec, после нарезки тикетов и после приёмки каждого тикета (awaiting-review). Исполнение уже согласованного набора работ не требует нового разрешения на каждый тикет — тикеты выполняются по очереди с остановкой на приёмку.
2. **Проверить существующее поведение**: прочитать все файлы из «Файлы для изменения» и найти фрагменты, противоречащие целевой модели (роли, «полный код в тикете», «200–300 строк», ссылки на templates/ticket-template.md, привязки к конкретной модели). Составить список правок.
3. **Написать docs/system-workflow.md** — единственный источник процесса: роли, фазы с гейтами, правило «один тикет = один коммит = одна остановка», правило тикетов (поведение и проверки вместо полного кода; короткие примеры только против неоднозначности), политика коммитов и push (коммит после каждого тикета; push — явно, после проверки, на выбранной ветке; без force push/reset; ошибки синхронизации видны пользователю — механизм в SC-11), правило «результат = проверено и запущено, а не написано», статусная цепочка planned → ready-for-agent → in-progress → awaiting-review → done / awaiting-validation / blocked.
4. **Проверить окружение и зафиксировать версии** (всё без вывода секретов, доступы — имена/наличие, не значения):
   - `git --version`; реальный путь Git Bash (`where bash` или `git --exec-path`); фактическое значение `git config core.hooksPath` (пусто или каталог — зафиксировать в ENVIRONMENT.md как есть, не сбрасывать и не предполагать); фактический `git remote -v` и текущая ветка.
   - `node --version`, `npm --version`.
   - `docker --version`, `docker compose version`, `docker info` (работает ли демон; режим WSL2/Desktop).
   - Khoj: `khoj --version` (если установлен), иначе пометить «не установлен» — установку делает SC-04.
   - Activepieces/Figma/AI-подключения: зафиксировать фактическое состояние (запущены/остановлены/отсутствуют — проверкой процессов/health, не по ожиданию) и перечислить, какие внешние доступы понадобятся далее (API-ключ Figma, ключ AI-провайдера для flow, доступ ко второму ПК) — только имена, не значения.
   - **Версии по официальным источникам**: выбери совместимые версии для Khoj (установщик и релиз), Activepieces (тег образа), postgres/redis-образов и Node LTS. Проверяй на официальных docs/release-страницах, в ENVIRONMENT.md запиши дату проверки и ссылки. Не копируй «latest» и не утверждай контракты/эндпоинты из старых тикетов без проверки.
5. **Внести правки** в перечисленные файлы по списку из шага 2. Сохранять смысл STOP-гейтов; для `.claude/skills/autopilot/SKILL.md` — только согласование формулировок исполнителя/гейтов в Phase 3.5/4/8 (маршруты фаз 0/0.5/1/2/3/5 не менять).
6. **Собрать ENVIRONMENT.md**: таблица версий с датами и ссылками; список доступного/отсутствующего; выбранный вариант сетевого подключения Windows/Docker к host-процессу (для SC-06) — проверить возможность `host.docker.internal` или зафиксировать альтернативу.
7. **Проверить результат** сценариями ниже; затем оформить коммит.

## Проверки

**Среда и предпосылки:** локально на этом ПК (Windows 11); в этом тикете сервисы не настраиваются (это SC-04/SC-06/SC-14) и не останавливаются — проверка ограничивается наличием, версиями и фактическим состоянием запущенных процессов; существующие настройки/конфиги не изменяются.
**Команды:** например: `git status`, `node --version`, `docker compose version` — точный набор в ENVIRONMENT.md. Команды, которых ещё нет, помечать «создать в этом тикете», если файл должен появиться здесь.
**Ожидаемый результат:** каждое утверждение в ENVIRONMENT.md подтверждено фактическим выводом команды или помечено как недоступное.
**Если проверка недоступна:** причина (например, «Docker Desktop не установлен», «нет доступа ко второму ПК») фиксируется в ENVIRONMENT.md; это не блокирует текстовые правки, но статус таких пунктов — awaiting-validation.

- Этот тикет — только правила, тексты и проверка среды. Сервисы Khoj/Activepieces/Figma/второй ПК здесь не настраиваются и не запускаются (SC-04/SC-06/SC-13/SC-14).

- Внешние версии закрепляются в ENVIRONMENT.md и переиспользуются всеми следующими тикетами; если позже обнаружится несовместимость, версии меняются в SC-01-revision только по согласованию.

## Как закончить

1. Проверить diff; выполнить проверки; сохранить краткие результаты в отчёт тикета.
2. Создать отдельный коммит с явным списком относящихся к тикету файлов (правила, system-workflow.md, ENVIRONMENT.md). Не включать чужие изменения (незакоммиченные черновики других работ) и не приписывать авторство другой модели.
3. Исполнитель ставит awaiting-review, приёмщик — done только после приёмки.
4. Ответ до 6 строк: ID, результат, проверки, коммит, оставшиеся ограничения, следующий доступный тикет (SC-02).
