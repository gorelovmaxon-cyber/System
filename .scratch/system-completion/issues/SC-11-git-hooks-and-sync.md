# SC-11 — Переносимые Git hooks и синхронизация

**What to build:** Переносимый post-commit hook в репозитории с установщиком (без перезаписи чужого hook), объединяющий capture события (SC-07) и уведомление flow (SC-09); синхронизация Git без force push/reset, с видимыми ошибками, сохранением конфликтующих версий и без бесконечной рекурсии.
**Requirement IDs:** R07, R09
**Blocked by:** SC-07, SC-10
**Status:** planned
**Перед началом работы:** Открой VS Code в `E:/System2`. SC-07 (capture/queue), SC-10 (indexer) приняты. SC-09 даёт конечный адрес уведомления flow. Свериться с фактическим состоянием hooks из ENVIRONMENT.md (SC-01) и перепроверить командами (`git config core.hooksPath`, наличие и содержимое `.git/hooks/post-commit`), ничего не изменяя и не сбрасывая. Если в `.git/hooks/post-commit` (вне дерева) есть curl-заглушка с webhook Activepieces — её роль заменяется этим механизмом.

## Контекст

SPEC: события из сессии дополняют Git; очередь/статус доставки не коммитятся; synced ≠ persisted ≠ indexed. Правила эксплуатации: коммиты scoped; push после проверки, без потери изменений и без безусловного фонового push master; настроить действительную ветку; ошибка синхронизации видна пользователю. R09: на другом ПК восстанавливается состояние; конфликты сохраняют обе версии.

Состояние на момент нарезки: в `.git/hooks/post-commit` (вне дерева) была curl-заглушка (bash, fail-open), шлющая JSON в webhook Activepieces; `core.hooksPath` тогда не был задан; `.git-hooks-templates/` не существовал. Фактическое состояние на момент исполнения — из ENVIRONMENT.md (SC-01): не предполагать, а свериться с ним и перепроверить (см. «Перед началом работы»). Старый тикет etap3/T2 (фоновый `git push origin master`) — отклонённая идея (авто-push без проверки запрещён); в CLAUDE.md правило «commit + push» конфликтует с git-guardrails (SC-01 уже снял безусловный push). Механизм auto-learn-исключения: существующий hook пропускал коммиты с префиксом `auto-learn:` — сохранить и формализовать.

## ⚠️ Файлы НЕЛЬЗЯ трогать

- `.git/` служебные файлы, кроме установки hooksPath через установщик; не редактировать `.git/config` вручную за пределами команды установщика.

- Не выполнять force push/reset и не настраивать фоновый авто-push.
- Flow/bridge/память — их работы уже приняты; здесь не переделывать.

## Входные/выходные данные

**post-commit (поведение):** после каждого коммита: (1) определить project_id (из реестра SC-02 по git remote/имени репозитория); (2) вызвать capture commit (SC-07) — событие уходит в локальную очередь, commit не блокируется и не зависит от сети/AI; (3) попытаться доставить/уведомить flow (SC-09) асинхронно; (4) пропустить коммиты с префиксом `auto-learn:`/служебным префиксом (SC-10/SC-12) — без рекурсии; (5) при любой ошибке — тихий выход (fail-open) + запись в лог очереди (SC-07), чтобы ошибка была видна через queue-status.
**sync.js:** показывает unpushed коммиты, статус относительно origin, untracked файлы памяти; `--push` выполняет push текущей ветки; divergence → сообщение «нужен merge/pull — конфликтующие версии сохраняются» (никакого --force).

## Алгоритм (шаг за шагом)

1. **Изучить текущий hook** `.git/hooks/post-commit` (только чтение): что он шлёт, какие поля, как пропускает `auto-learn:*`. Его логика capture-части переносится в переносимый hook + capture.js (SC-07).
2. **Создать `.git-hooks-templates/post-commit`**: переносимый bash/node-вызов. Правила: рабочая папка — корень git; определить project_id по remote (`origin` → github.com/gorelovmaxon-cyber/System.git → project_id systemqwen, соответствие в конфиге SC-02); собрать commit-событие (sha, message, при возможности — ограниченный diff) и передать в capture.js; затем неблокирующее уведомление flow (endpoint из конфига); пропуск служебных коммитов по префиксу; fail-open.
3. **Создать install-hooks.sh**: (а) проверка Git Bash; (б) если `core.hooksPath` уже указывает на этот каталог — ничего не делать (идемпотентно); (в) если пользовательский hook с именем post-commit существует в целевом месте и не является нашим — сделать резервную копию и спросить/потребовать `--force`; (г) установить `git config core.hooksPath .git-hooks-templates` (относительно корня) или скопировать файлы — выбери вариант и задокументируй; (д) проверить работу на тестовом коммите.
4. **Проверить отсутствие конкуренции двух post-commit**: в дереве только один источник (`.git-hooks-templates/post-commit`); до установки сохранить содержимое существующего `.git/hooks/post-commit` (если есть) в отчёт. После установки убедиться на тестовом коммите, что commit-событие создано ровно один раз и прежний hook (если остался в `.git/hooks`) не срабатывает повторно.
5. **Реализовать sync.js**: статус (git status/log относительно origin, untracked в `.claude/memory/` и конфигах), push текущей ветки явной командой, обработка offline и divergence; ни force, ни reset. Настроить действительную ветку для работы (не обязательно master): зафиксировать в доке, какая ветка используется для синхронизации.
6. **Обновить политику в доке/контракте**: docs/memory-contract.md — секция «Синхронизация»; CLAUDE.md — правило памяти (сверить с SC-01); usage-guide — ссылка.
7. **Живые проверки** ниже.

## Критерии приёмки

- [ ] Чистый клон репозитория во временную папку: `install-hooks.sh` ставит hooksPath, post-commit активен после установки (в клоне hooks не «приходят» сами — установщик обязателен; задокументировано).
- [ ] Повторная установка — идемпотентна (ничего не ломает, не дублирует). Установщик не перезаписывает чужой пользовательский hook без `--force` и бэкапа.
- [ ] Коммит (не служебный) → в очереди SC-07 появилось commit-событие с корректным project_id; commit не замедлился из-за сети/AI (fail-open).
- [ ] Служебный коммит `auto-learn:*`/эквивалент не порождает события/анализа (нет рекурсии).
- [ ] Offline/divergence: `sync.js --push` показывает понятную ошибку, ничего не теряет; при расхождении двух рабочих копий (эмуляция: второй клон с другим коммитом) merge сохраняет обе версии, без force.
- [ ] Установщик выполнен; активный источник post-commit — `.git-hooks-templates` (через hooksPath либо копирование — по выбранному и задокументированному варианту); дублирующего активного post-commit нет (тестовый коммит даёт ровно одно событие).
- [ ] В коммит не попадают `.local/` и локальные конфиги; R07-частично (событие в очередь) и R09-частично (конфликты сохраняются; полный второй ПК — SC-13).

## Проверки

**Среда и предпосылки:** локально; два изолированных клона для divergence-теста (можно локальные пути); network для push-теста — опционально (offline-сценарий выполняется без сети).
**Команды:** `bash .git-hooks-templates/install-hooks.sh`; `git commit` (тестовый); `node scripts/memory/queue-status.js`; `node scripts/memory/sync.js --status`, `node scripts/memory/sync.js --push`.
**Ожидаемый результат:** событие в очереди после коммита; установщик идемпотентен; конфликт/offline обработаны без потери.
**Если проверка недоступна:** push на реальный remote выполняется только с согласия пользователя; offline/divergence-сценарии проверяются на локальных клонах — этого достаточно для критериев.

## Ограничения

- Никакого безусловного фонового push; push — только явная команда/пользователь. Никаких force push/reset/clean.
- Полный сценарий второго ПК и «конфликт с двух устройств» — SC-13; здесь механика hooks/sync в одной рабочей копии.
- Не изменять capture/queue (SC-07) — hook их только вызывает.
