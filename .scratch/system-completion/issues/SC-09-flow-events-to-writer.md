## Входные/выходные данные

**Вход flow:** webhook-событие — JSON события по контракту SC-07 (kind=commit; в перспективе session-summary — если flow один на оба, учесть ветвление; v1: обрабатывать commit, session-summary — пометить как поддерживаемый ввод).
**Шаги flow:** (1) Webhook trigger; (2) подготовка prompt из полей события (summary/decisions/diff — ограниченно); (3) AI-шаг через выбранное подключение: задача «есть ли подтверждённое знание/паттерн для памяти; верни строгий JSON»; (4) разбор и валидация ответа (JSON-схема, has_pattern/category/statement/evidence/status); (5) ветка: has_pattern=false → завершить без записи (можно уведомить); category вне allow-list → ошибка/ветка; (6) вызов bridge `POST /write` на адрес host-моста (из ENVIRONMENT.md), заголовок с токеном; (7) по 200 — подтверждение (success), по ошибке — ветка ошибки с сохранением для диагностики.
**Схема ответа AI (пример для валидации; финальную фиксирует исполнитель в доке flow):**
```json
{ "has_pattern": true,
  "proposals": [ { "category": "gotchas", "statement": "…",
                   "evidence": "…", "scope": "systemqwen",
                   "status": "observation" } ] }
```
Валидация отклоняет: не-JSON ответ, отсутствие has_pattern, category вне allow-list, пустые statement.

## Алгоритм (шаг за шагом)

1. **Свериться с контрактом bridge** (docs/memory-contract.md, SC-08): URL, формат /write, токен, коды ошибок. Подтвердить адрес host-моста из ENVIRONMENT.md (SC-06).
2. **Выбрать AI-подключение**: имя connection из ENVIRONMENT.md (SC-06). Если ключа/подключения нет — flow всё равно собирается и импортируется, а живой AI-тест помечается blocked/awaiting-validation с причиной; НЕ заменять успехом мока.
3. **Собрать flow в UI** по шагам из «Входные/выходные данные». Для AI-шага: использовать выбранную модель подключения; инструкция-промпт требует строгий JSON по схеме; передавать в AI только нужные поля события и ограниченный diff.
4. **Экспортировать конфиг** в `services/activepieces/flows/`; вычистить секреты и локальные connection-id (заменить плейсхолдерами); написать README импорта.
5. **Импортировать** конфиг на чистой (или той же) инсталляции, чтобы убедиться в воспроизводимости (при необходимости — повторно создать connection локально).
6. **Живой тест**: (а) положительный сценарий — POST события, где AI находит паттерн: → /write 200, в памяти появилась запись, ответ flow success; (б) has_pattern=false — события без знания: flow завершается без записи; (в) невалидный AI JSON — ветка ошибки, запись не выполняется; (г) ошибка writer/provider (bridge остановлен или токен неверен) — ветка ошибки с видимой причиной, повтор возможен (SC-07 очередь).
7. **Проверить отсутствие рекурсии**: сгенерированная запись/коммит не порождает новый анализ (commit-префикс исключения — механизм SC-11; здесь убедиться, что flow не триггерится сам на свои артефакты, и при необходимости указать фильтр в SC-11).
8. **Обновить docs/activepieces-flow-config.md** и ENVIRONMENT.md; зафиксировать результаты тестов.

## Критерии приёмки

- [ ] Положительный сценарий: POST события (валидный JSON SC-07) → flow выполнен → bridge /write вызван → 200 → в `.claude/memory/` появилась запись (категория из allow-list), текст корректен.
- [ ] has_pattern=false: событие без знания → flow завершается без записи в память.
- [ ] Невалидный AI JSON (подмени ответ AI на мусор через тестовый сценарий/перехват) → ветка ошибки, запись не выполняется, ошибка видна в execution-логах flow.
- [ ] Ошибка writer (bridge остановлен) или provider (неверный токен/ключ) → flow не «молча проходит»: execution показывает ошибку; событие не потеряно (в очереди SC-07 остаётся для повтора).
- [ ] Конфиг flow в `services/activepieces/flows/` не содержит секретов и локальных connection-id; импорт на чистой инсталляции работает (или задокументированная ручная замена connection).
- [ ] Повторная доставка того же события не создаёт дубля в памяти (идемпотентность /write, SC-08).
- [ ] R06: Activepieces реально получает событие, анализирует и вызывает работающий writer; R07 — частично (полный цикл до Git — SC-11).

## Проверки

**Среда и предпосылки:** локально: Activepieces (SC-06) и bridge (SC-08) запущены. AI-подключение с действующим ключом — внешняя предпосылка; при её отсутствии живой AI-тест невозможен.
**Команды:** импорт/экспорт flow и запуск тестов — команды UI/API, фиксируются в docs/activepieces-flow-config.md; примеры curl: `curl -X POST http://localhost:8642/api/v1/webhooks/<WEBHOOK_ID> -H "Content-Type: application/json" -d @event.json` (event.json — по контракту SC-07); проверка результата в execution-логах и `git status`/`git diff` памяти.
**Ожидаемый результат:** выполнения flow в UI показывают success/ошибки по сценариям; запись в памяти соответствует ожиданиям.
**Если проверка недоступна:** отсутствие API-ключа AI-провайдера → положительный AI-сценарий помечается awaiting-validation (в SUMMARY и отчёте), но flow собирается, импортируется и тестируется до точки вызова AI (ошибка provider видна). Это не «успех мока» — статус честный.

## Контракт подтверждения webhook — редакция 2026-09-11

Durable-ответственность сначала принимает локальная очередь SC-07: hook выполняет
foreground enqueue и только затем запускает фоновый drain. Обычный ответ webhook
2xx не подтверждает запись памяти. Доставка подтверждается исключительно
синхронным коррелированным ответом flow `{event_id,status:"persisted"}` после
ответа bridge либо `{event_id,status:"no-pattern"}` для ветки без знания.
Отсутствующий, ошибочный или чужой `event_id`, а также 2xx без терминального
статуса считаются retryable; исходное событие остаётся в очереди. Повтор безопасен
за счёт идемпотентности writer.

Blueprint переведён на `/sync` и явный Return Response. По официальной документации
Activepieces sync webhook имеет отдельный timeout, а flow без Return Response не
даёт требуемого терминального подтверждения: [limits](https://www.activepieces.com/docs/install/reference/limits),
[flow control](https://www.activepieces.com/docs/build-pieces/piece-reference/flow-control).
Проверка выполнена 2026-09-11; live-import версии 0.86.3, restart и worker recovery
остаются `awaiting-validation`, поскольку Docker на этой машине отсутствует.
