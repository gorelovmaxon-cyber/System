## Входные/выходные данные

**HANDOFF-файл проекта** (`HANDOFF.md` в корне проекта, секции фиксированы):
```markdown
# HANDOFF — <project_id>
<!-- systemqwen:start -->
- **Задача:** …
- **Выполнено:** …
- **Текущие изменения/коммит:** … (незакоммиченное — явно: «НЕ ЗАКОММИЧЕНО: …»)
- **Подтверждённые решения:** …
- **Результаты проверок:** …
- **Незавершённое:** …
- **Следующий шаг:** …
<!-- systemqwen:end -->
```
Маркеры ограничивают секцию, которую система может обновлять; остальной файл принадлежит проекту. Обновление секции не затирает ручные правки вне маркеров.
**session-summary событие** (SC-07): источник — резюме сессии; revision растёт при повторном резюме той же сессии; публикация в реестре/конфиге: project_id + статус HANDOFF (link).

## Алгоритм (шаг за шагом)

1. **Создать project-memory-init**: шаги: (а) определить/создать project_id через реестр (SC-02): если проекта нет — предложить id и запросить подтверждение пользователя (не молча создавать); (б) в корне проекта найти CLAUDE.md и HANDOFF.md; (в) если системной секции нет — вставить блок `<!-- systemqwen:start/end -->` с шаблоном HANDOFF; если есть — обновить только секцию; (г) не трогать остальной файл; (д) записать статус в projects-overview/реестр; (е) идемпотентность: повторный запуск не создаёт дублей и не затирает ручные правки вне маркеров. Требование к кандидату скилла — проверенный повторяемый процесс (skill-forge: golden-кейсы в скилле или examples/).
2. **Развести auto-learn и резюме сессии**: auto-learn — запись подтверждённых фактов/правил через save.js (SC-08); резюме сессии — отдельный шаг: собрать session-summary-событие (SC-07: summary, decisions, user_corrections, checks, next_action) и сохранить HANDOFF + (при подтверждённых решениях) запись в память. Убрать дублирование Phase 5 → Phase 8 одного и того же разбора.
3. **Встроить в autopilot/start**: Phase 0 в проекте — вызов project-memory-init при необходимости; порядок «обязательные файлы → retrieval» в start (сверить с SC-05); при завершении сессии раньше задачи — запись/обновление HANDOFF со «следующим шагом» (в т.ч. в системах, где сессия обрывается).
4. **Обновить handoff-скилл**: формат по контракту, место хранения (в проекте), явная пометка незакоммиченной работы, публикация краткого статуса в реестр.
5. **Обновить docs/memory-contract.md** (секция HANDOFF/bootstrap) и projects-overview после реального init.
6. **Проверить** сценариями ниже на изолированном тестовом проекте.

## Критерии приёмки

- [ ] Новый тестовый проект: init создаёт HANDOFF.md и секцию в CLAUDE.md между маркерами; проект зарегистрирован с project_id; второй init не создаёт дублей и не затирает ручную правку вне маркеров.
- [ ] Существующий проект (например, сам System2): init находит секцию/обновляет статус, ничего чужого не меняет.
- [ ] Ручная правка внутри секции (не системная) при следующем обновлении сохраняется или явно показывается к подтверждению — без молчаливой потери.
- [ ] Завершение сессии до конца задачи: HANDOFF содержит «Незавершённое» и «Следующий шаг»; другая сессия (эмуляция новым процессом) по start/Phase 0 восстанавливает контекст из обязательных файлов и находит следующий шаг.
- [ ] За одну сессию — одна запись резюме (нет двойного auto-learn Phase 5+8): в журнале событий одно session-summary событие с revision.
- [ ] Незакоммиченные изменения явно отмечены в HANDOFF (текст «НЕ ЗАКОММИЧЕНО» при наличии); Git не «переносит» их сам.
- [ ] Профиль/память находятся по конфигурации (SC-02) независимо от текущей папки; тестовый проект не создал `.system-memory/` и не трогал чужой HANDOFF.
- [ ] R02/R07/R09-частично: общая память и память проекта связаны; резюме дополняет Git через очередь (полный цикл до второго ПК — SC-13).

## Проверки

**Среда и предпосылки:** локально; изолированный тестовый проект (временная папка или клон) для init-сценариев; запу��к скилла/фаз по их шагам.
**Команды:** инициализация и повторный init тестового проекта; проверка diff (только секция между маркерами); эмуляция второй сессии — чтение обязательных файлов по шагам start/Phase 0.
**Ожидаемый результат:** секция обновляется точечно; HANDOFF корректен; событие резюме одно.
**Если проверка недоступна:** работа с реальным внешним проектом (D:\dev) — только по явному подключению пользователем; без доступа — проверки на тестовом проекте и статус «внешние проекты не подключались» в отчёте.

## Ограничения

- Не создавать скилл без golden-кейсов и подтверждения процесса (skill-forge); реализация — в рамках этого тикета с проверкой.
- Новый skill — только для проверенного повторяемого процесса (SPEC); bootstrap должен быть опробован на тестовом проекте до подключения боевых.
- Не внедрять «глобальную память» в каждом проекте; единый корень — System2.
