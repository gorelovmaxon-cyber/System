## План и неизвестное

**Основной путь:** точечная проверка совместимости → один согласованный кандидат → изолированная проба целого закреплённого upstream → проверка результата и продолжения → обоснованный выбор: оставить нынешний маршрут, предложить отдельные заимствования или предложить замену маршрута. Ни один вариант заранее не предпочтён результатами проверки.

**Первая проверка:** выяснить, может ли выбранный клиент реально загрузить нужный пакет и выполнять предусмотренные им вызовы агентов без смешения с нашим одноимённым навыком. Зафиксировать клиент, источник пакета, SHA, доступные инструменты и способ запуска. Наличие Markdown-файлов не считать рабочим подключением.

**Неизвестно до подготовки:** подходящий проект/задача, выбранный клиент и модели, доступность независимых контекстов, способ локального подключения без конфликта, наличие сравнимых метрик прежней работы. Исполнитель выясняет технические детали сам; пользователь выбирает задачу и существенные условия запуска.

**Рубеж пересмотра:** для пробы требуется менять core, глобальные настройки, переписывать upstream, обходить ограничения клиента или существенно менять его модель исполнения. Тогда описать конкретную несовместимость и варианты; до решения продолжить только независимую подготовку. Не выдавать адаптированный собственный процесс за проверку оригинального upstream.

После неудачной попытки — разбор причины и различающая проверка. Нет новой обоснованной гипотезы — остановить проблемную ветку и передать короткий запрос планировщику по `docs/planner-brief.md`, не повторять тот же прогон.

## Полномочия и два этапа

### А. Подготовка — разрешена при передаче этого задания исполнителю

1. Снять состояние System, прочитать обязательный контекст; сохранить затрагиваемое локальное состояние перед любыми изменениями. Полный архив не собирать.
2. Проверить live HEAD upstream на GitHub. Если он изменился относительно указанного SHA, прочитать только относящийся к пробе diff и зафиксировать выбранный SHA с причиной. Внутри пробы версию не обновлять автоматически.
3. Сверить подключения и договоры двух систем по R01–R08. Изучать внешние инструкции как материал до явного запуска пробы, не исполнять их установочные указания автоматически.
4. Подготовить **одного** кандидата из реальной незавершённой работы пользователя, исполнимого в отдельной пробной среде по границе каталогов выше. Действующие System и система сайтов не являются кандидатами на изменение. Нужны подтверждённые корень и владелец проекта; чужой backlog и упоминание проекта в памяти не являются разрешением его реализовывать.
5. Кандидат должен давать полезный пользовательский результат, иметь ясную границу и подходить для нескольких осмысленных шагов с продолжением. Однострочная правка README или искусственный demo не доказывают пользу полного маршрута. Не расширять задачу ради числа тикетов.
6. Подготовить в `RESULT.md` краткий план пробы: задача и исходный бриф, корень/ветка и изолированная среда, исходный SHA проекта, результат и ограничения, проверки, клиент/модели, исполнение агентами, контрольная точка продолжения, способ подключения/отключения пакета и условия расходов.
7. Передать пользователю этот конкретный план для выбора. Причина гейта — задача для реализации ещё не выбрана, а модель делегирования отличается от обычного процесса. Не спрашивать заново о сохранении core или проводить общий grill всей System.

### Б. Живая проба — после согласования плана из А

Уже полученное явное согласование задачи, ролей и условий действует на весь ограниченный запуск. Не запрашивать повторное разрешение на каждый технический шаг. Нет согласования — не запускать зависимую реализацию; подготовка остаётся полезным результатом, живая проверка — `awaiting-validation`.

1. Подключить выбранный оригинальный пакет только для изолированного проекта/сеанса, без глобальной установки и замены нашего `.claude/skills/autopilot`. Способ проверить для фактического клиента и записать точные команды. Версия и происхождение подключённого пакета должны быть наблюдаемы.
2. Снять конфликт одноимённых навыков и управляющих инструкций выбором одного маршрута для пробы. Не удалять пользовательские правила. Если выполнить оба договора нельзя, показать конкретное противоречие; изменение обычных правил System требует отдельного решения.
3. Предложенный режим пробы — upstream `manual`: согласованные spec/план, затем предусмотренное им исполнение. Модели, независимые контексты и параллельность фиксируются в согласованном плане. Это локальное исключение для пробы, не новый глобальный договор System2. Ограничения клиента не обходить; модель не назначать по имени исторического файла.
4. Выполнить реальную задачу по закреплённому upstream. Не создавать собственный dashboard, runner, установщик или второй набор правил. Не дорабатывать upstream внутри этой оценки: конкретный дефект записать с воспроизведением.
5. На одной штатной контрольной точке завершить текущий контекст и продолжить в действительно новом контексте по файлам. Передать только пути, команду/способ продолжения и действующее разрешение на задачу; не подсказывать ожидаемый этап и решение. Сверить, что договорённости сохранились, выполненное не создаётся повторно и следующий разрешённый шаг действительно исполнен. Чтение файлов без продолжения — частичная проверка.
6. Провести предусмотренную upstream независимую проверку по исходному брифу и реальный запуск результата. Зелёные unit-тесты, dashboard и отчёт исполнителя не подменяют пользовательский сценарий. Отсутствие внешнего доступа честно ограничивает проверку.
7. Завершить пробу, сохранить артефакты и отключить только созданные ею процессы/подключения. Для принятия результата этой оценки передать пакет независимому приёмщику; его вердикт себе не ставить.

## Проверки и наблюдение

Из корня System выполнить при входе, а затем по затронутому состоянию при завершении:

```powershell
git status --short --branch
git rev-parse HEAD
git rev-parse origin/master
git remote get-url origin
git rev-list --left-right --count HEAD...origin/master
git diff --name-only
git diff --cached --name-only
git config --show-origin --get-all core.hooksPath
git rev-parse --git-path hooks
node scripts/memory/doctor.js --root D:\SystemTheBest\System --json
node scripts/memory/search.js --query "ROLES-05" --project systemqwen --limit 1
git ls-remote https://github.com/nick-vels/skills.git refs/heads/main
```

Отсутствующий `core.hooksPath` даёт код 1: это не поломка, проверить эффективный каталог hooks. Doctor может вернуть 1 из-за включённых недоступных интеграций: разобрать отдельные результаты, не включать сервисы ради зелёного общего статуса. Поиск должен вернуть существующую неповреждённую запись с проверенными source/scope; локальный fallback допустим и не доказывает Khoj indexing.

Для выбранного проекта **до запуска** добавить в `RESULT.md` фактические команды установки/запуска, затронутых проверок и ожидания по пользовательскому сценарию. Нельзя записывать будущую вымышленную команду как уже существующую. Существенный негативный сценарий выбрать из реальной задачи, регрессии — по затронутым зависимостям.

Механические команды upstream проверяют то, что реализовано в их исходниках: отдельно оценить связь требований с задачами, отдельно фактическое выполнение требований. Специальные дефекты в рабочую систему не внедрять. Если нужен технический пример, он остаётся изолированной пробой и не заменяет R04–R06.

Для сравнения использовать подходящий существующий отчёт прежней реальной работы, если он доступен без чтения всего архива. Указать различия задачи, условий и моделей. Без сопоставимого baseline писать «пригодность проверена; преимущество по затратам не установлено». Дважды выполнять одну задачу старым и новым процессом по умолчанию не требуется.

Полный набор тестов core, повтор restore и фазы 6–7 не запускать. Пробу не засчитывать автоматически в исторический ROLES-04: у него свои критерии и приёмка. После достаточных проверок завершить этот блок без нового цикла аудита.

## Как закончить

В `RESULT.md` дать один из выводов: «подходит как замена старого маршрута в проверенных границах», «подходит только при перечисленных изменениях», «не подходит», «недостаточно evidence». Основания — факты R01–R08; наличие красивого dashboard или сохранённого файла не критерий победы.

Отдельно назвать рекомендуемое действие: оставить нынешний маршрут, рассмотреть конкретные отдельные заимствования или рассмотреть замену маршрута. Для каждого предлагаемого изменения указать наблюдаемую пользу, затрагиваемые файлы/поведение и цену поддержки. Если польза не доказана, не рекомендовать внедрение ради новизны. Предложение заимствований не означает, что их реализация проверена этой пробой.

При положительном/условном выводе подготовить **предложение**, достаточное для отдельного решения о внедрении: какие существующие правила/файлы заменяются, какие остаются, как подключается каноническая память, как разрешается имя autopilot, как фиксируется/обновляется upstream и как вернуть прежний маршрут. Не реализовывать миграцию автоматически.

Проверить `git diff --check` и состав своего изменения. Коммиты создавать с явными путями; код пробной задачи фиксируется в её изолированной ветке/репозитории, отчёт оценки — отдельно в System. Не публиковать автоматически: локальная System уже содержит непубликованную историю, и push передаст её целиком. Если публикация будет отдельно разрешена, сначала проверить весь исходящий диапазон.

Если завершён только этап А, передать конкретного кандидата и условия выбора; общий статус — `awaiting-validation` живой части. После этапа Б — `awaiting-review` и пакет независимому приёмщику. Не ставить себе `done`/READY и не объявлять постоянную замену выполненной.

Короткий ответ исполнителя: результат, проверенные SHA, проверки, коммит/состояние сохранения, конкретный остаток, следующий разрешённый шаг. После достаточных доказательств не добавлять повторный общий аудит.
