# L04-04 — Конфликт записи не отличим от таймаута; failed блокирует watch

**What to build:** Повторная доставка уже сохранённого события завершается коррелированным терминальным подтверждением, а не пятью прогонами AI и ложным `failed`; терминальный `failed` не мешает `watch` достичь `idle`.
**Requirement IDs:** SC-09, SC-10, SC-17
**Blocked by:** —
**Status:** awaiting-review (F-04-2 и F-04-1 закрыты: flow-часть опубликована, живой повтор подтверждён)
**Перед началом работы:** Открой `D:\SystemTheBest\System`, проверь корень Git и текущие изменения.

## Контекст

Оба дефекта найдены живой проверкой L04-03, а не рассуждением.

### F-04-1 (high) — конфликт записи неотличим от таймаута

Writer идемпотентен по `event_id` + хешу содержимого; при другом содержимом того же
`event_id` он отвечает `409`. В живом цикле это выглядит так:

1. Отправитель шлёт событие; flow доходит до `write`; writer сохраняет запись.
2. Подтверждение теряется (сеть) либо событие доставлено повторно.
3. Шаг `write` получает `409`, `failureMode: retry_none` роняет run, flow-response
   не рождается, платформа отдаёт отправителю `408`.
4. Отправитель считает попытку повторяемой и повторяет. AI недетерминирован: тот же
   `event_id` даёт другие proposals, снова `409`.

Измерено: 5 живых прогонов на событие `evt_e33c5558759f` — 1 `SUCCEEDED` и 4 `FAILED`
(шаг `write`, `409`), очередь пришла к терминальному `failed`, память при этом
корректна и без дублей. То есть очередь подаёт ложный сигнал о неудаче и тратит
5 прогонов AI.

### F-04-2 (medium) — терминальный `failed` не даёт `watch` достичь `idle`

`undelivered` включает записи со статусом `failed`; при `--no-revive` ожидание всегда
заканчивается `failed`, поэтому `idle` недостижим. Измерено: `deadline` за 0.877 с при
малом окне и `failed` за 32.438 с при окне больше `reviveMs`. Hook запускает такой
worker на каждый commit, поэтому одна `failed`-запись удерживает lock ~32 с.

## Решение (2026-09-14)

Выбран **вариант 2** — отдельный терминальный статус `conflict`. Вариант 1 отклонён:
он подтверждал бы успех при фактически отвергнутых предложениях, то есть делал бы
расхождение невидимым. Дополнительно отклонены правка моста (`409` → `200` в
`bridge-server.js`) как ухудшение транспортного сигнала для всех клиентов и
согласование режима по заголовку как избыточная прослойка ради одного клиента.

Отдельного решения по F-04-2 не требовалось: правка самостоятельна и контракта не
меняет.

### Что сделано

- **F-04-2** — `queue-worker.js`: унаследованный терминальный `failed` исключён из
  `actionable` при `--no-revive`, поэтому не удерживает владение на `reviveMs`.
  Запись, отказавшая внутри текущего запуска, остаётся его собственным честным
  исходом `failed` (иначе ломается G12). Коммит `d2941f0`.
- **F-04-1, сторона отправителя** — `deliver.js`: `conflict` добавлен в терминальные
  подтверждения; `queue.js`: исход доставки сохраняется полем `outcome`;
  `queue-status.js`: поле видно в отчёте. Коммит `8c50847`.
- **F-04-1, flow-часть** — опубликована `2026-09-14` (`publishedVersionId
  Y8cdzG3eCuio0rFpXyoNV`): шаг `write` переведён на `failureMode: continue_4xx`,
  между ним и ответом вставлен `CODE`-шаг `classify_write`, `return_persisted`
  читает `classify_write['output'].body`. Экспорт пересобран с живого flow.
- **`docs/memory-contract.md`** — механизм flow описан рядом с третьим статусом
  (форма `{response,request}` против `{status,headers,body}`, отказ шага на всём,
  кроме 409 и подтверждённого `persisted`).

Классификатор намеренно построен на **форме** выхода, а не на тексте ошибки:
`409` — единственный отвергнутый writer'ом исход и превращается в коррелированный
`conflict`; подтверждённый `2xx` с `body.status === 'persisted'` — в `persisted`;
всё остальное (401, 5xx, транспорт, неожиданное тело) **бросает** ошибку шага, run
падает, платформа отдаёт отправителю `408`, и событие повторяется. Ни один
неизвестный исход не становится подтверждённым успехом.

### Почему flow-часть правилась через API, а не правкой файла

Коммитируемый `memory-event-to-writer.export.json` — регенерированный снимок живого
инстанса (`stripForExport`). Правка файла руками сломала бы это свойство, поэтому
изменения вносились в живой flow через API (`.local/services/l04-04-conflict-flow.cjs`)
и только затем пересобирались в экспорт. Правка идёт в два прохода: `probe` измеряет
форму выхода, `final` вносит рабочую форму и пересобирает экспорт.

## Живое подтверждение (2026-09-14)

### Форма результата HTTP-шага при продолжении после 409 — измерена, не предположена

`probe`-публикация (`PIyn8g2X1VdDhfvkzPT0i`, run `zeN6ktmMeOCwN6Sv5WBfP`) с шагом
`write` в режиме `continue_4xx` и `return_persisted`, возвращавшим `write['output']`
напрямую, дала на контролируемом событии ровно:

```json
{"response": {"status": 409, "body": {"error": "event_id already persisted with different content"}},
 "request":  {"body": {"event_id": "evt_l0404conflict1", "proposals": ["…3 proposals…"]}}}
```

Совпадает с исходником piece-http 0.11.19: `toFailsafeOutput`/`HttpError.errorMessage()`
отдают продолжение как `{response:{status,body},request:{body}}`, тогда как успешный
ответ той же ветви — `{status,headers,body}` **без** ключа `response`. Именно это
различие и использует `classify_write`; текст ошибки для классификации не нужен.

### Конфликт сделан детерминированным

Событие `evt_l0404conflict1` заранее сохранено через мост с `source:
'l04-04-conflict-probe'`, а flow шлёт `source: 'activepieces-flow'`. `proposalHash`
считается по содержимому вместе с `source`, поэтому совпадение хешей невозможно и
`409` гарантирован **одним** прогоном AI — без серии платных попыток «пока не
случится 409».

Ответ опубликованного flow (`Y8cdzG3eCuio0rFpXyoNV`) на это событие:

```json
{"event_id": "evt_l0404conflict1", "status": "conflict", "writer_status": 409,
 "reason": "writer rejected new proposals for an already persisted event_id",
 "writer_body": "{\"error\":\"event_id already persisted with different content\"}"}
```

### Ограниченный сценарий на настоящей очереди

Повторно доставлены три записи, ставшие терминальным `failed` при недоступном
Activepieces. Одна из них уже была сохранена, две — нет, поэтому один прогон
проверяет обе ветви сразу и на настоящих событиях, без выдуманных данных.

| Событие | Было | Стало | Исход |
|---|---|---|---|
| `evt_e33c5558759f` (уже сохранено) | `failed`, attempts 5 | `delivered` | `conflict` |
| `evt_9ff828f6e482` | `failed`, attempts 5 | `delivered` | `persisted` |
| `evt_0006d3a39705` | `failed`, attempts 5 | `delivered` | `persisted` |

- Весь сценарий — **17.925 с** на три события, то есть ~6 с на событие и **один
  прогон AI на событие**. Автоматической серии повторов «до 409» не возникло.
- Записи Activepieces (`flow_run`, настоящая БД, не API): три `SUCCEEDED` на версии
  `Y8cdzG3eCuio0rFpXyoNV` в 10:33:26 / 10:33:31 / 10:33:36 UTC, по 4.49 / 4.85 /
  6.08 с. Ни одного `FAILED` шага `write`.
- Для сравнения, до правки та же ветвь давала упавшие раны: `write` получал `409`,
  run падал, flow-response не рождался, отправитель повторял (8 ранов `FAILED`
  зафиксировано на двух прежних версиях; по `evt_e33c5558759f` — 1 `SUCCEEDED` и
  4 `FAILED`, замер L04-03).
- **Отвергнутые предложения не записаны.** У `evt_e33c5558759f` число записей в
  памяти до и после совпадает: по 1 в `decisions/writer-entries.md` и
  `gotchas/writer-entries.md`. Дублей нет ни у одного из трёх событий — у каждого
  ровно по одной записи в каждом файле.

Остановка автоповторов не означает, что отвергнутые предложения записаны: `conflict`
виден отдельно от `persisted` через поле `outcome`, и `queue-status.js` его
показывает.
