# L05-02 — Живой retrieval: как оба клиента реально получают контекст

**What to build:** Подтвердить на живом сервисе, что клиент действительно получает контекст: обязательные инструкции и HANDOFF читаются напрямую, Khoj вызывается для нового вопроса и возвращает источник, scope и статус, а текущий код читается из checkout. Для второго клиента, недоступного исполнителю, выдать один конкретный smoke-запрос и оставить проверку pending.
**Requirement IDs:** SC-05, SC-15, SC-16; R05.
**Blocked by:** L02-02, L02-03 (Khoj запущен, индекс настоящий).
**Status:** done — принят Astra в согласованном объёме блока фазы 5, дата фиксации 2026-09-14 (клиент Sonnet проверен живьём 2026-09-14; клиент GPT проверен Astra 2026-09-14 — результат зафиксирован ниже как внешнее доказательство; `done` поставлен приёмщиком, не исполнителем)
**Перед началом работы:** Открой `D:\SystemTheBest\System`, проверь корень Git и текущие изменения.

## Контекст

Инструкция в `start/SKILL.md` и разделе «Контекст и retrieval» `docs/system-workflow.md`
описывает *правило*: обязательные файлы читаются напрямую, Khoj используется для нового
существенного вопроса. Тикет проверяет, что это правило выполнимо на живом сервисе, и
измеряет фактический объём. Написанная инструкция не считается автоматическим вызовом
инструмента.

Итого: 3 запроса, 0 повторов, до 24 КБ прочитанного на задание. Кредиты не
расходуются (модели локальные), поэтому в метриках только объём и время.

**Передача результата работает:** по запросу о push верхним источником вернулась запись
`facts/github-remote.md` с подтверждённым scope `systemqwen` — то есть поиск находит
прежнее решение, и его можно передать вместе со ссылкой, датой и scope.

**Что показал живой прогон (не выдуманные проценты, а наблюдения):**

1. `search.js` возвращает `snippet`, `source`, `scope`, `status_hint`, `relevance` —
   **поля даты нет**. Дата видна только если она есть в теле записи или после чтения
   файла. Правило «учитывай дату находки» выполняется чтением источника, а не ответом
   поиска.
2. Запрос о сетевой среде вернул верхним `user-profile/work-patterns.md` с relevance
   `0.165` и scope `user` — ответа в проектной памяти нет: запись о fake-IP DNS лежит в
   персональной автоматической памяти, а не в `.claude/memory`. Две памяти — разные
   хранилища; Khoj индексирует только проектное.
3. Запрос о push нашёл `facts/github-remote.md`, где правило публикации записано в
   **прежней** формулировке («push выполняется только после проверки и явной командой»).
   Запись датирована 2026-08-19 и штатным путём не обновлялась; см. L05-01, где то же
   расхождение отмечено для `patterns/explicit-stop-gates.md`.
4. Итоговый исход `no-pattern`/`conflict`-цикл на поиск не влияет: индекс обновляется
   отдельной задачей, а поиск читает уже проиндексированное состояние.

Дефекты 1–3 не исправляются этим тикетом: `scripts/memory/**` и `.claude/memory/**`
вне его объёма. Они зафиксированы как ограничения.

## Проверка второго клиента — выполнена Astra 2026-09-14

Проверку выполнила **Astra в клиенте GPT**, а не исполнитель этого чата. Ниже — её
результат как внешнее доказательство; исполнитель тот же запрос не повторял и себе его
не приписывает.

**Что сделано:** прочитаны напрямую `CLAUDE.md` и `HANDOFF.md`, затем выполнен один запрос:

```

```

**Результат, как его передала Astra:**

- `ok:true`; актуальное решение вернулось из `decisions/writer-entries.md`, scope
  `systemqwen`, `status_hint: observation` — и **вернулось дважды**.
- Дополнительно найдена `facts/github-remote.md`, scope `systemqwen`, `confirmed`,
  дата `2026-08-19` — внутри snippet. **Отдельного поля даты у поиска нет**; это
  совпадает с наблюдением 1 из прогона на клиенте Sonnet.
- Astra применила **текущие обязательные инструкции**, а не старую запись памяти, то
  есть прямое чтение обязательных файлов перевесило устаревшую формулировку из
  `facts/github-remote.md`.

**Что это закрывает.** Критерий SC-05 для второго клиента: клиент читает обязательные
файлы напрямую, вызывает живой поиск, называет источник, scope и статус находки,
фиксирует отсутствие поля даты и расхождение с прежней записью памяти. Два клиента —
разные, и оба получили контекст живым путём.

**Побочное подтверждение.** Дублирование одной и той же записи в выдаче, отмеченное
ниже для клиента Sonnet, воспроизвелось и у второго клиента независимо. Это уже два
наблюдения на разных клиентах, а не свойство одного прогона; причина по-прежнему не
установлена и здесь не исследуется.
