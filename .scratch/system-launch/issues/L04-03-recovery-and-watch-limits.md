### Реальные пределы watch (измерено)

| Случай | Команда | Результат | Время |
|---|---|---|---|
| в очереди есть терминальный `failed` | `--watch --no-revive --max-idle-ms 5000` | `deadline`, `failed: 1` | 0.877 с |
| окно больше `reviveMs`, `--no-revive` | `--watch --no-revive --max-idle-ms 120000` | `failed`, `revives: 0` | 32.438 с |
| второй `watch` при занятом lock | `--watch --no-revive --max-idle-ms 5000` | `busy` | 0.200 с |

- `reviveMs = min(backoff_ms · 2^retries_max, 60000)` = **32 000 мс** при поставляемом
  конфиге. `--no-revive` не оживляет `failed`.
- `idle` достигается только когда нет недоставленных записей; терминальный `failed`
  не даёт его достичь никогда.
- Lock берёт только `watch`; одиночный `drain` его не берёт и не блокируется.
- **Событие с истёкшим окном не доставляется само.** Доставку после длительного
  простоя без нового commit закрывает только явный повторный запуск (`queue-worker.js`)
  или локальный планировщик. Бессрочный оркестратор не добавлялся.

## Найденные живые дефекты

- **F-04-1 (high):** повторная доставка уже сохранённого события не может завершиться
  успешно. 5 живых прогонов: 1 `SUCCEEDED` + 4 `FAILED` с шагом `write` и `HTTP 409
  "event_id already persisted with different content"`. AI недетерминирован, writer по
  контракту отказывает, run падает, платформа отдаёт 408, отправитель повторяет.
  Память при этом корректна и без дублей — дефект в наблюдаемости и в расходе.
  → [L04-04](L04-04-conflict-ack.md)
- **F-04-2 (medium):** терминальный `failed` держит `watch` ~32 с и удерживает lock.
  → [L04-04](L04-04-conflict-ack.md)
