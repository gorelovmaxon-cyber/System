# L06-03 — Restore в отдельную среду и сверка целостности

**What to build:** Восстановить резерв в отдельный каталог, сверить целостность памяти, состояние очереди и восстановление производного индекса. Восстановление AP flow/данных — только по проверенному экспорту/резерву. Не удалять единственную рабочую БД/volume для проверки.
**Requirement IDs:** SC-17; R13.
**Blocked by:** SC-17, L06-01 (для подтверждения на втором ПК).
**Status:** **awaiting-review** — восстановление в отдельный каталог и сверка целостности выполнены **трижды**: локально 2026-09-14 (19 файлов из пакета), на втором ПК 2026-09-15 против пакета `second-pc-20260915-191058` (28/28 записей манифеста, 18/18 файлов памяти по sha256), и **на втором ПК 2026-09-23 из живого состояния после L06-04** (22/22 файла, sha256 100% match, локальный поиск `evt_9861052a0dfe` найден с сохранением кириллицы, рабочая память не изменялась). Критерий «подтверждение на втором ПК» выполнен; актуальность памяти включая writer-entries подтверждена. Остаётся недоступной одна часть — **восстановление AP flow/volume** (Docker отсутствует, volume backup по `D:`/`E:` не найден). [Evidence 2026-09-23](../evidence/l06-03-restore-drill-second-pc-2026-09-23.json). `done` ставит приёмщик.
**Перед началом работы:** Открой `D:\SystemTheBest\System`, проверь корень Git и текущие изменения; рабочую БД/volume не трогать.

## Контекст

`docs/system-operations.md` разделял: память — источник истины в Git, Khoj-индекс —
производный и перестраивается, `.local/` и секреты — локальные и в Git не приходят. В
прошлых фазах строка «живой flow/index restore невозможен из-за отсутствия сервисов»
относилась к среде без Khoj и Docker. Сейчас Khoj живой, поэтому локальная часть drill
впервые выполнима без второго ПК; AP/volume-часть — нет, потому что Docker на этой
машине не запущен.

Два содержательных вывода, а не только «всё зелёное»:

1. **Восстановление из этого резерва не возвращает текущее состояние памяти.** Совпадает
   с ожиданием (память переносится Git, а не резервом), но означает прямо: слепое
   восстановление резерва поверх рабочей копии откатило бы память на 2026-09-13. Резерв
   не подменяет Git.
2. **Durable-очередь в пакетах локального состояния не сохраняется.** В проверенном
   пакете есть производные журналы (`tasks.jsonl`, `processed.jsonl`), но нет
   `queue/events.jsonl`. Живая очередь на этой машине на 2026-09-14 содержит 25 событий
   (`delivered` 23, `failed` 2) — именно столько коммитов прошло через hook, по одному
   событию на коммит; сырые 134 строки журнала это история переходов, а не накопление.
   Если событие не доставлено до переноса, из такого резерва оно не вернётся, а
   не доставлены сейчас ровно два — коммиты `c46ba83` и `3647a1d`. Это ограничение
   резерва, а не дефект восстановления; отдельным тикетом здесь не оформляется.

## Что не выполнено и почему

- **Восстановление AP flow/данных из резерва.** Пакет существует
  (`transfer-backups/docker-volumes-20260913/activepieces-{postgres,redis,cache}.tgz`), но
  Docker на этой машине не запущен (`docker ps` → демон недоступен). Разворачивать
  volumes вслепую и тем более удалять рабочий volume для проверки запрещено заданием.
- **Подтверждение на втором ПК.** Требует доступа (L06-01).
- **Повторная перестройка индекса.** Не выполнялась намеренно: это повтор проверки фазы 5
  (перестройка индекса из памяти там подтверждена живьём), а прогон против живого Khoj
  изменил бы рабочий индекс, ничего не добавив к проверке восстановления. Граница названа
  прямо, а не замолчана.

  `services/activepieces/flows/memory-event-to-writer.export.json` присутствуют;
  значения секретов не выводились и не публиковались. Экспорт ранее прошёл round-trip в

- В `.env` присутствуют все обязательные для compose параметры; отсутствует только
  необязательный `AP_OPENAI_API_KEY`. AI connection всё равно создаётся локально в UI.
  После импорта остаются обязательными webhook/`WEBHOOK_ID`, analyze endpoint и локальный
  bridge token.

  этом ПК. Поэтому restore volume нельзя начинать даже после готовности Docker, пока

- `integrations.activepieces.webhook_url` остаётся заглушкой до импорта flow и получения

- Это только подготовка; запуск стека и восстановление AP не проверены.

## Ограничения

- Проверка выполнена в отдельном каталоге на каждой машине; живая память, живой индекс и
  рабочая БД ни на одной из них не изменялись.
- Единственный рабочий volume не удалялся и не пересоздавался.
- Старая настоящая память (если пользователь захочет её перенести) требует отдельной
  инвентаризации источников, проверки коллизий, резерва и плана объединения; разрешение
  на уничтожение старой копии не предполагается.
- Восстановление AP-данных остаётся недостижимым до завершения Windows recovery,
  готовности Docker и предоставления отсутствующего volume backup. Импорт репозиторного
  flow без старых volumes не должен называться восстановлением прежних данных.
