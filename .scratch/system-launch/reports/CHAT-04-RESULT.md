## L04-03 — восстановление и реальные пределы watch

### Обрыв до acknowledgement и перезапуск получателя

Событие `evt_2cb2c33b2cbf` (коммит `ec847e2`):

1. Мост остановлен, `health` → `000`.
2. `queue-worker.js` — **31.075 с**, ответ `HTTP 408: {}`, запись осталась
   `pending`, `attempts: 1`, назначен повтор. Терминального `failed` нет.
3. Мост перезапущен, `health` → `200`.
4. `queue-worker.js` — **8.048 с**, `delivered`.
5. Память: два предложения одного `event_id`, дублей нет.

Это живое подтверждение правки L04-00: отправитель дождался детерминированного
ответа платформы и оставил событие повторяемым, а не терминальным.

### Отказ Khoj с восстановлением

1. `indexer.reindex_url` → закрытый порт.
2. `indexer.js --run` → `status: failed`, `reason: "fetch failed"`, `attempts: 1`.
   **Ложного `indexed` нет**, память сохранена.
3. `reindex_url` восстановлен; `indexer.js --run` → `indexed`, `attempts: 2`;
   запись находится поиском.

### Реальные пределы watch (измерено)

| Случай | Результат | Время |
|---|---|---|
| в очереди терминальный `failed`, окно 5 с | `deadline` | 0.877 с |
| окно 120 с, `--no-revive` | `failed`, `revives: 0` | 32.438 с |
| второй `watch` при занятом lock | `busy` | 0.200 с |

- `reviveMs = min(backoff_ms · 2^retries_max, 60000)` = 32 000 мс при поставляемом
  конфиге.
- `idle` достигается только при отсутствии недоставленных записей; терминальный
  `failed` не даёт достичь его никогда.
- Lock берёт только `watch`; одиночный `drain` не блокируется.
- **Событие с истёкшим окном само не доставляется.** Доставку после длительного
  простоя без нового commit закрывает только явный повторный запуск
  (`queue-worker.js`) или локальный планировщик. Бессрочный оркестратор не
  добавлялся — как и требует задание.

## Найденный живой дефект → L04-04

**F-04-1 (high).** Повторная доставка уже сохранённого события не может завершиться
успешно. Writer идемпотентен по `event_id` + хешу содержимого и при другом
содержимом отвечает `409`; шаг `write` роняет run, flow-response не рождается,
платформа отдаёт отправителю `408`, отправитель повторяет. AI недетерминирован, и
тот же `event_id` даёт другие proposals — снова `409`.

Измерено: 5 живых прогонов на `evt_e33c5558759f` — 1 `SUCCEEDED` и 4 `FAILED`
(шаг `write`, `409 "event_id already persisted with different content"`), очередь
пришла к терминальному `failed`, память корректна и без дублей. То есть при
потерянном подтверждении очередь подаёт ложный сигнал о неудаче и тратит 5
прогонов AI.

**F-04-2 (medium).** Терминальный `failed` не даёт `watch --no-revive` достичь
`idle` и удерживает lock ~32 с на каждый commit.

Обе вынесены в [L04-04](../issues/L04-04-conflict-ack.md). F-04-1 меняет контракт
подтверждения (сейчас терминальны только `persisted` и `no-pattern`), поэтому
исполнитель остановился и не правил его самовольно.

## L04-04 — закрытие (2026-09-14)

**Решение.** Выбран вариант 2: третий терминальный статус `conflict`. Вариант 1
(отвечать `persisted` при отвергнутых предложениях) отклонён — он делал бы расхождение
невидимым. Правка моста (`409` → `200`) отклонена как ухудшение транспортного сигнала
для всех клиентов.

**F-04-2** (`d2941f0`). Унаследованный терминальный `failed` исключён из `actionable`
при `--no-revive`, поэтому не удерживает владение на `reviveMs`. Запись, отказавшая
внутри текущего запуска, остаётся его собственным честным исходом `failed`.

**F-04-1, сторона отправителя** (`8c50847`). `deliver.js` считает `conflict`
терминальным подтверждением; `queue.js` сохраняет исход доставки полем `outcome`;
`queue-status.js` показывает его.

**F-04-1, flow-часть** (опубликована 2026-09-14, `publishedVersionId
Y8cdzG3eCuio0rFpXyoNV`). Шаг `write` переведён на `failureMode: continue_4xx`, между
ним и ответом вставлен `CODE`-шаг `classify_write`, `return_persisted` читает его
выход. Экспорт пересобран с живого flow.

Форма результата HTTP-шага при продолжении после 4xx **измерена**, а не взята из
документации: probe-публикация на контролируемом событии дала ровно
`{response:{status:409,body:{error:…}},request:{body:{…}}}`, тогда как успех —
`{status,headers,body}` без ключа `response`. Классификатор опирается на это различие.
Всё, кроме `409` и подтверждённого `persisted` (401, 5xx, транспорт, неожиданное тело),
**бросает** ошибку шага: run падает, отправитель получает `408` и повторяет. Ни один
неизвестный исход не становится подтверждённым успехом.

**Живой повтор** на настоящей очереди, 17.925 с на три события (один прогон AI на
событие):

| Событие | Исход | Память |
|---|---|---|
| `evt_e33c5558759f` (уже сохранено) | `delivered`, `outcome=conflict` | без изменений (1+1) |
| `evt_9ff828f6e482` | `delivered`, `outcome=persisted` | по одной записи |
| `evt_0006d3a39705` | `delivered`, `outcome=persisted` | по одной записи |

Записи Activepieces: три `SUCCEEDED` на `Y8cdzG3eCuio0rFpXyoNV` (4.49 / 4.85 / 6.08 с),
ни одного `FAILED` шага `write`; до правки та же ветвь давала 8 упавших ранов. Дублей
нет; отклонённые предложения не записаны. Остановка автоповторов не выдаётся за
успешное сохранение — конфликт виден отдельно.
