### Три дефекта среды, найденных на этой машине

Все три — про окружение, а не про код системы; два первых уже описаны в runbook.

1. **`USE_EMBEDDED_DB=true` на Windows непригоден** — ветка релиза рассчитывает на
   Unix-сокет. Обойдено `run-local.py` (уже задокументировано).
2. **В колесе pgserver 0.1.4 нет базы часовых поясов** — Django падает на
   `SET TimeZone='UTC'`. Обойдено `run-local.py` (уже задокументировано).
3. **Протокол HuggingFace Xet рвёт загрузку моделей** — `huggingface_hub` 0.36.2 через
   `xet_get` даёт `ConnectionError: Network error:`, из-за чего индекс не строился:
   `/api/update` → `500 Failed to update content index`, `/api/search` → `timeout` с
   уходом в локальный fallback. Лечится `HF_HUB_DISABLE_XET=1`; дополнительно задан
   `NO_PROXY=*`, потому что системный прокси WinINET (`socks=127.0.0.1:10808`,
   `ProxyEnable=1`) наследуется `pip` и даёт
   `ERROR: Could not install packages due to an OSError: Missing dependencies for SOCKS
   support`. Обе переменные дописаны в `services/khoj/config.local.env` — `run-local.py`
   переносит ключи этого файла в окружение процесса. После этого модель скачалась за
   3.5 с, индекс собрался, `500` и `timeout` исчезли. Runbook обновлён.

### Обмен изменениями через Git и конфликт (L06-02, шаг 7)

Обмен шёл через настоящий `origin`, а не между двумя каталогами на диске. Встречную
сторону исполнял временный клон вне репозитория
(`E:\SystemTheBest\transfer-backups\roundtrip-peer-20260915-194355`, после проверки удалён).

| Шаг | Коммит | Результат |
|---|---|---|
| старт | `6d08ca4` | локальный HEAD и `origin/master` совпадали |
| А: второй ПК → origin | `d125695` | push `6d08ca4..d125695` |
| А: приём встречной копией | `d125695` | `git log --left-right HEAD...origin/master` показал одно расхождение; `pull --ff-only` прошёл |
| Б: встречная копия → origin | `bad97cb` | push `d125695..bad97cb` |
| Б: независимая правка второго ПК | `37df900` | обе стороны ушли от `d125695` **в одну и ту же строку** |
| слияние | `a1692e9` | `CONFLICT (content)` в двух местах, разрешён вручную |
| публикация слияния | `a1692e9` | push fast-forward `bad97cb..a1692e9` |
| приём слияния | `a1692e9` | `pull --ff-only` прошёл |

Merge-commit `a1692e9` имеет двух родителей (`37df900`, `bad97cb`). В разрешённом файле
присутствуют **обе** правки; ни одна не выбрана за счёт другой. Force push, `reset --hard`
и `clean -f` не применялись ни на одном шаге — проверено в том числе по `git reflog`.

**Граница.** Встречная копия снята с `origin` на этой же машине и **ноутбуком не
является**. Проверено: механика обмена и разрешения конфликта через настоящий remote.
Не проверено: участие настоящего первого ПК — его доступ к `origin`, его `git status` и
его локальная привязка. Временный клон после проверки удалён, чтобы на машине осталась
одна каноническая копия памяти.

Оно построено так, чтобы ноутбуку хватило одной сессии и чтения одного файла:

1. снять состояние до изменений (`remote`, ветка, HEAD, `hooksPath`, `git status`,
   `git log --left-right HEAD...origin/master`);
2. сделать `git pull --no-rebase origin master` — этим подтверждается направление
   **второй ПК → ноутбук**, потому что файл задания добавлен вторым ПК и содержит отметку
   `SYSTEM2-EXCHANGE-NCLRFDV`;
3. заполнить в том же файле «слот первого ПК» фактическими значениями;
4. закоммитить и запушить **без force** — этим подтверждается направление
   **ноутбук → второй ПК**; доказательство — `git ls-remote origin refs/heads/master`,
   равный `git log -1`;
5. прислать перечисленные выводы, включая `queue-status.js`.

Запреты продублированы в самом задании: `push --force`, `reset --hard`, `clean -f`,
`pull --rebase` и удаление `.local/`. Отдельно оговорено: коммит ноутбука породит событие в
его очереди, и если стек Activepieces там не запущен, событие останется `failed` — это
ожидаемо; массовый `--redeliver` не запускать, это отдельное решение пользователя.
После ответа ноутбука второй ПК делает свой `pull` и сверяет отметку. **До этого обмен
подтверждён на одну сторону, и это в отчёте сказано прямо.**

- **25 событий = 25 коммитов**, по одному на коммит. Зацикливания и дублей нет: у каждого

- **6 из 25 (24%) — самонаведённые.** Это коммиты `memory: …`, которые создаёт сам writer,
  и которые затем снова проходят через тот же hook. Все 6 доставлены. Цикл «запись памяти →
  коммит → событие» существует по устройству системы и **сам не замыкается** — измерено
  ниже на продолжении цепочки; на момент этой диагностики он был остановлен вручную
  прекращением коммитов, а не механизмом.
- **19 из 25 — рабочие коммиты** (`L04-xx`, `L05-xx`, `L06-01`): 17 доставлено, 2 упали.

**Незавершённых ровно 2 события** (на момент диагностики) — это два последних коммита,
созданных уже при неработающем bridge:

| Событие | Коммит | Ошибка | Попыток |
|---|---|---|---|
| `evt_e15b1df50571` | `c46ba83` — передача фазы 5 | `fetch failed` | 5 |

именно недоступный bridge (`fetch failed`), а не дефект очереди. Массового накопления нет,
поэтому «расход на разбор очереди» сводится к повторной доставке двух событий, а не сотни.

Автоматического повтора не будет: post-commit hook запускает

  случаях из трёх коммит памяти порождает новую запись, которая сама становится коммитом
  памяти. Две подряд записи (`c170961b`, затем `d43a495`) говорят об одном и том же факте
  разными словами — цикл не только не замыкается, но и вырождается в пересказ. До сих пор
  его останавливало ручное прекращение коммитов, а не механизм.
- **Индексация догнана:** новые задачи `pending` → `indexer.js --run` → все **58**
  задач `indexed`. Поиск по записи диагностики возвращает её первой строкой
  (`ok:true`).

Практический вывод: правка «коммит, которым фиксируется уже обработанная память, не порождает
запись» нужна не для экономии одного вызова, а чтобы цикл вообще был ограничен. Записи-пересказы
(`decisions/writer-entries.md`, `patterns/writer-entries.md`) оставались незакоммиченными —
коммитить их значило оплатить следующую итерацию. **Правка выполнена 2026-09-15; разбор
оставшихся записей и публикация — в разделе «Защита от самоповторов» ниже.**

## Защита от самоповторов выполнена, 2026-09-15

Коммит, которым фиксируется уже обработанная память, больше не уходит в очередь, поэтому не
вызывает AI и не порождает запись о самом себе. Публикация: код и evidence — `1a36ad5`,
записи памяти — `41c9645`; точка публикации — **`634c039`**: сразу после push remote
`origin/master` был равен ей, ahead/behind `0/0` (`git rev-parse origin/master`,
`git ls-remote`). Всё добавленное после неё — документные коммиты передачи, код и память они
не меняют.

### Как признак устроен

Признак считается по проверяемым происхождению и составу изменений, а не по тексту сообщения:

| Условие | Что проверяется |
|---|---|
| Состав | diff целиком (не усечённый для события) изменяет только файлы внутри memory root; ничего не удаляется, не переименовывается, не является бинарным |
| Происхождение | каждый изменённый файл значится в `written_files` завершённой (`persisted`) записи журнала writer |
| Завершённость | каждый добавленный `event_id` уже имеет статус `persisted` |

Любое сомнение — ошибка разбора, недоступный журнал, кавычки в пути, неизвестный заголовок
секции — означает **обычный захват**, а не пропуск. Недостаток признаков не отбрасывает
событие. Сообщение `memory: …` само по себе ничего не решает: коммит с таким префиксом и
изменениями кода захватывается как обычно.

### Найденная ошибка и её цена

Первая редакция классификатора не снимала префиксы `a/`/`b/`, которые `git diff` ставит перед
путями. Путь читался как `b/.claude/memory/...`, не совпадал с memory root, и **ни один коммит
памяти не опознавался**. Это установлено прогоном по реальной истории
(`r08-fixation-classify-history.cjs`), а не рассуждением: на одних и тех же 157 коммитах
до правки — 0 распознанных, после — 8.

### Проверка на реальной истории (159 коммитов)

Прогон после публикации, поэтому в выборку попали и оба новых коммита — это и есть проверка
на живых данных, а не на синтетике. Результат сохранён:
[r08-fixation-classify-history-results.txt](../evidence/r08-fixation-classify-history-results.txt).
