## Цель и контракт
Пользователь открывает проект и вызывает start с задачей «Сделай сайт мороженого».
После однократного подключения клиент выполняет: вход → память → рекомендации →
grill → согласованная спецификация → тикеты → остановка перед передачей Sonnet/Sol →
исполнение переданного блока → независимая приёмка → сохранение полезного опыта.
Новый вызов start продолжает сохранённый этап, а не повторяет интервью с нуля.

Одна общая копия System на ПК, проекты отдельно. Не копировать SystemTheBest,
runtime, backups или всю System в каждый проект. В проекте — минимальный адаптер,
собственные правила и HANDOFF. Привязка local_paths сама по себе не устанавливает команду.

«Автоматически» = работающий агент следует контракту без повторных напоминаний
о поиске, сохранении и передаче. Это не daemon, не чтение всех чатов, не бессрочный
наблюдатель. Другого исполнителя открывает пользователь; runner не создавать.
Вопросы grill и согласование спецификации остаются частью одного маршрута.
Нет подключения команды в клиенте — сначала однократный setup; не обещать, что
неизвестная slash-команда сама загрузит файлы из другой папки.

## Требования SW
- SW-R1: однократное безопасное подключение реального проекта; доступность start в выбранном клиенте.
- SW-R2: весь планирующий маршрут из одного вызова, рекомендации до реализации, гейт передачи.
- SW-R3: опыт прошлых сайтов с источниками и границами scope; живой Khoj и проверенный fallback.
- SW-R4: автоматическое сохранение подтверждённых знаний на границах работы, без дублей и ложного synced/indexed.
- SW-R5: продолжение в новой сессии без старой переписки и сквозная независимая приёмка.

22 файла памяти в restore. Не повторять restore, установку Docker и исторический аудит.

init-project.js добавляет секции CLAUDE/HANDOFF; новый registry пишет локально;
для уже известного ID не заполняет отсутствующий local_paths.
Проектный поиск допускает собственный scope и user, не память всех клиентов.
auto-learn требует вопрос перед сохранением и ссылается на старый capture;
to-spec требует внешний issue tracker. Эти контракты нужно согласовать адресно.
В указанной папке сайта каталог существует, но при точечной проверке не найден

Khoj ранее запускался; текущее состояние нужно проверить, не переустанавливать.

## Задание одному исполнителю
Работай из E:\\SystemTheBest\\System. Прочитай CLAUDE.md, актуальный HANDOFF,
docs/system-workflow.md, docs/planner-brief.md и свой тикет. Последовательно
выполни разрешённый блок SW-01…05; без дополнительных агентов и без реализации
пользовательского сайта целиком. Для сквозной пробы достаточно одного маленького
тикета в изолированном демонстрационном проекте и реальной передачи между сессиями.
Глобальные настройки клиента не менять молча. Выясни используемый клиент и
поддерживаемый механизм подключения до реализации адаптера. Если для него нужны
новые права или установка — запроси только недостающее; независимую работу продолжай.

Тикет = scoped-коммит с проверками. Сохраняй чужие изменения, особенно
.scratch/system-launch/issues/L06-04-FIXES.md. Обычный push после проверки всего
исходящего диапазона и remote; без force/reset/clean/автоматического stash.
Финальную приёмку себе не ставь. Внешний issue tracker, платные API, массовый импорт
чужих проектов/чатов, Docker/AP, Figma и новый оркестратор не входят в задачу.
Не менять writer/locks/queue без воспроизведённой необходимости.
Полный набор нужен при изменении общих primitives; иначе целевые регрессии и один smoke.

сценарий, включая сохранение и продолжение, а не только наличие файлов навыков.
