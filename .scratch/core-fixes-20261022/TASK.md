## C01 — производное состояние indexed

Воспроизвести: persisted с index_error → успешный reconcile/run в изолированной среде → indexed:true → повтор того же writeProposal. Проверить состояние writer-log и задач, а не только возврат API. Сервис Khoj подменять локальной фикстурой.

Исправление должно оставлять indexed производным от задач на текущие ревизии всех written_files. Успешный retry не должен поверх актуального агрегата записывать устаревший previous/indexed:false. При подтверждённом успехе очистить неактуальный index_error; учесть ранний выход syncAggregate при уже совпадающем indexed, а не просто добавить поле в недостижимый append.

При ошибке refresh/append не выдавать подтверждённый успех индексации и не скрывать ошибку. Различать index_error постановки/индекса и актуальную ошибку доставки; не стирать действующую диагностику без основания. Сохранить идемпотентность payload, поддержку legacy hashes, locks и crash recovery.

Приёмка: указанный регрессионный сценарий проходит; повтор не добавляет память; изменение ревизии/отсутствующая задача снимают indexed; сбой индекса не отменяет persisted и не превращается в indexed:true.

## C03 — явное закрытие проектного journal

Это расширение действующего контракта. Сохранить `pending` и `persisted`; добавить явное терминальное закрытие без ложного persisted. Команда `close` принимает ID, disposition `resolved|dismissed|superseded`, непустую причину и проверяемую ссылку/описание основания; точный CLI документировать. Закрытый вопрос не переносится автоматически в каноническую память.

Закрывать допускается pending. Для superseded требуется существующая correction того же project_id, которая действительно ссылается на закрываемый ID. Автоматически изменять предыдущую запись внутри capture не нужно: явное закрытие избегает недоказанной двухфайловой атомарности. Причина dismissed/resolved не должна превращать observation в confirmed. Persisted не понижать и не перезаписывать через close; mark для закрытой записи должен явно отказывать. Точный повтор закрытия идемпотентен; несовместимый повтор — явный конфликт.

Изменения состояния сериализовать штатным локальным механизмом блокировки подходящего ресурса, с безопасной заменой файла; не вводить новую систему locks. Проверить конкурирующие close/mark и обрыв записи, не допустить повреждения JSON или потери уже завершённого перехода. Существующие источники/summary/verification сохранять. Не закрывать реальные pending пользователя во время тестов.

Коллизия регистра: сохранить старые ID и регистрозависимое сравнение payload. Не объединять case-sensitive строки через toLowerCase. Предусмотреть обратносуместимый выбор нового ID при коллизии нормализованного старого ID только из-за регистра summary: проверить старую точную запись первым делом, затем детерминированный case-sensitive ID с отдельным namespace; существующие ID не переименовывать. Изменение source/verification для того же точного summary по-прежнему конфликт, а не обход идемпотентности. Описать порядок lookup и проверить параллельное создание, повтор каждой версии и коррекции по прежним ID.

Приёмка: вопрос после явного закрытия исчезает из pending без writer-записи; заменённое решение закрывается с валидной correction; отклонённое observation сохраняется как история; неверный scope/ссылка/переход отвергается без частичного изменения. Старые записи и capture/mark остаются совместимы. Регистрозависимые payload не смешиваются.
