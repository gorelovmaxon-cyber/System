## R1 · P1 · Потеря предложения с тем же statement и другим scope

`scripts/memory/writer.js:140` — entryPresent проверяет только подстроку event_id и statement. В одном событии передать два предложения категории facts с statement SAME_TEXT, но scope A и B. Ответ persisted, запись B отсутствует. Отличающиеся evidence/status/source также не участвуют в идентичности предложения.

Вернуть FIX-01: определить устойчивую идентичность каждого предложения с учётом значимых полей/позиции и точной идентичности события. Сохранять весь обещанный набор, не смешивать знания разных scopes. Проверить повтор, частичное восстановление и одинаковые statement с разными metadata; отдельно определить поведение полностью одинаковых предложений.

## R2 · P1 · Положительный путь Khoj по-прежнему раскрывает B в проекте A

`scripts/memory/search.js:166` — entries(text)[0] задаёт scope всего файла, а snippet берётся из ответа сервиса. Создать user-запись, затем PRIVATE_B со scope B в том же файле. Вернуть от тестового сервиса source `facts/writer-entries.md` и snippet PRIVATE_B. Вызов searchKhoj(PRIVATE_B,A,{force:true}) возвращает ok:true, PRIVATE_B с меткой scope:user.

Это нарушение обязательной изоляции, а не допустимое «задокументированное ограничение». Живой сервис для проверки этой ветки локального кода не нужен. Исправить FIX-03: выдавать только выдержки с проверенным scope соответствующей записи; не доверять произвольному snippet сервиса и не присваивать чужому результату scope запрашивающего проекта.

Смежная находка при подборе входа: source `.claude/memory/facts/writer-entries.md` текущий relativeSource преобразует в `.claude/memory/claude/memory/facts/writer-entries.md`, после чего файл не читается и берётся текст сервиса. В окончательном R2 использован более простой `facts/...`, поэтому ошибка изоляции не зависит от этой проблемы нормализации. Добавить самостоятельные проверки разных разрешённых форм source, отсутствующего файла и отклонения неизвестного scope.

## R3 · P1 · CRLF снова открывает всю проектную память в fallback

`scripts/memory/search.js:49` — разделитель рассчитан только на LF. После обычной замены LF→CRLF файл с user и B распознаётся одной записью без metadata. Поиск PRIVATE_B из A возвращает весь фрагмент с scope:unknown, включая B.

В текущем Git `core.autocrlf=true`; это существенный сценарий для Windows/переноса, а не искусственный некорректный формат. Нормализовать окончания строк/корректно разбирать CRLF и смешанный ввод. Отсутствующая или нераспознанная metadata не должна автоматически открывать весь много-записный файл любому проекту. Проверить совместимость старых ручных файлов по явному контракту.

## R4 · P2 · CRLF нарушает идемпотентность writer

`scripts/memory/writer.js:131` и `writer.js:135` — после LF→CRLF entryStatement не находит `\n## ` и entryPresent не узнаёт прежнее предложение. Повтор event_id/того же содержания добавляет вторую копию; обе записи присутствуют в файле.

Вернуть FIX-01: единый устойчивый разбор записей writer/search, включая окончания строк. Проверить сохранение → преобразование CRLF → повтор и восстановление после частичного завершения.

## R5 · P1 · Живая блокировка крадётся, затем её удаляет другой владелец

`scripts/memory/writer.js:65` и `writer.js:61`.

В дочернем процессе остановить выполнение после реального openSync(memory.lock,'wx'), до writeOwner. Пока владелец жив, второй процесс вызывает acquireLock. Через 50 мс он удаляет пустой файл и получает собственную блокировку. Возобновить первый: он дописывает owner в свой старый fd, тоже возвращает успешный acquireLock и при release удаляет текущий lock второго процесса.

Воспроизведено: два живых держателя, release первого удаляет блокировку второго. Таймаут 50 мс не является доказательством смерти процесса; nonce записан, но не проверяется при освобождении. Проверка liveness только после готового owner недостаточна.

Вернуть FIX-02: закрыть окно публикации владельца и безопасный захват/освобождение; не удалять lock другого поколения. Учесть конкурентное восстановление осиротевшего lock, ошибки доступа при проверке pid, смену владельца между чтениями и отсутствие файла после гонки. Увеличение grace-периода само по себе дефект не исправляет.

## R6 · P1 · Конфликт одного event_id проверяется до блокировки и пропускается

`scripts/memory/writer.js:183` и `writer.js:194`.

Дочерний процесс проверяет журнал, не находит event_id и приостанавливается перед созданием lock. Родитель сохраняет PARENT_CONTENT с тем же event_id и освобождает lock. После возобновления ребёнок сохраняет CHILD_CONTENT: журнал под блокировкой не перечитывается. Оба возвращают persisted, в памяти два разных содержания под одним событием вместо CONFLICT.

Вернуть FIX-01/02: решения о конфликте/повторе и изменение журналов должны быть согласованы внутри защищённой операции. Проверить разные предложения одного event_id в отдельных процессах и точный повтор. Обычный последовательный тест 409 не покрывает эту гонку.

## Недостатки доказательств FIX-04 и WRITER-REVIEW

1. «Kill mid-save» с задержками 0/10/30/60 мс не доказывает прохождение конкретных аварийных точек: ребёнок мог ещё не начать запись или уже завершиться. Добавить handshake/детерминированные точки до/после intent, rename и persisted-журнала, с завершением реального тестового writer. fix-04-crash.cjs самостоятельно записывает intent и делает exit(1); это полезная модель состояния, но не доказательство остановки настоящего writer в этой точке.
2. В WRITER-REVIEW указано «после ответа, при queueIndex», хотя код вызывает queueIndex до persisted-log и ответа. Исправить фактический порядок и не описывать будущее восстановление FIX-07 как уже работающее.
3. Тест с локальным Git remote не отключает remote и не создаёт конфликт: A оставляет незакоммиченную facts, B коммитит другую категорию decisions, затем pull проходит без конфликтующих изменений. Он показывает сохранение разных файлов и различие persisted/synced; он не доказывает заявленные offline/divergence/conflict-restore. Добавить нужные сценарии либо сузить утверждения, оставив остальное на соответствующую приёмку.
4. fsync временного файла — улучшение. Но этим и process-kill тестами не доказана общая гарантия при отказе питания для памяти плюс журнала: writer-log использует append без fsync, rename/метаданные каталога и гарантии выбранной ФС отдельно не обоснованы. Уточнить контракт уровня гарантии, не объявлять реальный power-loss тест выполненным. В этом ревью отказ питания не воспроизводился.
5. Показатель reproduced:false в старом harness сам по себе не подтверждает исправление: harness ловит любое исключение. Нужны позитивные регрессионные ожидания и разбор причины отрицательного результата.
