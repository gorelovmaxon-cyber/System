## Воспроизведение

Актуальная команда из корня `D:\SystemTheBest\System`: `node .scratch/system-remediation/evidence/core-audit.cjs`.

Исторический запуск выполнялся из `D:\SystemTheBest\audit`; переносимая копия сценариев и отчёта теперь находится в `.scratch/system-remediation/evidence/` внутри репозитория. В этой копии корень кода определяется относительно расположения harness. Исходный JSON — исторические результаты, его абсолютные TEMP-пути не являются настройками системы. Перед повторным запуском сохрани исходный JSON отдельно: harness пишет результат в соседний `core-audit-results.json`.

Сценарии: [core-audit.cjs](core-audit.cjs). Машинный результат: [core-audit-results.json](core-audit-results.json).
Код выхода 0 означает, что все заявленные дефекты воспроизвелись и контрольные проверки прошли; это НЕ успешная приёмка продукта.

Каждый сценарий создаёт отдельный синтетический корень System2 в пользовательском TEMP и устанавливает SYSTEM2_ROOT только внутри процесса теста. Реальная память и конфигурация репозитория не изменяются. Сценарии с аварийными журналами моделируют состояние диска после сбоя, а не фактическое отключение питания. HTTP-ответы индекса подменяются в процессе; никакие запросы к настоящему Khoj не выполняются. Bridge проверяется на временном localhost-порту с тестовым токеном. Все созданные данные оставлены для разбора; их путь записан в JSON.

## Дефекты

P1 — исправить до подключения к реальным рабочим данным; P2 — исправить для надёжной эксплуатации.

### F01 · P1 · Writer теряет второе предложение в той же категории (SC-08)

Источник: `scripts/memory/writer.js:122`.
Передать один event_id и два разных предложения категории facts. Результат: HTTP-слой получает persisted, но файл содержит только первое предложение. Проверка existing.includes(event_id) срабатывает внутри цикла уже после первой записи и пропускает остальные предложения этого события в том же файле. В written_files один и тот же файл указан дважды.

Нужна идемпотентность всей операции с сохранением каждого предложения, а не пропуск по event_id на уровне файла. Приёмка: два и более предложения одной категории сохраняются целиком, повтор не добавляет дублей.

### F02 · P1 · Незавершённый intent считается успешной записью (SC-08)

Источник: `scripts/memory/writer.js:105` и `writer-log.js:24`.
Подготовить журнал с intent и корректным hash, без файла памяти — состояние после сбоя между intent и записью. Повтор возвращает `{status:"persisted",idempotent:true}`, хотя память отсутствует; written_files и revision отсутствуют. Writer не проверяет статус найденной записи журнала. В тесте lock отсутствует, чтобы отдельно проверить восстановление после снятия оставшейся блокировки.

Нужно отличать intent от завершённого persisted и восстанавливать незавершённую транзакцию. Приёмка должна включать прерывание до записи и после частичной записи нескольких файлов.

### F03 · P1 · Оставшаяся блокировка останавливает writer после перезапуска (SC-08)

Источник: `scripts/memory/writer.js:20`.
Создать пустой memory.lock, который реальный процесс создаёт через openSync('wx'), затем вызвать запись. После примерно секунды возникает writer lock timeout. Lock не содержит владельца и не восстанавливается после гибели процесса; перезапуск не помогает. Требуется безопасное определение владельца/восстановление, без снятия блокировки работающего writer.

### F04 · P1 · Поиск проекта A раскрывает запись проекта B (SC-05/08)

Источник: `scripts/memory/writer.js:65`, `scripts/memory/search.js:78`.
Через writer сохранить общую запись user, затем запись B той же категории. Запросить уникальный маркер B из проекта A. localResults возвращает маркер B с меткой scope:user. Writer объединяет разные scopes в writer-entries.md, а поиск определяет scope всего файла по первому frontmatter и строит выдержку из всего текста.

Нужно согласовать гранулярность хранения и фильтрации: проверять scope каждой возвращаемой записи/выдержки. Проверить также обратный порядок записей и общие записи после проектных. Успешный путь Khoj использует похожую фильтрацию, но живой Khoj в этом ревью не тестировался.

### F05 · P1 · Потерянная задача индексации не восстанавливается повтором (SC-10)

Источник: `scripts/memory/writer.js:135` и ранний возврат на строке 112.
Смоделировать недоступность каталога журнала индекса, записать память, восстановить каталог и повторить событие. Оба вызова возвращают persisted; очередь индекса остаётся пустой. Ошибка queueIndex проглатывается, а повтор выходит до постановки задачи. Само сохранение при отказе индекса допустимо; дефект — отсутствие надёжно сохранённой задачи/восстановления и причины сбоя.

Нужна сверка persisted-событий с задачами индекса или иной долговечный механизм восстановления. Повтор после восстановления журнала должен создать недостающую задачу.

### F06 · P1 · Индексация навсегда остаётся in-flight после сбоя (SC-10)

Источник: `scripts/memory/indexer.js:61`, `indexer.js:84`.
Подготовить задачу in-flight. run возвращает [], requeueFailed — 0, задача остаётся in-flight. Нет обработки оставшихся после сбоя задач. Нужны владение задачей и безопасный возврат прерванной работы в повторную обработку.

### F07 · P2 · Успех одного файла выдаётся за индексацию всего события (SC-10)

Источник: `scripts/memory/indexer.js:70`.
Записать событие в facts и decisions; вернуть успех индекса для первого файла и HTTP 503 для второго. У события indexed:true, хотя одна задача failed. Нужно вычислять итог по всем задачам события. HTTP в этом сценарии синтетический, проверена только локальная логика статусов.

### F08 · P1 · Два обработчика очереди перезаписывают результат доставки (SC-07)

Источник: `scripts/memory/queue.js:32`, `queue.js:51`, `queue.js:101`.
Первый обработчик ждёт ответа доставки. Создать второй DurableQueue: конструктор возвращает ещё активно обрабатываемое событие в pending. Второй обработчик доставляет его успешно. Затем первый получает терминальную ошибку и перезаписывает delivered на failed. Итог: две доставки и неверный конечный статус failed.

Сценарий использует два экземпляра очереди с асинхронным перекрытием в одном процессе; для воспроизведения межпроцессная гонка не требуется. Даже просмотр queue-status создаёт DurableQueue и может изменить активное состояние. Повторная доставка сама по себе допустима для at-least-once, но снятие живого in-flight и перезапись подтверждённого результата — дефекты. Нужны атомарное владение задачей и проверка актуального состояния при завершении.

### F09 · P2 · Повторный capture того же commit отклоняется из-за timestamp (SC-07)

Источник: `scripts/memory/events.js:68`, `queue.js:61`.
Создать два события одного project_id/SHA/summary с разницей только во времени capture. event_id одинаков, enqueue второго выбрасывает different content. Нужно отделить идентичность события от времени повторного захвата, сохранив проверку настоящих конфликтов содержимого.

### F10 · P1 · Оборванная последняя строка блокирует всю очередь (SC-07)

Источник: `scripts/memory/queue.js:45`.
После корректного события дописать незавершённую JSON-строку — модель прерванной записи. Создание очереди падает с SyntaxError, предыдущие корректные события недоступны через API очереди. JSONL читается без восстановления/изоляции повреждённого хвоста. Нужна стратегия восстановления, сохраняющая корректные записи и исходные повреждённые данные для диагностики. Аналогичный JSON.parse без обработки виден в writer-log/indexer-log; отдельное воспроизведение для них здесь не выполнялось.
