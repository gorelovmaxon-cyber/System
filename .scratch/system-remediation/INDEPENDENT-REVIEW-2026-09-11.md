## U1 · P1 · Гибель keeper освобождает блокировку живого writer

Места: `scripts/memory/ipc-lock.js:46` (создание дочернего keeper), `:74` (возвращается только release); `scripts/memory/lock-keeper.cjs:47` (endpoint принадлежит keeper).

Владелец критической секции и владелец OS endpoint — разные процессы. После успешного acquireProcessLock writer получает функцию release, но его право выполнять запись не отзывается при смерти keeper. ОС освобождает endpoint умершего keeper даже тогда, когда writer жив и не завершил секцию.

Независимая проба:

1. P штатно получает lock в отдельном TEMP-каталоге.
2. Завершаем только созданный им keeper; P остаётся живым, release не вызван.
3. Запускаем отдельный процесс T с acquireProcessLock для того же resource.
4. T успешно получает lock и печатает SECOND_OWNER_ACQUIRED, exit 0.

**Два живых процесса имеют успешно выданное право входа без release первого.** Это дефект authority, а не возврат старой гонки удаления metadata. Текущая смена технологии устранила зависимость от карантинного имени, но добавила отдельный жизненный цикл keeper.

Исправление для Sonnet, FIX-02 с проверкой пользователей примитива: описать гарантии при независимой смерти writer и keeper, затем реализовать механизм, который не оставляет первого writer способным продолжать запись после утраты authority. Одного уведомления/проверки после очередной записи недостаточно. Синхронный writer может быть остановлен планировщиком в любой точке. Нужна позитивная регрессия: после смерти keeper второй не получает опасно пересекающееся право записи; проверить паузу P, смерть P, ошибку запуска keeper и штатный release. Не переносить этот примитив в accepted до независимой проверки. Он уже используется и журналами — область влияния шире writer.

## U2 · P1 · Восстановление повреждённого JSONL может уничтожить корректную историю

Места: `scripts/memory/jsonl.js:26` и `:33`: `fs.writeFileSync(file, ...)` переписывает исходный журнал на месте; default flag `w` сначала обнуляет его. В quarantine сохраняется только повреждённый хвост.

Проба: журнал содержит одну корректную старую запись и оборванную следующую. При readJsonl подставляем детерминированный EIO на реальной границе «файл открыт с w и усечён, запись нового prefix ещё не выполнена». После ошибки исходный журнал пуст; quarantine содержит только оборванный хвост. Корректной старой записи нет ни в одном из этих файлов.

Это инъекция I/O-сбоя в синтетической памяти, не реальный сбой диска и не произвольное удаление файла. Она показывает небезопасный порядок операций. Похожая перезапись есть и при добавлении завершающего newline к целому JSON без LF.

Исправление для Sonnet, FIX-06 с FIX-01/07: не обнулять единственную корректную копию при repair. Сначала сохранять восстановимую полную исходную версию/подготавливать новый файл, обеспечить нужные fsync и безопасную замену с понятной стратегией восстановления. Проверять write/fsync/rename failures и остановку процесса на границах; хвост и корректный prefix должны оставаться восстановимыми. Не ограничиваться подавлением ошибки. Проверить также оговорённую durability append: сейчас appendJsonl/transactJsonl используют appendFileSync без fsync; если обещается устойчивость к power loss, она требует отдельного доказательства и реализации.
