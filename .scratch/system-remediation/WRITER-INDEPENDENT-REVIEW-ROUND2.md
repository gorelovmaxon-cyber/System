## S1 · P1 · Recheck перед unlink не защищает от смены владельца

Область: FIX-02 / R5. `scripts/memory/writer.js`, ветка восстановления мёртвого владельца: повторное lockOwner/pidAlive и последующий unlinkSync.

Детерминированное расписание на двух процессах:

1. На диске lock действительно завершившегося процесса.
2. Процесс C читает старого владельца, подтверждает его смерть и повторно читает lock. Приостанавливается непосредственно перед реальным unlinkSync.
3. Процесс P штатно восстанавливает тот же старый lock, создаёт свой, записывает владельца и успешно возвращается из acquireLock. P жив и release ещё не вызывал.
4. C возобновляется и выполняет ранее намеченный unlink по тому же имени: удаляет уже lock живого P. Затем C получает свой lock, проходит publish-verify и тоже возвращается из acquireLock.

Получены **два успешных acquireLock при ещё не освобождённой блокировке P**. Проверка nonce после публикации P не помогает: удаление происходит позднее. Пауза введена только на границе штатной операции в отдельном процессе; содержимое lock после захвата P вручную не подменялось.

Нужно исправить протокол восстановления/публикации так, чтобы устаревшее решение не могло удалить новый lock. Ещё одно чтение, большее число повторов или увеличение grace оставляют окно между проверкой и удалением. Проверь одновременно восстанавливающих обработчиков, смену поколения и инвариант единственного владельца критической секции. Это продолжение существующего R5, а не новый объём работ.

## S2 · P1 · Перенос строки в source меняет scope сохранённого знания

Область: FIX-01/03, граница валидации writer и чтения metadata.

Writer принимает корректное по текущей validateProposal предложение:

```json
{
  "category": "facts",
  "status": "observation",
  "scope": "B",
  "statement": "PRIVATE_B_VALUE",
  "evidence": "synthetic fixture",
  "source": "source text\nscope: user"
}
```

entryText напрямую вставляет source в frontmatter. На диске появляются две строки scope: B и scope: user. parseFields использует последнее значение. `localResults('PRIVATE_B_VALUE', 'A')` возвращает PRIVATE_B_VALUE с scope:user. Результат writer — persisted.

Так нарушается изоляция даже без повреждения файла снаружи: строка проходит публичный валидатор и сериализатор. Источник может содержать переносы от AI/пользовательского ввода; это не обязательно умышленная атака. Существующая HTTP-авторизация не делает структурированные поля безопасными для вставки в текстовый формат.

Нужно обеспечить однозначную сериализацию и чтение: либо проверяемо отклонять неподдерживаемые формы строк, либо безопасно кодировать их. Проверь также event_id, source, supersedes, evidence, разделители metadata и переносы LF/CRLF; поля не должны создавать новые scope/status/event_id или границы записи. Не ограничивайся заменой именно тестовой строки. Сохраняй значимое содержимое по явному контракту; тесты должны проверять валидацию и результат повторного разбора.

## S3 · P2 · CRLF нормализуется в сохранённом тексте, но не в expected

Область: FIX-01 / R4. `entryPresent`: existing разбирается через normalizeEol, expected = entryText(...).trim() остаётся с CRLF внутри statement.

Передать statement `FIRST_LINE\r\nSECOND_LINE`, сохранить, затем повторить тот же event_id и то же предложение без изменения файла извне. Оба вызова успешны, в файле **две копии FIRST_LINE**. В отличие от старого R4, это CRLF во входных данных, а не преобразование всего файла после записи.

Нужна одинаковая канонизация сравниваемых данных и согласованность с hash/восстановлением. Добавить повтор LF/CRLF-многострочного ввода, смешанные окончания строк и восстановление частично завершённого пакета. Убедиться, что нормализация не скрывает настоящее различие значимого содержимого.
