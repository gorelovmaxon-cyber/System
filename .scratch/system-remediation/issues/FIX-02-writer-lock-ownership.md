# FIX-02 — Writer: владение блокировкой и восстановление после гибели процесса

**What to build:** Оставшаяся после гибели процесса блокировка writer не останавливает запись; блокировка работающего процесса не снимается. Владелец фиксируется в файле блокировки, liveness проверяется по pid.
**Requirement IDs:** SC-08 (R07), дефект F03.
**Blocked by:** none
**Status:** awaiting-review

## Контекст

Аудит: пустой `memory.lock` (созданный реальным процессом через `openSync('wx')`) блокирует writer на ~1с и навсегда после смерти процесса — владельца в файле нет, восстановления нет. Требование: безопасное определение владельца/восстановление, без снятия блокировки ещё работающего процесса. На Windows проверено: `process.kill(pid, 0)` бросает `ESRCH` для мёртвого pid и не бросает для живого.

## Файлы для изменения

- `scripts/memory/writer.js` — `acquireLock`: писать владельца `{pid, hostname, created, nonce}` в файл сразу после `openSync('wx')` (с fsync); при EEXIST читать владельца: пустой/неразбираемый файл или мёртвый pid → снять (unlink) и повторить; живой pid → ждать (текущий retry-цикл).
- `scripts/memory/tests/fix-02.test.js` — новый регрессионный тест.

## ⚠️ Файлы НЕЛЬЗЯ трогать

- `.claude/memory/`, `.local/` настоящие; контракт HTTP bridge.

## Входные/выходные данные

`acquireLock()` → функция освобождения. Время ожидания — как сейчас (100×10мс). Снятие чужих блокировок — только для осиротевших (пустой файл, неразбираемый, мёртвый pid).

## Алгоритм (шаг за шагом)

1. `acquireLock` создаёт `owner = {pid, hostname, created, nonce}`; после `openSync('wx')` пишет JSON и делает `fsync` до записи в журнал (честная долговечность владения).
2. При `EEXIST`: прочитать файл. Не удалось прочитать/пусто/JSON не разбирается/нет числового `pid` → подождать ~50мс и перечитать один раз (закрыть окно «открыл, ещё не записал владельца»), затем `unlink` и `continue` (повторить попытку `wx`).
3. JSON с `pid`: `try { process.kill(pid, 0); } catch { unlink; continue; }` — мёртвый владелец → снять. Живой → `Atomics.wait 10мс`, следующий цикл.
4. Время ожидания не увеличивать. Ошибка по-прежнему `writer lock timeout`.
5. Освобождение: как сейчас (`closeSync` + `unlinkSync`), дополнительно обернуть в try/catch — гонка со steal не должна падать.

## Критерии приёмки

- [ ] Пустой `memory.lock` (модель обрыва после `openSync('wx')`) → запись проходит (восстановление).
- [ ] Lock с владельцем-мёртвым-pid → запись проходит.
- [ ] **Реальные отдельные процессы:** процесс A держит блокировку и спит; процесс B вызывает запись → B получает `writer lock timeout` (не снимает чужую живую блокировку); после выхода A запись B проходит.
- [ ] Повторный вызов при отсутствии блокировки не падает; существующее поведение атомарной записи не меняется.

**Команды:** `node --test scripts/memory/tests/fix-02.test.js` (+ повторный прогон FIX-01).
**Ожидаемый результат:** красный на исходной реализации (F03: `assert.throws(/writer lock timeout/)`), зелёный после правки.
**Если проверка недоступна:** указать причину; awaiting-validation.

## Ограничения

Windows-семантика `process.kill(pid,0)` подтверждена локально (ESRCH). Крайний случай переиспользования pid не покрывается полностью — документируется как ограничение (уменьшается nonce+временем записи). Не снимаем блокировку живого процесса ни при каких обстоятельствах.

**Ограничение:** крайний случай переиспользования pid (мёртвый процесс, pid которого уже передан другому процессу) не покрывается полностью — риск снижен nonce+временем создания владельца, документируется как известное ограничение; живая блокировка не снимается ни при каких обстоятельствах.

## Доработка по ревью R5/R6 (2026-09-09, коммит `8f4809a`)

**Замечание R5 (P1):** окно `openSync('wx')` → `writeOwner` открывало кражу живого lock: второй процесс через 50 мс удалял пустой файл, получал свою блокировку, а первый по release удалял блокировку второго. Timeout-пауза не является доказательством смерти; nonce писался, но не проверялся при освобождении.

**Замечание R6 (P1):** проверка CONFLICT и повтор выполнялись ДО `acquireLock` → два процесса с одним event_id возвращали оба `persisted` с разным содержимым (журнал под блокировкой не перечитывался).

**Исправление (writer.js):**
- publish-verify: `wx` → `writeOwner` → `closeSync` → повторное чтение; если файл уже не наш (sameOwner(pid+nonce)) — НЕ удаляем чужой lock, повторяем попытку.
- Пустой/мусорный lock: 5×50 мс grace-перечитываний, только затем unlink (владелец мог не успеть опубликоваться).
- Мёртвый владелец: повторное чтение непосредственно перед unlink — pid должен быть тем же и всё ещё мёртвым; живой — 10 мс ожидание.
- `pidAlive`: только `ESRCH` → мёртв; `EPERM`/прочие ошибки доступа → жив (lock не крадём).
- `release()`: unlink только если текущее содержимое — наш pid+nonce (чужое поколение не трогаем).
- CONFLICT-проверка и идемпотентный fast-path перенесены ВНУТРЬ `acquireLock`; журнал читается заново после захвата.

## Доработка по ревью S1 (2026-09-09, раунд 2, продолжение R5)

**Замечание S1 (P1):** окно «повторное чтение мёртвого владельца → unlinkSync» не защищает от смены владельца. Воспроизведённое расписание (два процесса): C читает мёртвого владельца, повторно подтверждает смерть, приостанавливается ПЕРЕД unlink; P штатно восстанавливает тот же lock, создаёт свой, проходит publish-verify и работает (release не вызывал); C возобновляется и удаляет живой lock P по пути. Затем C сам захватывает lock — **два успешных acquireLock при неосвобождённой блокировке P**. Ещё одно чтение/больше повторов/больше grace не закрывают окно между проверкой и удалением.

### Инварианты протокола блокировки

1. **Единственный владелец критической секции:** в любой момент времени не более одного процесса находится между успешным возвратом `acquireLock()` и `release()`.
2. **Владение устанавливается только publish-verify:** процесс владелец только после того, как перечитал `memory.lock` по каноническому пути и увидел собственное поколение `{pid, nonce}`. Файл вне канонического пути (карантин) владением не является.
3. **Смена поколения:** каждое владение — поколение `{pid, nonce}`; `release()` удаляет lock только если канонический путь содержит собственное поколение (чужое поколение не трогаем — R5).
4. **Устаревшее решение не разрушает новое поколение:** процесс, решивший восстановить lock (пустое содержимое или мёртвый pid), не выполняет разрушающее действие по каноническому пути. Вместо этого он атомарно перемещает текущий occupant пути в уникальный карантин (`rename`), проверяет, что именно переместил, и либо удаляет verified-карантин (мёртвый владелец/пусто), либо возвращает перемещённое на место (живой владелец — устаревшее решение не имеет права его удалять).
5. **Разрушение непроверенного файла безопасно:** если перемещённый файл принадлежит процессу, не завершившему publish-verify (пустой файл в окне open→write владельца), удаление карантина безопасно — такой процесс владельцем не является, его publish-verify на каноническом пути провалится, и он повторит попытку.
6. **Граница гарантии (документируется):** между `rename` канонического пути в карантин и восстановлением пути путь `memory.lock` отсутствует. Третий процесс, стартующий ровно в этом окне (два соседних syscall в одном синхронном блоке без внешней паузы), может захватить блокировку, пока предыдущий владелец ещё завершает операцию. Без OS-примитива условного unlink/swap (в Node fs отсутствует) окно не закрывается атомарно; в двухпроцессных расписаниях — сценарий ревьюера и два одновременных реклаймера — инвариант 1 выполняется. Это качественное отличие от прежнего unlink по пути: устаревшее решение больше не может УДАЛИТЬ новый lock (может только временно переместить и обязано вернуть).

### Исправление (writer.js)

- Ветка восстановления мёртвого владельца и ветка пустого/мусорного lock: вместо `unlinkSync(file)` — `renameSync(file, file + '.reclaim-<pid>-<nonce>')`, чтение перемещённого файла, проверка: тот же мёртвый pid/пусто → `unlinkSync(карантин)`; иное содержимое (живой владелец, сменившееся поколение) → `renameSync(карантин, file)` (восстановление; при занятом пути — короткие повторы, затем подчистка карантина — он не является владением).
- `release()`, publish-verify, `pidAlive` (ESRCH→мёртв, EPERM→жив) и ожидание живого владельца не меняются.
- В карантин попадает только то, что реально лежало на пути в момент `rename`; содержимое карантина проверяется до любого удаления.

**RED/GREEN:** на `980d331` (до правки) новые тесты S1 падают — ребёнок-реклаймер удаляет живой lock родителя и входит в критическую секцию; после правки — `fix-02.test.js` (12/12), весь набор зелёный. Проба ревью `writer-review-round2.cjs` S1: `reproduced:false` (пауза-зацепка harness на `unlinkSync(memory.lock)` больше не срабатывает — восстановление не удаляет путь).

**Тесты (добавлены в `fix-02.test.js` + `fix-02-reclaim-pause.cjs`):** S1: ребёнок-реклаймер приостанавливается перед своим разрушающим действием над memory.lock (ready/resume); родитель штатно восстанавливает тот же lock и захватывает его; возобновление ребёнка НЕ удаляет живой lock родителя (pid родителя сохранён), ребёнок получает `writer lock timeout`, «child-acquired» нет; S1: второй реклаймер при удерживаемом первым lock не входит в секцию (timeout), lock первого переживает, после освобождения подчищен; S1: восстановление мёртвого lock не оставляет карантинных файлов (после захвата в каталоге только живой lock).

## Четвёртое ревью U1 (2026-09-11, P1): гибель keeper освобождала блокировку живого writer

Четвёртое независимое ревью ([INDEPENDENT-REVIEW-2026-09-11.md](../INDEPENDENT-REVIEW-2026-09-11.md))
подтвердило 87/87 текущего набора и закрытие T1 через смену примитива (endpoint вместо
карантинного имени), но **отклонило блок по U1 (P1)**.

**U1:** владелец критической секции и владелец OS-endpoint — разные процессы. ОС освобождает
endpoint умершего keeper'а и тогда, когда writer жив и секцию не завершил. Проба: P штатно
захватывает ресурс, убивается только его keeper; второй процесс T получает право входа и
печатает `SECOND_OWNER_ACQUIRED` (exit 0) при живом P, не вызывавшем release. **Два живых
процесса имеют выданное право входа без первого release.** Это дефект authority, а не возврат
гонки удаления metadata.

Требование ревью: описать гарантии при независимой смерти writer и keeper, реализовать
механизм, не оставляющий первого writer'а способным писать после утраты authority; одной
проверки после очередной записи недостаточно — синхронный writer может быть остановлен
планировщиком в любой точке. Нужна позитивная регрессия. Примитив не переносить в accepted до
независимой проверки: он используется журналами (`jsonl.js`), область влияния шире writer.

### Пересмотренная модель authority

**Authority = каноническая запись владения `{pid, hostname, created, nonce}` по каноническому
пути, удерживаемая живым процессом.** Endpoint — не authority, а право на шаг публикации
(сериализует «прочитать → решить → опубликовать»). Authority утрачивается, когда владелец
завершился или его запись заменена новым поколением после release; смерть keeper'а сама по
себе authority не отзывает.

| Событие | OS-endpoint | Право входа | Запись владения |
|---|---|---|---|
| Независимая смерть writer (keeper жив) | keeper замечает смерть родителя (опрос 10 мс) и освобождает endpoint | освобождается: записанный владелец мёртв | остаётся до следующего захвата, затем заменяется новым поколением |
| **Независимая смерть keeper (writer жив)** | освобождается немедленно | **не освобождается**: запись называет живого владельца, претендент поверх неё не публикует | сохраняется за writer'ом |
| Смерть обоих | свободен | свободно | мёртвый владелец не препятствует: следующий acquire перезаписывает своим поколением |
| Штатный release | keeper получает release-файл и освобождает endpoint | освобождается вместе с удалением записи | удаляется |
| Отказ запуска keeper | нет | не выдаётся: синхронная ошибка до цикла попыток | не публикуется |
| Пауза/депривация writer'а внутри секции | удерживается его keeper'ом | удерживается | сохраняется |

### Исправление (`ipc-lock.js`, `writer.js`)

- **Шаг 1 — эксклюзивный bind keeper'а** (как было): OS-endpoint ресурса.
- **Шаг 2 — guard живого владельца**: под своим bind'ом перечитать канонический файл владения;
  записанный **живой** владелец → `keeper.kill()`, отказ `live-owner`, повтор. Проверка идёт и до
  `spawn` (ожидание живого владельца не стоит процесса keeper на каждую попытку), и повторно
  после bind — второе чтение отвечает именно на смерть keeper'а живого владельца. Решение
  «прочитать → решить → опубликовать» сериализуется эксклюзивным bind, поэтому конкурирующий
  acquire не может его аннулировать.
- `pidAlive`: `ESRCH` — единственное доказательство смерти; `EPERM` и прочие ошибки → жив
  (fail-closed в сторону отказа, а не кражи).
- Проверка наличия keeper-скрипта — синхронно и до цикла: без keeper право входа недостижимо,
  это ошибка, а не таймаут через `attempts`.
- **`hold.assertHeld()`** — владелец может падать fail-closed (`LOCK_AUTHORITY_LOST`), если
  keeper ушёл или запись владения больше не называет его поколение. Документировано как
  **сужение окна, а не инвариант**: инвариант несёт guard шага 2.
- `release()` не ждёт release-ack у мёртвого keeper'а (иначе fail-closed владелец висел бы
  секунду); запись владения удаляется только если она — наше поколение (`sameOwner`).
- `LOCK_TIMEOUT.reason` — причина последнего отказа (`live-owner` / `busy` / `no-status`).
- `writer.js`: `release.assertHeld()` после захвата, перед каждой записью целевого файла и перед
  публикацией в журнал. Путь записи падает fail-closed, а не пишет по утраченному праву.

### Тесты (новые: `fix-02-keeper.test.js`, `fix-02-keeper.cjs`)

Только TEMP-ресурсы; фикстура перехватывает `cp.spawn` до загрузки `ipc-lock`, чтобы наблюдать
конкретного keeper'а.

1. гибель keeper'а при живом владельце: endpoint свободен (`probe-endpoint` → `acquired`), но
   второй процесс получает `REFUSED:live-owner`, `ACQUIRED` нет, запись владения — прежняя,
   владелец жив; `assertHeld()` → `LOCK_AUTHORITY_LOST`; после штатного release следующий
   процесс получает ресурс;
2. **пауза живого владельца** внутри секции: второй процесс не входит, запись владения не
   меняется (nonce тот же); после release — входит;
3. **независимая смерть writer'а**: keeper освобождает endpoint, следующий процесс публикует
   своё поколение (`try-owned.json`, pid ≠ pid погибшего);
4. **отказ запуска keeper'а**: синхронная ошибка `lock keeper script is missing`, владение не
   опубликовано, каталог без leftovers, обычный захват после отказа проходит;
5. `assertHeld()` отвергает подменённую запись владения (`LOCK_AUTHORITY_LOST`);
6. **штатный release** передаёт ресурс следующему.

### Ограничения и статус

- Переиспользование pid по-прежнему не покрывается полностью: если pid мёртвого владельца уже
  передан другому процессу, его запись считается живой → отказ. Отказ безопасен (не кража),
  но это ограничение, а не гарантия; снижается nonce + временем создания.
- `assertHeld()` — сужение окна, не инвариант: инвариант обеспечивает guard шага 2.
- **Тикет не переводится в accepted автором.** Примитив уже используется журналами
  (`jsonl.js` → `writer-log`, `indexer-log`, очередь), поэтому независимая проверка нужна и для
  интеграции с writer/queue/indexer, а не только для самого примитива.
