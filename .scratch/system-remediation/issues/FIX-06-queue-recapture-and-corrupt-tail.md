# FIX-06 — Очередь/журналы: повторный capture без конфликта по времени и устойчивость к оборванному хвосту JSONL

**What to build:** Повторный capture того же commit/session revision не отклоняется из-за нового времени захвата; оборванная последняя строка JSONL не блокирует очередь и журналы writer/indexer; повреждённые строки не удаляются молча и доступны для диагностики.
**Requirement IDs:** SC-07 (R07), дефекты F09, F10.
**Blocked by:** none (общий модуль `jsonl.js` создаётся здесь; FIX-05 правит те же файлы — выполнять после FIX-05)
**Status:** awaiting-review

## Контекст

Аудит:
- **F09:** `eventIdFor` детерминирован, но `createEvent` проставляет новый `timestamp` при каждом capture → `enqueue` сравнивает полный JSON и бросает «different content». Идентичность события не должна зависеть от времени повторного захвата; настоящие конфликты содержимого должны по-прежнему отклоняться.
- **F10:** `records()` делает `JSON.parse` каждой строки; оборванный хвост → `SyntaxError` в конструкторе, предыдущие корректные события недоступны. Аналогичный необработанный parse — в `writer-log`/`indexer-log`. Нужна стратегия восстановления: корректные записи доступны, повреждённые сохранены для диагностики (карантин), обработка продолжается.

## Файлы для изменения

- `scripts/memory/jsonl.js` — новый общий модуль: `readRecords(file, keyFn)` → `{records: Map, corrupt: [...]}` (толерантный построчный parse, без выбрасывания); `appendDurable(file, record)` — open 'a' + write + fsync + close (долговечность хвоста).
- `scripts/memory/queue.js` — `records()` через `jsonl.readRecords(this.file, r => r.event?.event_id)`, хранить `this._corrupt`; `append` через `appendDurable`; `quarantineCorrupt()` — перенести повреждённые строки в `events.jsonl.corrupt-<ts>` (атомарная перезапись главного файла корректными строками); `enqueue` сравнивать каноническое содержимое без `timestamp`.
- `scripts/memory/events.js` — `contentKey(event)` = JSON без поля `timestamp` (канон для сравнения содержимого); используется в `queue.enqueue`.
- `scripts/memory/writer-log.js`, `scripts/memory/indexer-log.js` — толерантное чтение через `jsonl.readRecords`, `append` через `appendDurable`; экспонировать `corrupt()`.
- `scripts/memory/queue-status.js` — показывать `corrupt_count` и, при запросе `--quarantine`, вызывать карантин.
- `scripts/memory/tests/fix-06.test.js` — новый регрессионный тест.

## ⚠️ Файлы НЕЛЬЗЯ трогать

- `.local/` реальные; формат событий (schema_version '1') — не менять; поле `timestamp` остаётся обязательным в событии.

## Входные/выходные данные

`contentKey(event)`: JSON.stringify события с удалённым `timestamp`. `readRecords(file, keyFn)` → `{records, corrupt:[{index, raw}]}`. `quarantineCorrupt()` → число перемещённых строк; исходные повреждённые данные сохраняются в sidecar-файле.

## Алгоритм (шаг за шагом)

1. `jsonl.js`: читать файл построчно; пустые строки пропускать; `JSON.parse` в try — при ошибке собрать `{index, raw}`; ключ записи — `keyFn(record)`; одинаковые ключи — последняя строка выигрывает (как сейчас). `appendDurable` — open 'a', write, fsync, close.
2. `queue.enqueue`: существующий → `contentKey(existing.event) === contentKey(event)` → вернуть существующий (повторный capture ок); иначе — «different content» (настоящий конфликт). Разделить во времени: `event_id` и содержимое детерминированы, timestamp не участвует в сравнении.
3. `queue.records()`: толерантно; `process()/list()` работают только с корректными записями; `quarantineCorrupt()` переносит хвост в sidecar (файл `events.jsonl.corrupt-<ISO ts>`), главный файл переписывается атомарно корректными строками; повреждённые данные не удаляются.
4. `writer-log`/`indexer-log`: толерантное чтение (журнал writer критичен для FIX-01: сбойный хвост не должен блокировать writer); `corrupt()` для диагностики.
5. `queue-status`: вывод `corrupt_count` (и `--quarantine`).

## Критерии приёмки

- [ ] Повторный capture того же commit (другой timestamp) → enqueue возвращает существующую запись без ошибки; реально изменённое содержимое (другая summary) → «different content».
- [ ] Оборванная строка после корректного события: конструктор не бросает, корректные события доступны и доставляются, повреждённая строка видна в `corrupt_count`.
- [ ] Карантин переносит повреждённые строки в sidecar, не теряя их; после карантина файл читается без corrupt.
- [ ] `writer-log`/`indexer-log` с оборванным хвостом: чтение не падает, корректные записи доступны.
- [ ] `appendDurable` сохраняет рабочее поведение добавления (долговечный хвост).

## Результаты: что поставлено на самом деле (2026-09-11)

План выше описывал `readRecords`/`corrupt_count`/`quarantineCorrupt()`. Поставлено иначе —
расхождение фиксируется здесь явно, чтобы приёмка проверяла реальный код:

| План | Поставлено |
|---|---|
| `jsonl.readRecords(file, keyFn)` → `{records, corrupt}` | `readJsonl(file)` → массив записей; оборванный хвост **ремонтируется при чтении**, повреждение в середине — fail-closed `JSONL_CORRUPT_MIDDLE` (файл не изменяется) |
| `quarantineCorrupt()` из очереди + `--quarantine` | карантин делает сам ремонт: sidecar `<файл>.corrupt-tail-<ts>-<pid>-<hash>` (имя сохраняет префикс `<basename>.corrupt-tail-`, это проверяет B09) |
| `queue-status --quarantine`, `corrupt_count` | не реализовано; `queue-status.js` показывает очередь без corrupt-счётчика |
| `writer-log`/`indexer-log` через `readRecords` + `corrupt()` | оба используют `readJsonl`/`appendJsonl`; отдельного `corrupt()` нет |
| `appendDurable` = open 'a' + write + fsync + close | как в плане (`jsonl.appendDurable`) |
| `contentKey(event)` без `timestamp` | `eventContent(event)` в `queue.js` (то же поведение: F09) |

Почему карантин перенесён в чтение: ремонт обязан происходить под тем же журнальным
primitive, что и запись (FIX-02), иначе восстановление конкурирует с дозаписью; очередь и оба
журнала получили его без дублирования кода.

**Тесты FIX-06 (9):** B10 (UTF-8 truncation), B11 ×2 (валидация события/очереди), B09/F10
(оборванные хвосты writer/indexer/queue → карантин, корректные записи живы), B09 (повреждение

## Четвёртое ревью U2 (2026-09-11, P1): ремонт мог уничтожить корректную историю

Независимое ревью ([INDEPENDENT-REVIEW-2026-09-11.md](../INDEPENDENT-REVIEW-2026-09-11.md)) **отклонило
блок по U2 (P1)**.

**U2:** `fs.writeFileSync(file, ...)` переписывал журнал **на месте**, а default flag `w` сначала
усекает файл. Проба подставляет детерминированный EIO на реальной границе «файл открыт с `w` и
усечён, новый prefix ещё не записан»: после ошибки исходный журнал пуст, в карантине только
оборванный хвост — **корректной старой записи нет ни в одном файле**. Та же перезапись
происходила при добавлении завершающего LF к целому JSON без LF. Дополнительно ревью указало,
что `appendJsonl`/`transactJsonl` использовали `appendFileSync` без fsync: если durability
обещана, она требует отдельной реализации и доказательства.

Требование: не обнулять единственную корректную копию при repair — сначала сохранять
восстановимую полную исходную версию/готовить новый файл, обеспечить нужные fsync и безопасную
замену с понятной стратегией восстановления; проверять write/fsync/rename failures и остановку
процесса на границах; хвост и корректный prefix должны оставаться восстановимыми; не
ограничиваться подавлением ошибки.

### Исправление (`scripts/memory/jsonl.js`)

Порядок операций ремонта оборванного хвоста:

1. **карантин первым**: оборванный хвост пишется durable (`openSync 'wx'` + write + fsync +
   close) в sidecar `<файл>.corrupt-tail-<ts>-<pid>-<hash>`; `'wx'` исключает перезапись
   чужого карантина;
2. **подготовка копии**: исправленное содержимое (byte-exact prefix по `lastIndexOf('\n')`)
   пишется в соседний файл `<файл>.repair-<pid>-<hex>` с fsync;
3. **атомарная замена**: `renameSync(tmp, file)`; при отказе tmp удаляется, оригинал не тронут;
   затем best-effort fsync каталога (Windows не открывает каталог как файл).

Любой отказ до шага 3 оставляет исходный файл целиком — корректный префикс и оборванный хвост
восстановимы оба. Канонический путь никогда не открывается на запись/усечение и никогда не
переписывается на месте: единственная мутация — rename подготовленного соседа.

Соседние исправления:
- **валидная последняя запись без LF больше не переписывается** — файл не изменяется, разделитель
  вставляет следующий append;
- **durability append**: `appendDurable` = `openSync(file,'a')` + `writeFileSync(fd)` +
  `fsyncSync(fd)` + `closeSync(fd)`; `appendFileSync` не используется. `appendJsonl`/`transactJsonl`
  читают под тем же журнальным primitive перед дозаписью и проверяют `assertHeld()` перед каждой
  записью.

### Тесты (новые U2: `fix-06.test.js`, фикстура `fix-06-repair-crash.cjs`)

Аварийные регрессии инжектируют отказ и смерть процесса на каждой границе ремонта (только
TEMP-файлы):

1. **отказ записи карантина** → журнал байт-в-байт прежний, карантин не заявлен;
2. **отказ записи подготовленной копии** → журнал прежний, хвост в карантине, префикс в журнале;
3. **отказ замены (rename)** → журнал прежний, хвост в карантине, tmp-файлов не осталось;
4. **смерть процесса** сразу после карантина и после подготовленной копии (exit 23) → журнал
   байт-в-байт прежний, хвост в карантине — восстановимы обе части;
5. **механизм**: канонический журнал не открывается на запись и не переписывается на месте;
   единственная замена — rename подготовленного соседа, содержимое копии = byte-exact prefix;
6. **валидная последняя запись без LF** не переписывается и остаётся дозаписываемой
   (`{"a":1}\n{"b":2}` → append → `{"a":1}\n{"b":2}\n{"c":3}\n`);
7. **durability append**: запись идёт через явно открытый fd с флагом `'a'` и этот fd сбрасывается
   fsync'ом до освобождения блокировки; `appendFileSync` по каноническому пути не вызывается.

### Ограничения и статус

- Карантин и ремонт выполняются при чтении под журнальным primitive (FIX-02). Ремонт — не
  отдельная команда: `queue-status --quarantine` и `corrupt_count` из плана не поставлены.
- Повреждение в середине файла не ремонтируется и не удаляется: `JSONL_CORRUPT_MIDDLE`, файл
  остаётся как есть (fail-closed).
- **Тикет не переводится в accepted автором**; приёмка — за независимым проверяющим, включая
  интеграцию с writer/queue/indexer.

## Блок 3: валидация capture до нормализации (G08) — 2026-09-12

**Проблема (G08, P1).** `createEvent({decisions:'KEEP_THIS_DECISION', …})` возвращал валидное
событие с `decisions: []`: нормализация (`Array.isArray(x) ? x : []`) стирала содержательный вход
до `validateEvent`, и неверный тип принимался с незаметной потерей решения/коррекции/проверки.
Прямой enqueue массивы проверяет, а capture через `createEvent` — нет.

**Что изменено в `scripts/memory/events.js`:** добавлен `validateInput(input)`, вызываемый первым
в `createEvent` — тип проверяется на **исходном** входе, до нормализации. Отсутствующее или явно
пустое (`undefined`/`null`) необязательное поле означает пустое значение и допустимо;
присутствующее поле неверного типа отклоняется явно (`decisions must be an array of strings`,
`summary must be a string`, `revision must be an integer`). Скалярные поля больше не подменяются
приведением типа. `validateEvent` не изменён.
