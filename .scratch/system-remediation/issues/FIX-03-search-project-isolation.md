# FIX-03 — Поиск: изоляция проектов по записям в общих файлах

**What to build:** Запись проекта B, лежащая в том же файле `writer-entries.md`, что и общие записи, не возвращается при поиске из проекта A. Фильтрация выполняется по каждой записи файла, а не по первой frontmatter всего файла.
**Requirement IDs:** SC-05/SC-08 (R04, R05, R07), дефект F04.
**Blocked by:** none (не зависит от FIX-01/02; может выполняться параллельно)
**Status:** awaiting-review

## Контекст

Аудит: writer объединяет разные scopes в один файл; `search.localResults` берёт scope всего файла по первой frontmatter и строит выдержку из всего текста → поиск проекта A раскрывает запись B. Требуется согласовать гранулярность хранения и фильтрации: проверять scope каждой записи; проверять обратный порядок записей и общие записи после проектных; не ломать ручные однозаписные файлы памяти.

## Файлы для изменения

- `scripts/memory/search.js` — новый парсер записей `entries(text)`: файл делится по строкам-разделителям `^---\n`; у каждой записи свои frontmatter-поля и тело. `localResults`: hits/scope/snippet считаются по записи, а не по файлу. `searchKhoj`: локальное чтение файла для meta — тоже через записи.
- `scripts/memory/tests/fix-03.test.js` — новый регрессионный тест.

## ⚠️ Файлы НЕЛЬЗЯ трогать

- Формат хранения `writer-entries.md` (память сохраняется; миграция не требуется).
- `.claude/memory/` реальную.

## Входные/выходные данные

`entries(text)` → `[{meta:{...}, body:"..."}]`. `localResults(query, projectId, {paths, limit, budget})` — как сейчас, но фильтр per-entry. Поля результата поиска без изменений: `snippet, source, scope, status_hint, relevance`.

## Алгоритм (шаг за шагом)

1. `entries(text)`: `parts = text.split(/^---\n/m)`; первый элемент — префикс до первой `---` (обычно пустой), игнорируется; для каждого следующего: `end = part.indexOf('\n---')`; поля = `part.slice(0, end)`, тело = `part.slice(end+4).trim()`; парс полей — как существующий `frontmatter`. Если файл без frontmatter (`parts.length === 1`) → одна запись `{meta:{}, body:text.trim()}` (сохраняет текущее поведение).
2. `localResults`: для каждого файла — для каждой записи: фильтр `projectId && meta.scope && meta.scope !== 'user' && meta.scope !== projectId` → пропустить запись; `hits` по тексту записи (meta+body); `snippetFor(body || text записи, ...)`. Один файл может дать несколько результатов — их разрешено вернуть все (или ограничить лимитом), источники сохраняются.
3. `searchKhoj`: при чтении локального файла для meta брать первую запись файла; фильтр по её scope (документированное ограничение: Khoj индексирует файлы целиком; live-проверка — awaiting-validation).
4. `frontmatter` оставить экспортируемой (обратная совместимость).

## Критерии приёмки

- [ ] Запись B сохранена после общей записи в одном файле; поиск уникального маркера B из проекта A не возвращает её; из проекта B — возвращает.
- [ ] Обратный порядок (проектная запись записана до общей) — та же изоляция.
- [ ] Общая запись (scope user) видна и из A, и из B; `status_hint`/`scope` в результатах соответствуют конкретной записи.
- [ ] Ручные однозаписные файлы (например, `user-profile/*.md`) возвращаются как раньше.
- [ ] Лимит и бюджет по-прежнему применяются.

## Доработка по ревью R2/R3 (2026-09-09, коммит `1b6e1e9`)

**Замечание R2 (P1):** положительный путь `searchKhoj` присваивал scope по первой записи файла (`entries(text)[0]`), а snippet брал из ответа сервиса → запись B возвращалась проекту A с меткой scope:user. Смежно: `relativeSource` (`/^\.\/??/`) съедал ведущую точку у `.claude/...`, файл не читался и брался текст сервиса.

**Замечание R3 (P1):** разделитель `entries` рассчитан только на LF — после LF→CRLF файл распознавался одной «записью» без metadata, весь файл открывался проекту с scope:unknown. `core.autocrlf=true` делает CRLF реальным сценарием Windows.

**Исправление (search.js):**
- R2: каждый хит сервиса атрибутируется к локальной записи `matchEntry` (запись должна содержать слово запроса; среди кандидатов — максимум совпадений слов запроса и токенов сниппета); snippet пересобирается из тела подтверждённой записи; отсутствующий локальный файл и неатрибутируемый хит отбрасываются; scope берётся из meta подтверждённой записи, чужому результату scope запрашивающего проекта не присваивается.
- R3: `entries()`/`frontmatter()` нормализуют CRLF перед разбором; проектный запрос видит только `scope: user` или свой `project_id` (неизвестный/отсутствующий scope исключён — виден только на пользовательском уровне без project_id); `relativeSource` — `/^\.\//` (только префикс './').
