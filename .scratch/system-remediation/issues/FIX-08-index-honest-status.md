# FIX-08 — Индекс: честный статус события (indexed только по текущей ревизии всех файлов)

**What to build:** `indexed:true` у события выставляется только когда для каждого файла события существует задача на ТЕКУЩУЮ ревизию файла и эта задача завершена успешно; частичный успех, устаревший снимок задач и сбой записи агрегата отражаются честно.
**Requirement IDs:** SC-10 (R08), дефекты F07, G01, G02.
**Blocked by:** FIX-07
**Status:** awaiting-validation

## Контекст

Аудит 2026-09-09 (F07): событие пишется в facts и decisions; первый файл индексируется (200), второй — 503; у события `indexed:true`, хотя одна задача failed. Причина: `run()` выставлял `writerLog.indexed = true` после каждого отдельного успеха.

Общий аудит 2026-09-12 добавил два дефекта той же модели:
- **G01:** подтверждение стояло по устаревшему снимку задач. Новая ревизия файла создавала новую задачу, но событие оставалось `indexed:true` при незавершённой задаче на текущую ревизию (`before:true, after:true, pending:1`, воспроизведено). Актуальность надо проверять по ревизии, снятой с диска, а не по снимку.
- **G02:** запись агрегата выполнялась внутри того же `try`, что и доставка, поэтому сбой записи агрегата подменял исход задачи: принятая задача докладывалась как `superseded`, а расхождение между журналами оставалось невидимым и невосстановленным (`retry.length === 0`, `writerIndexed: false`, воспроизведено).

## Файлы для изменения

- `scripts/memory/indexer.js` — единая модель `aggregateState`: событие подтверждено ровно тогда, когда для каждого относительного пути из `written_files` есть задача с `file_revision`, равной хэшу ТЕКУЩЕГО содержимого файла, и эта задача `indexed`. Запись агрегата вынесена за `try` доставки; сбой виден (`index_error`-путь через warn) и не разрушает состояние; поле `index_state` описывает, чего не хватает (`missing`/`pending`).
- `scripts/memory/tests/fix-08.test.js` — новый регрессионный тест.

## ⚠️ Файлы НЕЛЬЗЯ трогать

- Реальные `.local/`; контракт `indexed` как «все обязательные файлы события проиндексированы по текущей ревизии» — зафиксирован в memory-contract.

## Входные/выходные данные

Журнал writer события: `{..., indexed: boolean, index_state: null | {missing: string[], pending: {file, status, task_id}[]}}`. `run()` возвращает per-task результаты (форма не меняется: массив с `task_id`, `status`, `reason`).

## Алгоритм (шаг за шагом)

1. `aggregateState(record, paths, tasks)`: для каждого `relative` из `record.written_files` берётся ревизия `fileRevision(path.resolve(paths.system_root, relative))`; ищется задача с `file === relative && file_revision === revision`. Нет задачи → `missing`; задача не `indexed` → `pending`. Пустой `written_files` → не подтверждено (`reason: 'no-written-files'`).
2. `syncAggregate()`: запись в writerLog только при смене флага; при `indexed:false` пишется `index_state` с недостающим, при `true` — `null`. Сбой записи не бросает: результат помечается `error`, флаг остаётся прежним.
3. `queueIndex()` после постановки задачи вызывает `refreshEvent()` — новая ревизия немедленно снимает подтверждение (G01).
4. `run()` после цикла вызывает `refreshAggregates(paths)` — пересчёт по всем сохранённым событиям, включая события вовсе без задач (пустой набор задач актуальность не подтверждает). Ошибки попадают в stderr с идентификатором события, но не в результат задачи (G02).
5. `reconcile()` (FIX-07) доводит `missing` до задач; после успешного `run` событие снова `indexed:true`.

## Критерии приёмки

- [x] Событие с двумя файлами: успех первого + 503 второго → `writerLog.get(evt).indexed === false`.
- [x] После `requeue-failed` и повторного `run` с успехом обоих → `indexed === true`.
- [x] Событие с одной задачей: успех → `indexed:true` (поведение не сломалось).
- [x] Событие без задач не получает `indexed:true` по ошибке.
- [x] **G01:** новая ревизия файла снимает `indexed` сразу; завершённая задача возвращает `indexed:true` и обнуляет `index_state`.
- [x] **G01:** правка файла в обход очереди (ревизия с диска не совпадает со снимком задач) делает подтверждение недействительным; `index_state.missing` называет путь; `reconcile` + `run` возвращают состояние к факту.
- [x] **G02:** сбой записи агрегата не выдаётся за исход задачи (`status: 'indexed'`, `reason: null`), виден в stderr, агрегат остаётся честным (`false`), следующий проход восстанавливает его без повтора доставки.
- [x] Осиротевшая задача с истёкшей арендой не подтверждает агрегат до успешного повторного прохода.

## Ограничения

Живой reindex Khoj — внешняя блокировка (SC-04); здесь чинится локальная логика статусов (как в аудите). Модель считает «текущей» ревизию с диска на момент прохода; она не является подписью содержимого Khoj — если Khoj принял старую ревизию и файл с тех пор изменился, состояние честно останется неподтверждённым до новой задачи.
