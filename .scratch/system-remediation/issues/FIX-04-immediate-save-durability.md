# FIX-04 — Немедленное сохранение без сервисов и честные границы долговечности

**What to build:** Важные решения и исправления сохраняются сразу по ходу работы через единый writer/`save.js` без работающих Activepieces, Khoj или AI-провайдера; `persisted` возвращается только после долговечной локальной фиксации; границы гарантий при остановке процесса и при отказе питания описаны честно и отдельно; требование задокументировано в SPEC и контракте с датированным источником.
**Requirement IDs:** SC-08 (R03, R07), R05; требование ревью Opus от 2026-09-09 (восстановлено исходное намерение пользователя).
**Blocked by:** FIX-01 (семантика восстановления), частично FIX-07 (видимость сбоя очереди индекса)
**Status:** awaiting-review

## Контекст

В ревью Opus (см. `OPUS-REVIEW-PLAN.md` → актуальное задание `SONNET-PROMPT.md`) восстановлено исходное намерение: важные решения сохраняются сразу, а не только итоговым резюме/асинхронным анализом. Существующий ручной путь `node scripts/memory/save.js` уже пишет напрямую через `writeProposal`; нужно: (а) честная долговечность (fsync до подтверждения), (б) проверяемые сценарии приёмки на временной памяти, (в) явная документация границ. Второй системы записи не создаём; каждую реплику/браузерный чат автоматически не сохраняем.

## Файлы для изменения

- `scripts/memory/writer.js` — `writeAtomic`: писать во временный файл через открытый fd, `fsyncSync` перед `renameSync` (долговечность против отказа питания насколько её гарантирует ФС); `acquireLock` — fsync владельца (см. FIX-02).
- `scripts/memory/tests/fix-04.test.js` — новый регрессионный тест сценариев приёмки (процессный уровень).
- `scripts/memory/save.js` — без изменений логики; проверить стабильный event_id для повторов (уже есть: `--event_id` или случайный).
- `docs/memory-contract.md` — секции Writer/Актуальность индекса: границы persisted (остановка процесса vs отказ питания), немедленное сохранение.
- `.scratch/system-completion/SPEC.md` — новая секция «Немедленное сохранение» с датированным примечанием источника требования (2026-09-09, ревью Opus / задание Sonnet); пометка «не выдавать за уже реализованную гарантию» снимается после FIX-01…04.
- `SC-REVIEW-MATRIX.md` (этот каталог) — обновить строку SC-08/R03 по факту.

## ⚠️ Файлы НЕЛЬЗЯ трогать

- Настоящую память и конфиги; реальный push. Все сценарии — на временных фикстурах и временном bare-remote.

## Входные/выходные данные

CLI: `node scripts/memory/save.js --category facts --statement "..." --evidence "..." [--scope user] [--event_id evt_...] [--source "..."]`. Ответ `{status:"persisted", written_files, revision}` — только после fsync+rename. Документация — в memory-contract.

## Алгоритм (шаг за шагом)

1. `writeAtomic`: `fd = fs.openSync(tmp, 'w')`; `fs.writeFileSync(fd, ...)`; `fs.fsyncSync(fd)`; `fs.closeSync(fd)`; `fs.renameSync(tmp, file)`. При ошибке — подчистить tmp.
2. Сценарии приёмки (реализовать как тесты на синтетической памяти):
   - **CLI без сервисов:** с выключенными Khoj (`integrations.khoj.enabled:false`) и без bridge/Activepieces/AI запись через `save.js` возвращает `persisted`; файл существует; **отдельный процесс** `search.js --query <маркер> --project <проект>` находит запись (fallback) после «перезапуска».
   - **Решение до конца сессии:** сохранить решение; завершить тестовый процесс; решение в канонической памяти (файл на диске). Для события, требующего AI до превращения в знание — долговечный capture (очередь, FIX-06) до подтверждения приёма; не обещать уже сохранённое знание.
   - **Прерывание внутри сохранения:** убить процесс после записи tmp/файла, но до ответа (спавн + kill); повтор того же event_id → без ложного persisted и без дублей (опирается на FIX-01); стабильный идентификатор операции — event_id.
   - **Сбой очереди индекса:** запись остаётся persisted, `indexed:false`, причина видна (см. FIX-07); отката записи нет.
   - **Offline-remote:** во временном git-репозитории с временным bare-remote: локальная запись persisted, `sync.js --status` показывает незасинхронизированные изменения памяти, `--push` не выполняется автоматически; проверка push и конфликта — на временном bare-remote (без внешнего push).
3. Документация: SPEC (новая секция, датированная), memory-contract (границы: остановка процесса — запись завершена rename'ом до ответа; отказ питания — fsync tmp перед rename, гарантия уровня ФС; окно «решение только во внутреннем контексте модели» невосстановимо — сокращаем немедленным сохранением).

## Критерии приёмки

- [ ] Сценарий «CLI без сервисов» проходит целиком (включая перезапуск процесса и поиск из разрешённого проекта).
- [ ] Сценарий «убийство процесса до ответа» + повтор: нет потери подтверждённого, нет дублей, нет ложного persisted.
- [ ] Сценарий «сбой очереди индекса»: запись persisted, отката нет, задача/причина восстановимы (пересечение с FIX-07).
- [ ] Сценарий «offline-remote»: persisted ≠ synced; push только явный; конфликт на временном remote не теряет версии.
- [ ] SPEC и memory-contract содержат требование немедленного сохранения и границы гарантий с датой 2026-09-09.

## Ограничения

Отказ питания: fsync до rename — гарантия уровня ФС/ОС (на NTFS обычно долговечно); «никогда не теряется» не обещается. Сценарии — только синтетические; к настоящей памяти не применяются до внешней приёмки блока.
