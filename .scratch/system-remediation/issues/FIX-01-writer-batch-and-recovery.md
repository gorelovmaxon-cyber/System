# FIX-01 — Writer: пакетная запись всех предложений и восстановление прерванной транзакции

**What to build:** Writer сохраняет все предложения одного события (включая несколько предложений одной категории) без потерь и без дублей; незавершённая запись (intent без файлов, частичная запись нескольких файлов) восстанавливается повторным вызовом, а не выдаётся за успех.
**Requirement IDs:** SC-08 (R03, R07), дефекты F01, F02.
**Blocked by:** none
**Status:** awaiting-review
**Перед началом работы:** корень `D:\SystemTheBest\System`, HEAD `69a257c`.

## Контекст

Аудит (evidence/CORE-AUDIT-2026-09-09.md) воспроизвёл:
- **F01:** два предложения одной категории из одного события — сохраняется только первое: проверка `existing.includes('event_id: '+eventId)` выполняется внутри цикла уже после первой записи и пропускает остальные.
- **F02:** журнал с intent и корректным hash, но без файла памяти — повтор возвращает `{status:"persisted", idempotent:true}` при отсутствующей памяти. Writer не различает intent и завершённый persisted.

Требование: идемпотентность всей операции с сохранением каждого предложения, восстановление незавершённой транзакции, прерывания «до первого файла», «между файлами», «между записью и подтверждением».

## Входные/выходные данные

Вход `writeProposal(eventId, proposals|proposal)`: поля предложения `category, status, scope, statement, evidence, source, confidence?, supersedes?`.
Выход: `{status:"persisted", written_files:[...], revision}` или `{..., idempotent:true}` для точного повтора; `CONFLICT` (код) для другого содержимого того же event_id.

## Алгоритм (шаг за шагом)

1. `hash = proposalHash(eventId, proposals)` (существующий, по всем предложениям). `previous = writerLog.get(eventId)`.
2. Если `previous` и `previous.hash !== hash` → `CONFLICT` (как сейчас).
3. Быстрый путь идемпотентности: `previous.status === 'persisted'` и hash совпал и **все записи присутствуют** в целевых файлах (проверка по entry-блоку: `entryPresent(file, eventId, proposal)` — блок с `event_id` и точным statement) → вернуть `{..., written_files: previous.written_files, revision: previous.revision, idempotent:true}`. (Индексная сверка — в FIX-07.)
4. Иначе — путь записи/восстановления: под блокировкой для каждого предложения: если `entryPresent` истинно → пропустить (это и устраняет F01, и не создаёт дублей при восстановлении); иначе `writeAtomic` (существующая атомарная запись).
5. В журнал: intent при входе в путь записи; по завершении — persisted с written_files/revision. Повтор intent при восстановлении допустим (журнал append-only, последняя запись выигрывает).
6. Очередь индексации: существующий вызов сохранён; при падении `queueIndex` в журнал persisted дописывается `index_error: <причина>` (видимая причина), запись не теряется.

## Критерии приёмки

- [ ] Один event_id, два предложения одной категории → оба текста в файле; повтор события не добавляет дублей (количество вхождений маркеров не растёт).
- [ ] intent с корректным hash, без файла → повтор возвращает persisted и файл создаётся (восстановление, не ложный успех).
- [ ] Частичная запись нескольких файлов (например, факт записан, решение — нет) → повтор дописывает недостающее без дублей.
- [ ] Точный повтор завершённого события → idempotent:true, revision прежний, журнал не разрастается новыми intent/persisted.
- [ ] Другое содержимое того же event_id → CONFLICT.

## Доработка по ревью S2/S3 (2026-09-09, раунд 2)

**Замечание S2 (P1):** `entryText` напрямую вставлял `source` во frontmatter; `parseFields` при чтении брал последнее значение дубликата. Вход `source: "source text\nscope: user"` проходил валидатор, на диске появлялись две строки `scope:` (B и user), и проект A получал приватную запись B со scope:user — изоляция нарушалась легитимным сериализатором без внешнего повреждения файла.

**Замечание S3 (P2):** `entryPresent` нормализовал `existing` через `normalizeEol`, но `expected = entryText(...).trim()` сохранял CRLF внутри statement → многострочный CRLF-вход при повторе давал две копии записи (в отличие от R4 — это CRLF во входных данных, а не преобразование файла после записи).

### Инварианты однозначной сериализации proposal → текст → запись

1. **Взаимная однозначность:** разбор сохранённой записи возвращает те же значения полей, что были в валидированном предложении (round-trip); вход не может создать поля (`scope`, `status`, `event_id`) или границы записи, которых не было в предложении.
2. **Frontmatter-поля — однострочные:** `event_id`, `source`, `evidence`, `supersedes` (и enums `category`/`status`/`scope`, число `confidence`) не содержат `\n`/`\r`. Нарушение — ошибка валидации (400), запись не выполняется. (Формат-канон `.claude/memory/README.md` описывает эти поля как однострочные YAML-значения.)
3. **`statement` — многострочное тело:** строка не начинается с `---` (иначе при разборе создаётся граница записи); переносы нормализуются к LF (S3).
4. **`entryText` детерминирован:** поля вставляются без потерь и без склеивания (`replaceAll('\n',' ')` для evidence удалён — однострочность гарантируется валидацией); `event_id` берётся из валидированного аргумента `writeProposal`.
5. **Каноническая форма содержимого — LF:** вход нормализуется в `validateProposal` ДО вычисления hash; LF и CRLF формы одного содержимого дают один hash (идемпотентный повтор, не CONFLICT); файл хранится в LF; `entryPresent` дополнительно нормализует expected (защита legacy/восстановления). Нормализация не скрывает содержательные различия: разное содержимое того же event_id по-прежнему даёт CONFLICT.

### Исправление (writer.js)

- `validateProposal`: `source`/`evidence`/`supersedes` — однострочные (`singleLine`, отклонение CR/LF); `statement` — `normalizeEol` + отклонение строк, начинающихся с `---`; возвращает нормализованные значения (повторная сериализация детерминирована).
- `writeProposal`: `event_id` валидируется (`validateEventId`: непустая однострочная строка) до записи в журнал/hash/файл.
- `entryText`: `source`/`evidence`/`supersedes` берутся из валидированных значений напрямую; `replaceAll('\n',' ')` удалён.
- `entryPresent`: `expected = normalizeEol(entryText(...)).trim()` — одинаковая канонизация обеих сторон сравнения.
