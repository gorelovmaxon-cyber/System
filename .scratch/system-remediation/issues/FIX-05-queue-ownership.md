# FIX-05 — Очередь: владение задачей и защита подтверждённого результата

**What to build:** Два обработчика очереди (в одном или разных процессах) не обрабатывают одно событие одновременно; просмотр состояния не возвращает живое in-flight в pending; завершение устаревшим обработчиком не перезаписывает уже подтверждённый результат; аренда считается от момента захвата и ограниченно продлевается, пока владелец действительно доставляет. At-least-once сохраняется, получатель остаётся идемпотентным по event_id.
**Requirement IDs:** SC-07 (R07), дефекты F08, G03, G04.
**Blocked by:** none
**Status:** awaiting-validation

## Контекст

Аудит 2026-09-09: конструктор `DurableQueue` безусловно переводил in-flight в pending → второй обработчик доставлял событие, уже обрабатываемое первым; затем первый получал терминальную ошибку и `mark()` перезаписывал `delivered` на `failed` (журнал append-only, последняя запись побеждает).

Общий аудит 2026-09-12 добавил два дефекта того же класса — «аренда, посчитанная не в тот момент»:

- **G03:** `process()` брал `const now = Date.now()` один раз на весь проход и передавал его в захват. Аренда каждого следующего события считалась от начала прохода, поэтому после длинной первой доставки второе событие захватывалось с уже истёкшей арендой; любой другой процесс считал доставку осиротевшей и забирал её (`overlapping: true`, воспроизведено). Тот же снимок времени использовался для повторов.
- **G04:** в индексаторе `run()` тем же способом передавал единый `now` в захват, поэтому вторая задача в проходе получала аренду в прошлом (`expiredOnStart: true`, воспроизведено). Общий корень G03/G04 — «владение, выданное по устаревшему снимку времени»; блок исправляется целиком, хотя G04 относится к FIX-07/08.

## Файлы для изменения

- `scripts/memory/queue.js` — владение поколением аренды: переход в in-flight только через `claim()` (одна транзакция журнала), поля `lease_id` + `lease_expires_at`; завершение только через `finish()` с CAS по `lease_id`, поэтому устаревший обработчик не перезаписывает подтверждённый результат; `restoreInflight()` возвращает в pending только записи с истёкшей арендой, поэтому просмотр состояния не мутирует живое in-flight; `process()` пропускает событие с живой арендой.

## Входные/выходные данные

Запись очереди получает поля `lease_id`, `lease_expires_at` (только в in-flight; при завершении сбрасываются в `null`). Статусы без изменений: pending → in-flight → delivered|failed. `finish()` возвращает актуальную запись (текущую, если завершение устарело).

## Алгоритм (шаг за шагом)

1. `claim(eventId, options)`: одна транзакция журнала. Момент захвата `now = options.now ?? Date.now()` вычисляется **внутри** транзакции; принимаются только `pending|failed` (для `failed` нужен `redeliver`, для будущего `next_attempt_at` — тоже); пишется `{status:'in-flight', lease_id, lease_expires_at: now+leaseMs}`.
2. `finish(claimed, fields)`: транзакция; если текущая запись уже не `in-flight` или её `lease_id` не совпадает с захваченным — журнал не меняется (устаревшее завершение не перезаписывает подтверждённый результат).
3. `restoreInflight()`: в pending возвращаются только `in-flight` с истёкшим `lease_expires_at` (или без него — legacy-запись). Живая аренда не трогается, поэтому конструктор и `queue-status` безопасны для просмотра.
4. `process()`: предварительный отбор — только по статусу; решение о времени принимает `claim()`. Аренда, посчитанная от начала прохода, к моменту захвата следующего события была бы уже истёкшей, и живая доставка выглядела бы осиротевшей (G03). Захват → `startRenewal(claimed)` → доставка → `finish()`; в `finally` — `renewal.stop()`.
5. `startRenewal(claimed)`: `setInterval` с периодом `leaseMs/3` продлевает аренду через `renew()`; `renew()` — тот же CAS по `lease_id`, поэтому потерявшее аренду поколение ничего не перезаписывает, а первая же неудача прекращает продление. Продление ограничено длительностью доставки: таймер снимается в `finally`.
6. Отсчёт повтора в `catch` идёт от времени результата (`failedAt = Date.now()`), а не от начала прохода.
7. `redeliver()` — без изменений, работает с pending/failed.

## Критерии приёмки

- [x] Сценарий аудита 2026-09-09 (два `DurableQueue` в одном процессе, первый ждёт): событие доставляется ровно один раз; второй обработчик не получает его; конечный статус соответствует единственному обработчику.
- [x] Конструктор/`queue-status` при живом in-flight не переводит его в pending.
- [x] Осиротевший in-flight (истёкшая аренда) → при следующей обработке возвращается в pending.
- [x] Устаревшее завершение (`finish` после того, как событие уже delivered) не перезаписывает delivered.
- [x] Повторная доставка `--redeliver` и обычный happy-path не сломаны.
- [x] **G03:** аренда датируется моментом захвата; доставка, чья предыдущая итерация заняла 5 с при аренде 1 с, не становится доступной второму процессу.
- [x] **G03:** просроченная аренда по-прежнему восстанавливается (отказ не превращается в вечное владение).
- [x] **G03:** `next_attempt_at` отсчитывается от времени результата.
- [x] **FIX-05:** доставка, законно длящаяся дольше аренды (700 мс при аренде 400 мс), удерживает своё поколение; параллельный процесс не может её забрать.
- [x] **FIX-05:** продление прекращается вместе с доставкой и не возвращает аренду поколению, которое её потеряло.

## Ограничения

Межпроцессная гонка «два claim одновременно» возможна (append не атомарный между процессами), смягчается guard при захвате (вторая инстанция видит живой in-flight и пропускает). At-least-once с идемпотентным получателем — документированная модель; сетевого exactly-once не обещаем. Продление аренды ограничено длительностью доставки в процессе; смерть процесса продление прекращает вместе с собой.
