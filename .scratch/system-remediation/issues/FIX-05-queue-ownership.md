# FIX-05 — Очередь: владение задачей и защита подтверждённого результата

**What to build:** Два обработчика очереди (в одном или разных процессах) не обрабатывают одно событие одновременно; просмотр состояния не возвращает живое in-flight в pending; завершение устаревшим обработчиком не перезаписывает уже подтверждённый результат. At-least-once сохраняется, получатель остаётся идемпотентным по event_id.
**Requirement IDs:** SC-07 (R07), дефект F08.
**Blocked by:** none
**Status:** planned

## Контекст

Аудит: конструктор `DurableQueue` вызывает `restoreInflight`, который безусловно переводит in-flight в pending → второй обработчик доставляет событие, уже обрабатываемое первым; затем первый получает терминальную ошибку и `mark()` перезаписывает `delivered` на `failed` (журнал append-only, последняя запись побеждает). Даже `queue-status` (создание очереди) меняет активное состояние. Нужны атомарное владение задачей и проверка актуального состояния при завершении.

## Файлы для изменения

- `scripts/memory/queue.js` — владение: `claim_id` (уникальный на процесс) + `claim_pid` + `claimed_at` при переходе в in-flight; модульный набор живых claims в процессе; `restoreInflight` переводит в pending только осиротевшие claims (нет claim_id в активном наборе И pid мёртв/отсутствует); `mark()` не перезаписывает результат, если текущая запись события уже не in-flight с тем же claim_id; `process()` пропускает событие с живым in-flight claim.
- `scripts/memory/queue-status.js` — показать `corrupt_count` не требуется здесь (FIX-06); здесь — убедиться, что просмотр не мутирует (покрывается тестом).
- `scripts/memory/tests/fix-05.test.js` — новый регрессионный тест.

## ⚠️ Файлы НЕЛЬЗЯ трогать

- `.local/` реальные очереди; контракт `deliver.js`/endpoint.

## Входные/выходные данные

Запись очереди получает поля: `claim_id`, `claim_pid`, `claimed_at` (только в in-flight). Статусы без изменений: pending → in-flight → delivered|failed. `mark` возвращает актуальную запись (текущую, если завершение устарело).

## Алгоритм (шаг за шагом)

1. `const activeClaims = new Set()` на уровне модуля. `claimId()` = `crypto.randomUUID()`.
2. `process()`: перед claim — `latest = records().get(id)`; если `latest.status === 'in-flight'` → пропустить событие (другая инстанция владеет). Claim: `mark(record, {status:'in-flight', claim_id, claim_pid: process.pid, claimed_at})`; добавить claim_id в `activeClaims`. В `finally` — удалить из набора.
3. `mark()`: если текущая запись переходит из in-flight (completion): `latest = records().get(id)`; если `latest.status !== 'in-flight' || latest.claim_id !== record.claim_id` → ве��нуть `latest` без записи (устаревший обработчик; подтверждённый результат не перезаписывается).
4. `restoreInflight()`: для in-flight: если `claim_id ∈ activeClaims` → skip (живой в этом процессе); иначе если `claim_pid` число и `process.kill(pid,0)` не бросает → skip (живой в другом процессе); иначе (нет владельца/мёртв) → append pending. Это делает конструктор безопасным для просмотра.
5. `process()` продолжает только `pending|failed`; in-flight не трогает.
6. `redeliver()` — без изменений, работает с pending/failed.

## Критерии приёмки

- [ ] Сценарий аудита (два `DurableQueue` в одном процессе, первый ждёт): событие доставляется ровно один раз; второй обработчик не получает его; конечный статус соответствует единственному обработчику.
- [ ] Конструктор/`queue-status` при живом in-flight не переводит его в pending.
- [ ] Осиротевший in-flight (мёртвый pid, без активного claim) → при конструкторе возвращается в pending.
- [ ] Устаревшее завершение (mark failed после того, как событие уже delivered) не перезаписывает delivered.
- [ ] Повторная доставка `--redeliver` и обычный happy-path не сломаны.

## Ограничения

Межпроцессная гонка «два claim одновременно» возможна (append не атомарный между процессами), смягчается guard в `mark()` при claim (вторая инстанция видит in-flight и пропускает). At-least-once с идемпотентным получателем — документированная модель; сетевого exactly-once не обещаем.
