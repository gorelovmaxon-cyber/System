# Общий независимый аудит System2 — 12 сентября 2026

## Итог и точка проекта

**Локальное ядро пока не принято.** Система не переписывается с нуля: существует существенная реализация, много прежних дефектов устранено и **100/100 штатных регрессий независимо проходят**. Однако сквозные аварийные сценарии выявили оставшиеся проблемы владения, восстановления производных состояний, путей, очереди и переноса.

Проверен один текущий пакет целиком по перечисленным ниже областям, а не только U1/U2. В новых harness воспроизведены **19 дополнительных сценариев G01…G19**. Это не 19 независимых корневых причин и не 19 одинаково критичных ошибок: G12/G14/G18 показывают незавершённые операции/интеграцию, G16 требует явного решения по контракту. Отдельно сохраняется V1 из [приёмки U1/U2](INDEPENDENT-REVIEW-2026-09-12.md). Проблемы сгруппированы в порядок доработки, чтобы не исправлять их по одному симптому за раунд.

**Граница честности:** общий аудит не доказывает отсутствие всех возможных ошибок. Проверены локальные исходники, штатные тесты и специально построенные сценарии. Live AP/Khoj/AI/Figma, реальная миграция/restore и домашняя конфигурация не проверялись. Полная эксплуатационная готовность остаётся отдельным этапом после приёмки локального ядра.

## Первый приоритет: владение и отсутствие потерь

### V1 · P1 · Устаревшая публикация guard после смерти keeper

Подробности и probe в [отдельном отчёте](INDEPENDENT-REVIEW-2026-09-12.md). Между чтением владельца и rename собственного metadata keeper может умереть; другой B успевает войти, после чего старый A заменяет его guard. AssertHeld A отказывает, но release удаляет уже испорченное владение. При последующем сбое keeper B третий процесс входит одновременно с живым B. Защитить всю передачу права, а не добавить ещё одну проверку перед rename.

### G15 · P1 · Один memory_root с разными data_dir допускает потерю записи без гибели процессов

`writer.acquireLock()` привязан к `data_dir/writer/memory.lock`, а изменяемые файлы — к `memory_root`. Две валидные конфигурации на одном ПК указывают одну и ту же память, но имеют свои стандартные `.local`. Их lock не пересекаются.

Проба останавливает A перед rename подготовленной памяти; B полностью сохраняет свою запись; A продолжает и заменяет файл своей старой копией. **Оба вернули persisted, в файле осталась A, запись B исчезла.** Никакой подмены metadata, сбоя keeper, удалённой ФС или внешнего редактора не требуется.

Sonnet: определить идентичность защищаемого ресурса по фактической памяти, включая допустимые алиасы путей. Если разделяемый memory_root не поддерживается, это должно быть явным проверяемым ограничением с отказом до записи, а не молчаливой потерей. Проверить две копии/два data_dir, custom roots, обычный последовательный доступ, восстановление и lock всех журналов. Не закрывать FIX-02 только тестом V1.

### G03/G04 · P1 · Срок владения задачей рассчитывается по устаревшему времени начала прохода

`queue.process()` и `indexer.run()` вычисляют now один раз перед циклом. Если первая доставка длится дольше lease, следующая задача получает lease_expires_at, который уже прошёл к моменту её фактического захвата.

G03 с управляемыми часами: пока второй callback ещё выполняется, другой экземпляр очереди уже восстанавливает и захватывает ту же задачу. G04: второй запрос индекса стартует с уже истёкшим lease. Это отличается от допустимого повторения после действительного истечения срока долгой задачи: здесь срок истёк **ещё до её начала**.

Sonnet, FIX-05/07: получать текущее время внутри атомарного claim каждой задачи, считать retry от времени результата, определить продление/ограничение долгой доставки. Проверить долгую первую задачу, вторую/третью, конкурентный worker, terminal/stale CAS и часы. Lease/CAS защищает журнал от устаревшего finish, но не делает внешние HTTP-эффекты exactly-once — нужна идемпотентность получателя.

## Индекс: единое восстановление производного состояния

### G01 · P1 · indexed:true остаётся при новых pending-задачах того же события

Сначала событие A полностью индексируется. B дописывает общий файл. Идемпотентный повтор A ставит новую задачу для новой file_revision, но writerLog A остаётся indexed:true: ветка сбрасывает его только при прежнем index_error. Проба: before=true, after=true, pending для A=1. Нарушен текущий контракт «все файловые задачи события завершены».

### G02 · P2 · Сбой между завершением index task и обновлением writerLog не восстанавливается

После успешного reindex задача уже indexed. Инъекция ошибки writerLog.append при indexed:true оставляет агрегат false. Повторный run возвращает [], поскольку задача больше не eligible. Ошибка первого прохода дополнительно выглядит как superseded, хотя причина — несохранённый агрегат. Одних retry для pending/failed недостаточно.

### G18 · P2 · Обещанный --reconcile отсутствует

FIX-07 явно требует reconcile() и CLI --reconcile для восстановления всех persisted-событий без задач. В текущем indexer ни функции, ни аргумента нет: команда завершается exit 1 с usage. F05 покрыт повторным предъявлением исходного предложения writer, но массовое восстановление без оригинального input не поставлено.

Sonnet, FIX-07/08: сделать одну проверяемую модель event/file revision/tasks/aggregate; восстанавливать missing tasks и несогласованные агрегаты; не подтверждать актуальность по устаревшему снимку задач. Реализовать предусмотренную операцию reconcile и повтор после сбоя на каждой межжурнальной границе. Проверить обратный случай, когда задача добавляется после проверки all-indexed, параллельный writer/indexer, удаление/смену файла и повтор без доступа к оригинальному AI-ответу. G01/G02/G18 — один согласованный блок, не три изолированные косметические правки.

## Границы чтения и исполнения путей

### G05 · P1 · Положительный Khoj-путь читает вне memory_root через junction

Writer/indexer enqueue используют path-safety, но search.sourceFile/relativeSource проверяют только лексический путь. Junction внутри синтетической памяти ведёт в другой TEMP с Markdown scope:user. Замоканный Khoj-hit ссылается на этот файл; search возвращает OUTSIDE_SECRET_MARKER как обычный источник `.claude/memory/linked/outside.md`.

Доказано локальное чтение и выдача внешнего по отношению к разрешённому корню файла. Никакие настоящие секреты не читались. Граница корня должна применяться на read-side тоже.

### G06/G13 · P1 · Indexer проверяет путь при enqueue, но доверяет ему при run

G06: восстановленная/изменённая запись журнала содержит `../../outside.md`; run отправляет это значение reindex-адаптеру и отмечает indexed. G13 сильнее для обычного жизненного цикла: корректный файл поставлен в очередь, затем до run его каталог штатно переименован и заменён junction на другой TEMP; run всё равно делает запрос и подтверждает indexed.

Доказана передача непроверенного задания mock-адаптеру и ложное успешное состояние. Реальная утечка через конкретный Khoj backend не проверена и не утверждается.

Sonnet, FIX-03/07 + общий path-safety: проверять фактические пути непосредственно при чтении/передаче задания, одинаково обрабатывать custom roots, относительные/абсолютные пути, junction/symlink и данные старых журналов. Проверить изменения файла/ревизии между enqueue и run. Не заявлять защиту от произвольного процесса с правом менять ФС в любой момент без соответствующего OS-механизма.

### G09 · P2 · Неизвестный project_id разрешён на положительном Khoj-пути

localResults отвергает незарегистрированный проект с unknown-project, searchKhoj при успешном сервисе этого не делает. Файл с scope:ghost-project выдаётся запросу ghost-project, хотя его нет в registry. Выполнять проверку project_id на общей входной границе до HTTP и fallback; неправильная конфигурация не должна менять допустимость запроса в зависимости от доступности сервиса.

## Идентичность и capture

### G07 · P2 · Порядок JSON-полей меняет hash того же предложения

validateProposal возвращает spread входного объекта, proposalHash использует обычный JSON.stringify. Полностью те же значения в обратном порядке ключей при повторе event_id вызывают CONFLICT. Итоговый Markdown при этом одинаковый. Для ответов внешнего AI порядок ключей не является содержательным отличием.

Sonnet, FIX-01: определить каноническую схему идентичности с фиксированными полями/порядком, defaults и исключением/валидацией лишних полей. Проверить перестановку ключей, одно и то же значение с явными defaults, реальные различия, старые intent/hash. Не ослаблять конфликт по содержанию ради устранения G07.

### G08 · P1 · createEvent молча отбрасывает неверно типизированные решения

createEvent({decisions:'KEEP_THIS_DECISION', ...}) возвращает валидное событие с decisions:[]; validateEvent уже не видит исходного значения. Аналогично нормализуются user_corrections/checks. Прямой enqueue проверяет массивы, но capture через createEvent может предварительно удалить содержательные данные.

Это неверный вход, который должен быть явно отклонён или обработан по задокументированному правилу, а не принят с незаметной потерей. Sonnet, FIX-06/capture: валидация исходного input до нормализации; прямой API и --file с неправильными типами, корректные массивы и отсутствующие необязательные поля.

### G19 · P2 · Первый commit сохраняется без diff

Hook использует `git diff HEAD^ HEAD`; у первого commit нет HEAD^. Ошибка подавляется, пустой файл передаётся capture. В настоящем TEMP Git-репозитории первый commit с INITIAL_DIFF_MARKER создал ровно одно событие, но его diff пуст. Сохранение самого commit не нарушено, утрачен вход для анализа содержимого.

Sonnet, FIX-11/capture: корректный root-commit diff и контролируемая политика merge-commit diff. Ошибки получения diff не выдавать за корректный пустой diff; сохранить поведение пустого commit и ограничение размера.

## Автономность, проекты и перенос

### G12 · Незавершённая интеграция · Worker делает только один проход

queue-worker drain возвращается после одной неудачной попытки с pending/next_attempt_at. В просмотренных scripts/services/docs не найден подключённый расписатель, который снова запускает его после восстановления сервиса; hook стартует его при новом commit. Внешний Scheduler на конкретной машине этим аудитом не инвентаризировался, его отсутствие в ОС не утверждается.

Sonnet, FIX-05/09/11: поставить согласованный механизм повторного drain и запуска после перезапуска среды либо явно оформить установку внешнего расписания с проверкой. Критерий: сервис недоступен → событие осталось durable → сервис доступен → без нового commit/ручного capture событие завершилось. Проверить один активный worker, backoff и остановку. Не вводить новый глобальный оркестратор без необходимости.

### G10 · P2 · Обратный порядок managed-маркеров не распознаётся как повреждение

initProject/replaceSection проверяет количество START/END, но не порядок. CLAUDE.md с END перед START принимается, добавляется новая секция и возникает второй START. HANDOFF с такими же маркерами ошибочно считается существующей корректной секцией. Проба содержит только синтетическое IMPORTANT_STATE.

Sonnet, SC-12/FIX-11: валидировать структуру обоих документов до любой записи и регистрации, включая обратный порядок/дубликаты/обрыв. При ошибке не оставлять частично обновлённые CLAUDE/registry. Сохранить повторный init без уничтожения текущего HANDOFF.

### G14 · Незавершённая интеграция · --register не связывает проект с его каталогом

initProject --register успешно записывает registry entry и CLAUDE/HANDOFF для new-project. Последующий projectId(тот же каталог) не находит проект: нет local_paths/remote, а CLAUDE он не читает. Hook без ручного SYSTEM2_PROJECT_ID тихо выходит без capture.

Sonnet, SC-02/12/FIX-11: регистрация должна сохранять нужную локальную привязку либо требовать/выдавать явный обязательный шаг настройки. Проверка от начала до конца: новый проект → init/register → обычный commit → событие правильного project_id без ручного подменивания env в тесте.

### G11 · P1 · Installer в Git worktree отключает существующий общий user hook

Installer смотрит только `$ROOT/.git/hooks/post-commit`. В linked worktree `.git` — файл, действующий default hooks лежит в общем git-dir. Без core.hooksPath, но с реальным пользовательским hook в common dir installer возвращает exit 0 и переключает hooksPath на шаблоны без --force/backup/chain. Исходный файл не удалён, но больше не выполняется.

Sonnet, FIX-11: определять эффективный hooks path средствами Git, включая common git-dir/worktree и область действия конфигурации. Проверять marker-поведение hooks до/после, безмолвное отключение недопустимо. Не менять hooks настоящего рабочего репозитория во время тестов.

### G17 · P2 · sync --push выбирает имя локальной ветки вместо её upstream-ветки

В TEMP local-work отслеживает origin/main, содержит новый commit. sync --push проверяет отставание от origin/main, но исполняет push origin local-work. Итог pushed:true, на remote создаётся local-work, main остаётся прежним. Работа не удалена, но домашний pull main не получит её.

Sonnet, FIX-11/sync: согласовать, что означает push по умолчанию — выбранный upstream destination или явно указанная новая ветка; при несовпадении имён не сообщать пользователю неоговорённую «синхронизацию». Проверить refspec, разные remote/branch names, detached, diverged/behind, dirty/untracked и post-push SHA. Все проверки на локальном bare remote.

## Figma: граница контракта, не заявленная live-утечка

### G16 · Требует решения · nodeId фильтрует дерево узлов, но не общие styles

extractDesignTokens сначала собирает все file.styles, затем выбирает nodeId. Локальная фикстура с отдельным OUTSIDE_STYLE возвращает этот стиль при выбранном другом node. Новая B18-регрессия проверяет только узлы. Нужно решить и задокументировать, являются ли file-wide styles допустимым отдельным блоком ответа либо должны ограничиваться используемыми в выбранном subtree.

Sonnet, FIX-11/SC-14: расширить fixture-контракт вместе с видимостью fills, alpha, gap без padding, радиусами и nodeId из URL. Live API-формат и доступность стилевых значений подтвердить отдельно на разрешённом макете. Эти соседние пункты пока статическая зона проверки, а не дополнительные воспроизведённые G-дефекты.

## Порядок одного согласованного исправления пакета

1. **Владение:** V1 + G15; выбрать/обосновать весь протокол и допустимую топологию памяти до переноса lock в accepted. Проверить writer, journal, queue, indexer как пользователей одного примитива.
2. **Очередь/индекс:** G03/G04 и G01/G02/G18; claims по актуальному времени, reconcile, восстановление между журналами, честный indexed. Результат должен выдерживать сбои на всех переходах, а не только pass списка сценариев.
3. **Границы/идентичность:** G05/G06/G13/G09 и G07/G08; общая валидация, каноническая идентичность и совместимость старых данных.
4. **Полный локальный путь проекта:** G10/G14/G11/G19, затем G12/G17 — init → capture → повторная доставка → явная синхронизация в правильную ветку.
5. **Контракты и доказательства:** G16, незавершённые команды FIX-06 (`corrupt_count`/quarantine) и другие явные расхождения плана; реализовать или честно согласовать объём, не отмечать критерий выполненным только новым описанием.
6. **Независимая локальная приёмка:** позитивные регрессии, интеграционные аварийные расписания, перечень RED/GREEN с происхождением fixtures, проверка именно сохранённой ревизии/дерева.
7. **После принятого локального блока:** резервная копия/миграция, живой AP→AI→writer→Khoj, credentials/таймауты/idempotency, реальные Figma/второй ПК/restore, финальный SC-18. Самому Sonnet рубеж writer не закрывать.

Sonnet сам группирует находки по существующим FIX/SC, дополняет тикеты и выполняет; не нужно 19 новых разрозненных тикетов или глобальная перенарезка. Сохраняются принятые роли и архитектура. Сначала сохранить незакоммиченную работу без потерь, затем scoped-коммиты по результатам. Пользователь в этом проходе поручил аудит, а не production-исправления или push; проверяющий их не выполнял.

## Как воспроизвести и читать evidence

Из корня System:

```text
node .scratch/system-remediation/evidence/comprehensive-audit-2026-09-12.cjs
node .scratch/system-remediation/evidence/comprehensive-extra-2026-09-12.cjs
node .scratch/system-remediation/evidence/comprehensive-transfer-2026-09-12.cjs
```

Во всех трёх **exit 0 означает, что перечисленные проблемные/обсуждаемые поведения воспроизведены**, не успешную приёмку. Exit 1 — не все воспроизведены; exit 2 — ошибка harness. JSON содержит детали каждой проверки. Сначала сохранять historical JSON: повтор перезаписывает results. После исправления нужны позитивные ожидания; отсутствие reproduced само по себе недостаточно.

При первом запуске transfer harness G19 не воспроизводился, поскольку в синтетическом SYSTEM2_ROOT не было scripts/memory и hook корректно вышел до capture. Фикстура дополнена копией текущих скриптов; после этого первый commit создал событие с пустым diff. Исходный неполный запуск сохранён как comprehensive-transfer-2026-09-12-incomplete-fixture.json и не выдается за доказательство дефекта.

**Что считать завершением этого аудита:** найденные проблемы сведены в один воспроизводимый пакет, положительные проверки и непроверенные области разделены. Что не завершено: исправления, приёмка ядра и запуск всей системы. Skill-forge текущего lock не выполняется.
