# PROFILE-01 — актуализировать профиль без выдуманных предпочтений

**What to build:** Сделать существующий профиль пользователя пригодным для текущих рекомендаций: явно отделить подтверждённые решения от исторических наблюдений, убрать неоднозначность устаревших советов и дать короткую навигацию по актуальным источникам. Историю сохранить; неподтверждённые предпочтения не заполнять догадками.
**Requirement IDs:** P01–P05 ниже.
**Blocked by:** none для сверки и актуализации по существующим источникам; новые предполагаемые предпочтения зависят от подтверждения пользователя.
**Status:** ready-for-agent.
**Перед началом работы:** открыть `D:\SystemTheBest\System`, проверить корень Git и рабочее дерево. Это задача профиля общей системы ПК, не сайтов, не восстановления Khoj и не нового аудита core.

## Контекст и подтверждённые пробелы

Пользователь 2026-10-22 попросил просмотреть профиль и дать задание только при реальной необходимости. Проверены пять файлов `.claude/memory/user-profile/` и индекс MEMORY.md.

- В writer-entries.md четыре confirmed-записи: выбор ролей, стандарт сайтов, стандарт операционных карт, команда ОК. Не переписывать их payload и не создавать дубликаты.
- architecture-prefs, coding-style, common-mistakes и work-patterns — исторические observation с источником 2026-09-08. Их формулировки местами выглядят как действующие обязательные инструкции.
- Конкретные примеры: common-mistakes — always stash, always GRILL, one ticket = one file = one stop, full suite after every change; architecture-prefs — обязательный `/clear`; work-patterns — одна задача/один файл и экономия 60×; coding-style — безусловные стек/структура и stash. Номера строк не считать устойчивыми, найти текст на месте.
- Эти утверждения не должны отменять актуальный workflow, соразмерность проверок, сохранение контекста и выбор ролей пользователем. Непроверенные экономические цифры не являются измеренными выгодами.
- Индекс называет writer-entries только Current role selection и датирован 2026-10-08, хотя содержит также решения о сайтах и ОК. Исторические файлы названы как обычные текущие предпочтения.
- Предложение о трёх моделях-проверяющих в беседе пока не принято пользователем. Не записывать его как действующий процесс. Запрет менять сайты в обновлениях не превращать в вечный запрет любой работы над сайтами.

## План и неизвестное

Основной путь: прочитать ограниченный набор источников → сопоставить утверждения с подтверждениями → обновить индекс и пометки исторических разделов → сохранить только реально новые подтверждённые предпочтения через writer, если такие найдены → проверить поиск и ссылки → передать отчёт.

Первая проверка: сопоставить повторяющиеся спорные утверждения с актуальными CLAUDE/system-workflow/planner-brief и четырьмя confirmed-записями. Не считать существование старой строки подтверждением предпочтения пользователя.

Рубеж пересмотра: если два подтверждённых источника несовместимы и порядок замены неясен, оставить точный вопрос, не выбирать предпочтение за пользователя. Если для устранения выдачи старого знания требуется менять retrieval, индексатор или writer — описать наблюдение и остановить эту ветку; код памяти не входит в задачу.

## Файлы для изменения

- `.claude/memory/MEMORY.md`: актуальное описание confirmed-записей, явные пометки исторических observation и понятный порядок чтения. Кратко указать, где лежат предпочтения, текущие правила и проектные решения; не копировать в индекс полный workflow.
- Четыре исторических user-profile-файла: краткие предупреждения и точечные пометки около спорных разделов со ссылками на актуальные источники. Исходное историческое содержимое сохранить, не переписывать его как будто пользователь изменил мнение сегодня. Не помечать весь смешанный файл superseded, если заменены лишь отдельные утверждения.
- Только при обнаружении нового прямого подтверждённого предпочтения: штатные journal/writer-артефакты с точными source/evidence/scope и устойчивым event_id. Отсутствие новых предпочтений — корректный no-op, это не недостаток результата.
- `.scratch/profile-refresh-20261022/RESULT.md`: один компактный отчёт — что было неактуально, что изменено, источник, проверки, оставшиеся вопросы. HANDOFF — короткая передача. Не создавать отдельные дублирующие профили, длинные матрицы или новый skill.

## Нельзя трогать

Код writer/search, интеграции, конфиги/hooks, глобальные настройки клиента, проекты сайтов/VPS, документы резюме, чужие pending и текущие dirty/untracked. Существующие payload/event_id в writer-entries не редактировать вручную и не удалять. Не переносить проектные факты или машинные пути в общий user-profile.

## Вход и выход

Вход — сохранённые предпочтения с источниками, действующие правила и исторические наблюдения. Выход — понятный актуальный указатель и корректно обозначенная история. Это не анкета личности и не обещание автоматического чтения профиля каждым клиентом.

## Алгоритм

1. Снять Git-состояние; сохранить ограниченный резерв затрагиваемой памяти/HANDOFF/журналов и writer-log вне репозитория до правок. Не архивировать всю System.
2. В одном отчёте кратко разделить найденное: подтверждено; заменено конкретным решением; историческое/непроверенное; требует ответа. Различать предпочтение пользователя, правило проекта и совет автора старого текста.
3. Обновить навигацию MEMORY.md и локальные пометки рядом с конфликтующими рекомендациями. Приоритет — прямое последнее решение и действующий канон. Например, исторический full-suite-every-change больше не рекомендация для текущего процесса; не дублировать актуальные правила вместо ссылки.
4. Не объявлять общий стек пользователя установленным по одному старому проекту. Не превращать старые цифры 60× в факт или гарантированную экономию: явно обозначить отсутствие подтверждённого применимого измерения.
5. Если новые предпочтения подтверждены первоисточником, использовать journal → save.js → search → mark по действующему контракту. Повторно разрешение на сохранение прямого решения не спрашивать; гипотезу не повышать до confirmed. Новые вопросы собрать максимум в три существенных пункта и передать одним сообщением, только если ответы реально меняют рекомендации. Независимую часть выполнить без ожидания.
6. Проверить фактическую выдачу поиска по ролям, ОК и одному устаревшему совету. Старая observation может оставаться в выдаче: проверить её метаданные и возможность установить актуальный источник, не заявлять, что supersedes автоматически удаляет старый результат. Если этого недостаточно для безопасной интерпретации, честно зафиксировать ограничение, не исправлять движок в этой задаче.
7. Проверить diff, ссылки и сохранность прежних payload/чужих правок. Передать на независимую приёмку; не расширять задачу новым циклом изучения личности пользователя.

## Критерии приёмки

| ID | Доказательство |
|---|---|
| P01 | Из MEMORY.md понятно, что подтверждено, что историческое и где текущие правила; все четыре подтверждённые темы доступны без чтения всего архива |
| P02 | Все перечисленные выше конфликтующие советы явно обозначены у соответствующих разделов; история сохранена, нет новой безусловной инструкции из предположения |
| P03 | Каждое новое confirmed-предпочтение имеет прямое основание и правильный scope; нет дублей, проектных фактов, вымышленных предпочтений и автоматического принятия схемы трёх моделей |
| P04 | Локальный поиск проверен на существующих данных, source/scope/status показаны корректно; ограничения retrieval описаны, отсутствие Khoj не скрыто |
| P05 | Diff ограничен профилем/индексом/обоснованными journal-writer записями и отчётом, прежние dirty сохранены; ссылки и check проходят либо указан конкретный блокер |

## Проверки

Из корня System: `git status --short`, `git diff --check`, `npm run check` (один раз после содержательных правок). Для поиска существующих записей:

```powershell
node scripts/memory/search.js --query "планировщик исполнитель приёмщик" --project systemqwen --limit 3
node scripts/memory/search.js --query "операционных карт" --project systemqwen --limit 3
node scripts/memory/search.js --query "full test suite after every change" --project systemqwen --limit 3
```

Выдачу сравнить с файлами, а не только exit code. Если формулировка не находится, указать факт и сделать один осмысленный уточняющий запрос. Не добавлять тестовые факты. Полный memory suite, restore, живые агенты, платные API и запуск Khoj/bridge не нужны. Если требуемая проверка недоступна — awaiting-validation с причиной.

## Как закончить

RESULT.md: конкретные улучшения навигации/пометок, новые подтверждённые записи либо честный no-op, проверки, открытые вопросы, сохранность. Статус awaiting-review, не self-done. При scoped-коммите явно выбрать только свои изменения; чужие строки HANDOFF и памяти не захватывать. Новые записи writer коммитить по контракту, если они создавались. Push не выполнять: публикация всей расходящейся/неопубликованной истории не входит в актуализацию профиля.

Не обещать полностью заполненный профиль, автосохранение всех бесед или гарантированное применение всех рекомендаций. Цель — проверяемые актуальные сведения и ясная граница неизвестного.
