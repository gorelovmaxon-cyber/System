**What to build:** Скилл для ручного обновления user-profile после завершения задачи

**Blocked by:** none

**Status:** ready-for-agent

**Перед началом работы:**
Открой VS Code в папке `D:\System` (File > Open Folder).

## Контекст

**Файлы для создания:**
- [D:\System\.claude\skills\profile-update\SKILL.md](D:\System\.claude\skills\profile-update\SKILL.md)

**Смежные файлы для понимания контекста:**
- [D:\System\memory\user-profile\coding-style.md](D:\System\memory\user-profile\coding-style.md) — структура файлов user-profile
- [D:\System\memory\user-profile\architecture-prefs.md](D:\System\memory\user-profile\architecture-prefs.md) — пример содержимого
- [D:\System\.claude\skills\auto-learn\SKILL.md](D:\System\.claude\skills\auto-learn\SKILL.md) — похожий скилл для понимания структуры

Нужно создать скилл `/profile-update`, который анализирует последнюю завершённую задачу и предлагает обновить файлы в `D:\System\memory\user-profile\`.

**Цель:** После каждой задачи можно вручную вызвать `/profile-update` и система предложит, что добавить в профиль пользователя.

- [ ] Создать папку `D:\System\.claude\skills\profile-update\`
- [ ] Создать файл `SKILL.md` с frontmatter и инструкцией
- [ ] Описать шаги анализа последней задачи
- [ ] Описать логику предложений по обновлению профиля

## Файлы для создания

- `D:\System\.claude\skills\profile-update\SKILL.md` — основной файл скилла

## Алгоритм (шаг за шагом)

1. **Создай папку для скилла:**
   ```bash
   mkdir -p /d/System/.claude/skills/profile-update
   ```

2. **Создай файл SKILL.md с frontmatter:**
   ```markdown
   ---
   name: profile-update
   description: Анализирует последнюю задачу и предлагает обновить user-profile (D:\System\memory\user-profile\). Вызывается вручную после завершения задачи или автоматически через auto-learn.
   ---
   ```

3. **Добавь раздел "# profile-update"** с описанием скилла

4. **Добавь раздел "## Когда запускается":**
   - Вручную: `/profile-update` после задачи
   - Автоматически: из `/auto-learn` если найден новый паттерн в стиле пользователя

5. **Добавь раздел "## Шаги" с детальным алгоритмом:**

   **Шаг 1:** Проанализировать последнюю задачу
   - Что делали (из git log или истории диалога)
   - Какие решения принимали
   - Какой стиль кода использовали
   - Какие технологии применили
   
   **Готово, когда:** есть список из 3-5 наблюдений

   **Шаг 2:** Определить категорию для обновления
   - `coding-style.md` — если нашли паттерны кода, стиль именования, форматирование
   - `architecture-prefs.md` — если нашли архитектурные решения, выбор технологий
   - `common-mistakes.md` — если нашли ошибку и как её исправили
   - `work-patterns.md` — если нашли паттерн работы, workflow, организацию
   
   **Готово, когда:** категория определена

   **Шаг 3:** Предложить конкретное обновление
   - Показать, в какой файл добавить
   - Показать, в какую секцию
   - Показать конкретный текст для добавления
   - Спросить подтверждение: "Добавить?"
   
   **Готово, когда:** пользователь ответил "да" или "нет"

   **Шаг 4:** Если "да" — обновить файл
   - Прочитать существующий файл
   - Найти подходящую секцию (или создать новую)
   - Добавить новую информацию
   - Сохранить файл
   
   **Готово, когда:** файл обновлён

   **Шаг 5:** Обновить MEMORY.md если нужно
   - Если добавлена новая секция — обновить индекс
   
   **Готово, когда:** индекс актуален

   **Шаг 6:** Резюме
   - "Обновлён `user-profile/<файл>`, секция `<название>`"
   - "Будет доступно в следующих сессиях"
   
   **Готово, когда:** пользователь уведомлён

6. **Добавь раздел "## Что НЕ записывать":**
   - Разовые решения специфичные для одного проекта
   - Временные workarounds
   - То, что уже есть в профиле
   - Факты о проектах (это в `facts/`, не в `user-profile/`)

7. **Добавь раздел "## Gotchas":**
   - Не дублировать существующую информацию — сначала проверить файл
   - Не записывать детали проекта — только стиль/подход пользователя
   - Спрашивать подтверждение перед записью

8. **Добавь раздел "## Пример вызова":**
   ```
   Пользователь: /profile-update
   
   Claude: Анализирую последнюю задачу...
   
   Нашёл паттерн: используешь explicit stop gates между фазами работы.
   
   Предлагаю добавить в work-patterns.md, секция "Workflow":
   
   ### Explicit Stop Gates
   Всегда останавливаюсь после каждой фазы (grill → spec → tickets → implement).
   Никогда не продолжаю автоматически без подтверждения пользователя.
   
   Добавить? (да/нет)
   
   Пользователь: да
   
   Claude: ✅ Обновлён user-profile/work-patterns.md, секция "Workflow"
   Будет доступно в следующих сессиях.
   ```
